## 1. ターゲット1(主成果): (a) 搬入経路の封鎖の分解

### 1.1 測定設計 — 何を「厳密化」したのか

Phase22 の搬入経路判定は**楽観近似**だった。荷物を「最終高さのまま +y 方向へ掃引する」
とみなし、以下をすべて無視していた。

| 無視していた要素 | 実際の挙動(`validator.check_transport_path`) |
|---|---|
| 浮上 | 底面が直置き面(床 / 棚上面)の 0〜50mm 上でなければ `START_Z=80mm` 持ち上げて掃引する |
| 天井クリップ | 浮上後の天面が中間高さ(棚下面)・天井に近いと `effective_start_z` を切り詰める |
| z 余裕 | 掃引中は障害物に対し `SWEEP_Z_MARGIN=15.5mm` の z 方向余裕が必要 |
| xy 余裕 | 掃引中は `SAFETY_MARGIN_XY=22mm` の横方向余裕が必要 |
| **x 掃引** | 目標 x が搬入可能域(切り欠き `cut_x` で左が削られる)の外なら、いったん境界で y 掃引してから **x 方向へも掃引**する |

`tools/phase24_corridor_audit.py` はこの5点すべてを validator と同式で再現する。
実装上の要点は、Phase22 の「voxel を膨張させて判定する」方式をやめ、
**支持まで通った候補位置だけを疎に取り出し、位置ごとに y掃引箱・x掃引箱と全障害物の
AABB 分離判定を連続座標で行う**ように変えたこと(voxel 化による量子化誤差が
搬入経路の判定から消える。位置の離散化だけが残る)。障害物は
`geo.packed_obstacles` + `geo.static_obstacles` に限る —— `validator._move_item` は
**コンテナ壁とは当たり判定しない**(壁・切り欠きは搬入開始 x の制限としてのみ効く)ことを
`src/ground_handling/validator.py` で確認したうえで一致させている。

Stage A((c) を production の実コードで測って行き詰まり状態を進める)は Phase22 と
同一実装のまま残してあるので、両フェーズの数値は同じ土俵で比較できる。

### 1.2 (a) の真の大きさ: 17.49 → 29.99 m³

26シーンの行き詰まり状態(強い探索で (c) を追加配置したあと)に対する測定結果。

| 量 | 値 |
|---|---|

| 置けた体積(production, Phase23 b=3) | 56.823 m³ → 体積利用率 **39.5%** |
| 強い探索での追加配置 (c) | 6.421 m³ |
| (c) 適用後の空き体積 | **77.298 m³** |
| 換算係数 | **1 m³ = 0.438 pt**(fill_strict, Phase21 の `fill_strict ≒ 0.63 × 体積利用率` より) |

| 搬入経路の判定 | (a) の体積 | 空きの% | fill換算 |

| Phase22 の楽観近似(参考再計算) | 17.492 m³ | 22.6% | 7.66 pt |

**楽観近似は (a) を 42% 過小評価していた**(29.993 → 17.492 は −41.7%)。
指示にあった「実際の (a) はもっと大きい」という見立ては正しく、しかも

逆側の数字も出ている: 「支持もあり搬入経路も生きている」空間は
**4.261 m³(空きの 5.5%)しかない**。つまり **行き詰まり状態の空きのうち、
今すぐ物理的に使える余地はほとんど残っていない**——(a) を開けない限り、
配置能力をいくら上げても届かない。

### 1.3 (i) 帯域別 — 封鎖の 39.9% は「浮上しない帯」

「その空間へ到達する配置が `is_resting` になるか」で (a) を排他分割した
(低い帯を優先。`is_resting` の判定は validator と同式で、
**底面が直置き面(床 `thickness` / 中間高さ `height/2+thickness+buffer`)の 0〜50mm 上**かどうか)。

| 帯域 | 体積 | (a)の% | fill換算 | この帯の実効不感帯 |
|---|---|---|---|---|
| 床直置き帯 | 2.237 m³ | 7.5% | 0.98 pt | `REST_CLEARANCE − SWEEP_Z_MARGIN` = **0.0005 m** |
| 中間高さ(棚上面レベル)直置き帯 | 9.740 m³ | 32.5% | 4.27 pt | 同上 **0.0005 m** |
| 浮上帯(非直置き) | 18.016 m³ | 60.1% | 7.89 pt | `RC + START_Z − SWEEP_Z_MARGIN` = 0.0805 m |
| **直置き帯 合計** | **11.977 m³** | **39.9%** | **5.25 pt** | |

**これが指示の「穴1」の直接の実測である。** 現在の `CORRIDOR_DEADBAND = 0.0805` は
「後から差し込む荷物が `START_Z=80mm` 浮上する」ことを前提にした値だが、
**封鎖されている空間の 39.9% は、その前提が成り立たない帯にある**。そこへ向かう荷物は
浮上せず最終高さのまま掃引されるため、通路が生きている条件は
`手前の天面 ≤ 奥の天面 + 0.0005 m` であり、実効的な不感帯はほぼゼロ。
現行実装はこの帯の通路に対しても一律 80.5mm の猶予を与えており、
**その帯の通路を塞ぐ候補にペナルティが一切かからない**。

重要な補足: 「棚上面レベル」は棚のあるシーンに限った話ではない。判定は
**底面の絶対高さ**で行われるので、積み上げた荷物の天面がたまたま
`height/2 + thickness` の 5cm 帯に入れば、その上に置く荷物も浮上しない。
実際、大棚を持たない `A01`(1c_40_plain)でも 0.266 m³ がこの帯にある。
**この帯は「棚」ではなくコンテナ中央高さを横切る水平な帯**である。

分布も偏っていない: **26シーン中 22シーンで直置き帯の封鎖が発生**しており、
(a) に占める割合は上位シーンで 43〜78%(`D03` 78%、`A05` 63%、`B03` 54%、`P03` 52%)。

| 仮説 | 判定 |

## 2. ターゲット2: 削減 — 実測して不採用(ただし理由が特定できた)

### 2.1 対策の設計(新しい調整パラメータを増やさない)

§1.7 の判定に従い、**穴1だけ**に対策する。`_corridor_excess` の不感帯を、
**奥の天面がどの種類の面かによって物理から一意に決める**ように一般化した。

```
その天面 T の上に着地する将来の荷物の底面は  T + REST_CLEARANCE
  それが直置き判定 (0 <= 底面 - r_z <= 0.05, r_z ∈ {thickness, height/2+thickness+buffer}) に入る
      -> 浮上しない -> 不感帯 = REST_CLEARANCE - SWEEP_Z_MARGIN            = 0.0005 m
  入らない
      -> START_Z 浮上する -> 不感帯 = REST_CLEARANCE + START_Z - SWEEP_Z_MARGIN = 0.0805 m
```

どちらも `REST_CLEARANCE` / `START_Z` / `SWEEP_Z_MARGIN` の3定数から導かれる値で、
**新しいハイパーパラメータではない**。Phase14 が「物理から一意に導出した不感帯」を入れて
応答をカオスから単峰に変えた設計方針を、そのまま帯域別に一般化しただけである。

実装上は、`min(天面) + 不感帯` ではなく **`min(天面 + その天面の不感帯)`** を取る形に変えた
(不感帯が面ごとに違うので、最小値を取る前に足す必要がある)。
併せて `CORRIDOR_MIN_HEADROOM` による「そこにはもう何も入らない天面は守らない」判定を
障害物ごとに適用する形へ移した。

**この一般化が Phase23 と厳密に等価であること(既定 `uniform` モード)を2重に確認した。**

1. 乱数 300 ケース(候補200点 × 障害物 0〜11個)で旧実装との差の最大値が **0.0**。
2. 26シーンの `uniform` 実行が Phase23 の suite 平均 **fill_strict = 25.684830854** を
   **小数第9位まで完全再現**。

### 2.3 なぜ効かなかったのか — 実行時プローブで機序を特定した

「機序は §1.3 で実測したとおり実在するのに、なぜ決定が動かないのか」を、
`tools/phase24_probe.py` で**実行時に候補単位で数えて**特定した
(`_corridor_excess` をラップし、同じ入力に対して uniform と surface の両方を計算して比較する)。

| シーン | 大棚 | 評価した候補数 | excess>0(現行) | **不感帯が縮んだ候補** |
|---|---|---|---|---|
| A01_1c_40_plain | 無 | 5,633,170 | 57.52% | **83 件 (0.00%)** |
| P03_A_2c_pre8_prio | 無 | 2,174,014 | 43.92% | **0 件 (0.00%)** |
| C02_2c_55_shelfprio | 有 | 4,645,437 | 41.68% | 440,186 件 (9.48%) |
| P05_C_2c_pre8_shelfprio | 有 | 2,481,313 | 50.25% | 451,875 件 (18.21%) |
| **合計** | | 14,933,934 | 49.41% | 892,144 件 (5.97%) |

**corridor_penalty 自体は極めてよく効いている**(評価候補の **49.4%** が excess>0)。
にもかかわらず不感帯の帯域別化が届く候補は全体の 5.97% で、しかも
**大棚を持つコンテナにほぼ限定される**(大棚無しでは 0.00%)。

理由は幾何から追える。不感帯が縮むには「候補より奥にあり、同一Xレーンで重なり、
かつ**天面が直置き帯(床から 34mm 以内 / 中間高さ ±3.4cm)に入る**障害物」が
**拘束面になる**必要がある。ここで2つの構造的な壁がある。

1. **`min` が低い面を選んでしまう。** 拘束面は `min(天面 + 不感帯)` なので、
   直置き帯の面 `T_high` が拘束するのは `T_high + 0.0005 < T_low + 0.0805`、すなわち
   **`T_high` が最低天面より 8cm 以内**のときだけ。これは狭い窓である。
2. **常設構造物は「奥」に来ない。** 小棚(全コンテナに存在)は
   `center_y=0, half_y=width/2−thickness` で**手前面がコンテナ最前面**にあるため、
   `behind` 判定が原理的に成立しない。大棚は `center_y=width/4, half_y=width/4−thickness`
   で手前面が `y=thickness` にあり、**手前半分の候補に対してのみ「奥」になる**。
   これが「大棚のあるシーンだけ発火する」ことの直接の原因である。

そして最も本質的な点として、**§1.3 で測った中間高さ帯の 9.740 m³ の多くは、
決定時点にはまだ存在しない天面である**。あの帯の「行き先の面」は、その後に積み上げた
荷物の天面がたまたま中間高さの5cm帯に入って生まれることが多い。
`corridor_penalty` は**既に置かれている障害物の上の通路しか守れない**ので、
**将来生まれる通路を守ることは原理的にできない**(myopia)。
不感帯をいくら正しくしても、この分は取りに行けない。

### 2.4 検討して採らなかった案

- **床を仮想障害物として corridor 障害物集合に足す(穴2の直訳)。** §1.7 のとおり
  床直置き帯は (a) の 7.5%(0.98 pt)しかないうえ、床は常に全候補の「奥」に存在するので
  `min_limit` が常に `thickness + 0.0005` に固定され、**実質的に「天面の高さそのもの」への
  一律ペナルティ(重み6.0)**に化ける。これは `z_term`(−12×world_z)と `back_term`(5.85、
  Phase6 で 5.8 / 5.9 の両側に崖が実測されている)への二重計上であり、
  積み上げを壊す方向の大きな変更になる。**測定上のリターンが 0.98 pt しかないのに
  リスクが大きすぎるため採らない。**
- **中間高さの平面そのものを仮想的な保護面にする。** 上と同じ理由で、
  「天面が中間高さを超えたら一律ペナルティ」に化けるため不可。
- **切り欠き(cut_x)に対応した候補生成・スコア項。** §1.4 で
  x掃引でだけ塞がれる体積が **0.003 m³(0.0%)** と実測され、対象が存在しない。

## 3. 結論と次フェーズへの申し送り

### 3.1 本フェーズで確定したこと

1. **(a) 搬入経路の封鎖は 29.993 m³(空きの 38.8%、fill換算 13.14 pt)** であり、
   Phase22 の楽観近似 17.492 m³ を **42% 上回る**。**空きの最大要因は (a) である。**
2. **「支持もあり経路も生きている」空間は 4.261 m³(空きの 5.5%)しか残っていない。**
   (a) を開けない限り配置能力の向上は届かない。
3. **封鎖の 39.9%(11.977 m³ = 5.25 pt)は「浮上しない帯」**にあり、
   現行の不感帯 80.5mm はこの帯に対して物理的に誤っている(**穴1は成立**)。
4. **穴2(床の前後関係)は量的に小さい**(a の 7.5% = 0.98 pt)。床は既に埋まっており、
   Z 分布でも床側3割は (a) の 9.7% しかない。**穴2の実体は床ではなく中間高さの帯**で、
   それは穴1と同じ機序である。
5. **コンテナ形状(切り欠き)は封鎖の原因ではない**(x掃引でだけ塞がれる体積 0.0%)。
6. **封鎖の 72.1% は既配置荷物だけが原因**だが、**単一障害物で塞がれているのは 23.6%
   (3.09 pt)にとどまり、55% は3個以上**に塞がれている。
7. **封鎖されている空間は「高くて奥」**(上位3割の高さに 51.2%、奥半分に 58.8%)。
8. 不感帯の帯域別化は **26シーンで +0.27(ノイズ内)/ 改善1・悪化0・同値25 で不採用**。
   届く候補が 5.97% しかなく、しかも大棚シーンに限定される(§2.3)。

### 3.2 本フェーズで消えた選択肢(再訪しないために)

- **不感帯の帯域別化(穴1の直接対策)**: 物理的には正しいが、
  `min` による拘束面の選択と常設構造物の y 位置という2つの幾何的制約で、
  評価候補の 5.97% にしか届かない(§2.3)。26シーンで +0.27。
- **床/中間高さ平面を仮想障害物として corridor に足す(穴2の直訳)**: 対象体積が小さく
  (0.98 pt)、一律の高さペナルティに化けて `back_term`/`z_term` と二重計上になる(§2.4)。
- **切り欠き形状に対応した候補生成・スコア項**: 対象が存在しない(§1.4、0.0%)。
- **「順序を1手入れ替えて封鎖を避ける」系の単発対策**: 上限が (a) の 23.6% = 3.09 pt
  (§1.5)。過半は3個以上の障害物による構造的封鎖なので、単発の入れ替えでは開かない。

### 3.3 次にやるべきこと

本フェーズの測定は、`corridor_penalty` の**枠組みそのものの限界**を指している。

- corridor_penalty は **既に置かれた障害物の上の通路しか守れない**(§2.3 の myopia)。
  しかし封鎖の主因である中間高さ帯・上部の通路は、**その後の積み上げで生まれる**。
- したがって効くのは「**置いた後にどんな通路が残るか**」を見る評価であり、
  それを持っているのは **オフライン順序探索(`simulate.py` の影シミュレータ)** の側である。
  影シミュレータは順序を最後まで流し込むので、封鎖の結果(=置けなくなった体積)を
  **事後に観測できる**。現在その情報は risk 調整済み体積という単一スカラーにしか
  反映されていない。

具体案(次フェーズの候補、いずれも本フェーズでは未検証):

1. **影シミュレータの目的関数に「行き詰まり時点の (a)」を加える。** 本フェーズの
   厳密判定は `tools/phase24_corridor_audit.py` に実装済みで、疎な位置集合に対する
   AABB 判定なので十分に速い。順序の良し悪しを「置けた体積」だけでなく
   「**残った空間のうち到達可能な割合**」でも測れば、自己封鎖する順序を事前に落とせる。
2. **ビームサーチ(Phase23, b=3)のスコアに同じ項を入れる。** Phase23 で
   探索の枠組みは既にビーム化されているので、評価関数の差し替えだけで済む。

いずれも「新しい大域重みペナルティ項の追加」(Phase18 の崖)ではなく
**オフライン探索の評価関数の変更**である点で、閉じた方向とは別筋であることを明記しておく。

### 3.4 未解決の持ち越し

1. `gen_2containers_priority` の stability 制約違反(96.87 < 97、Phase17から未解決)。
2. 本番の内包判定レジーム(strict/loose)。Phase16 の予算掃引が唯一の識別可能な観測だが n=1。
