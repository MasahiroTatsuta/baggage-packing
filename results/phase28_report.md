## 1. 実装方針

### 1.1 なぜ順序探索側なのか(Phase24 の設計をそのまま踏襲)

`corridor_penalty`(`planner._corridor_excess`)は **候補1手ごとに、その時点の障害物に対して**
罰則を課す。したがって「これから積み上がる荷物が作る通路」を守れない —— これが Phase24 が
特定した**時間方向の myopia** である(`results/phase24_report.md` §2.3)。封鎖の主因である
中間高さ帯・上部の通路は、その後の積み上げで初めて生まれるため、不感帯の精度をいくら
上げてもこの分は取れない(実測: `corridor_penalty` は候補の49.4%で発火するが、
帯域別化が届くのは 5.97%)。

一方、影シミュレータは順序を最後まで流し込むので、**「その順序が最終的に自己封鎖したか」を
事後に観測できる**。myopia の原因そのものを外している点が、本フェーズが Phase24 の再演に
ならない理由である。

### 1.2 到達可能性の定義

行き詰まり時点(= `simulate_order` のループが `action is None` で抜けた時点)で、
残っている全荷物 × 全 orientation を全 voxel 位置で列挙し、

| 量 | 定義 |
|---|---|
| `supported_volume` | 「残荷物のどれかが収まり、かつ支持がある」空き体積 |
| `blocked_volume` | そのうち **搬入経路が塞がれている**体積 = Phase24 の **(a)** |
| `blocked_ratio` | `blocked_volume / supported_volume` ∈ [0,1] |

判定式は `validator.check_transport_path` と同式(y掃引 → x掃引、浮上量の直置き判定と
天井クリップ、`SAFETY_MARGIN_XY`/`SWEEP_Z_MARGIN`)で、Phase24 の監査ツールと完全に同一。

### 1.3 目的関数への入れ方(加算ではなく乗算)

`ordering.validate()`:

```python
discount = max(0.0, 1.0 - REACH_WEIGHT * reach_info['blocked_ratio'])
return (risk_adjusted_volume * discount - penalty, count)
```

**加算ペナルティにしてはならない。** Phase18 が加算形で
「達成可能な体積より罰則が大きく、何も置かないほうが目的関数上は得」という退化解を引き当てて
おり(実測: `suite_A07_1c_40_bulky` で 40個中1個しか置かない順序が選ばれ fill 28.07→**0.00**)、
同じ構造を繰り返さないため、`stability_discount` と同じ**乗算の割引**にした。
これなら常に 0 以上で、達成した体積を超えて罰することがない。

さらに `blocked_ratio` の分母を `empty` ではなく **`supported`** にした。`empty` で正規化すると
「置かない順序ほど空きが大きく、封鎖の割合が小さくなる」ので、目的関数が
「何も置かない」方向へ直接引っ張られる。実際、事前調査で `empty` 正規化版は
最良順序(risk_vol 1.164)が最悪の blocked_ratio(0.619)を示し、
最悪順序(risk_vol 0.296)が最良の blocked_ratio(0.327)になっていた。

### 5.1 t=1.000 は構造的な上限であって偶然ではない

25シーンが 0、1シーンだけが d のとき:

```
mean = d/26
分散 = [25·(d/26)² + (d − d/26)²] / 25 = d²/26     →  σ = d/√26
SE   = σ/√26 = d/26 = mean
t    = mean/SE ≡ 1.000        (d に依存しない)
```

**単一シーンしか動かさない変更は、その1シーンでどれだけ大きな改善が出ても t=1.000 で
頭打ちになり、採用基準 t>2 を原理的に通過できない。** これは基準の欠陥ではなく、
「1シーンだけの改善は別シーン集合へ一般化する根拠にならない」という
Phase25a の設計意図がそのまま働いた結果である。

### 5.2 なぜ25シーンが動かなかったか(本フェーズの主成果)

`tools/phase28_rerank.py` で、`build_order` が実際に評価した**全候補順序**の
(risk_vol, placementペナルティ, blocked_ratio) を記録し(`simulate_order` を読み取り専用で
フックする手法は `tools/phase20_surrogate.py` と同じ)、
**「採用される順序が変わる最小の W」** を直接走査した。

| シーン | 候補数 | base目的関数の相対スプレッド | blocked_ratio スプレッド | **勝者が変わる最小 W** |
|---|---|---|---|---|
| A01_1c_40_plain | 6 | 32.6% | 0.4570 | **2.29** |
| A02_1c_80_plain | 7 | 72.1% | 0.3509 | **1.04** |
| A03_1c_40_shelf | 6 | 29.8% | 0.4570 | **0.23** |
| A04_2c_80_noprio | 6 | 29.3% | 0.4468 | **0.39** |

**閾値が 0.23〜2.29 と10倍に散らばっている。** W=0.25 で反応するのは A03 だけであり、
26シーン測定で1シーンしか動かなかった事実と完全に整合する。

決定的なのは**崖の位置との関係**である:

```
A03 が壊れる W (0.5 < W < 1.0)   <   A02 が反応し始める W (1.04)  <  A01 (2.29)
```

**A03 が崖から落ちた後でなければ、A02 も A01 も反応しない。**
つまり「広く効く W」と「どのシーンも壊さない W」の**共通区間が存在しない**。
これは Phase18 が単一大域重みについて出した結論
(「両方を同時に満たす重みの区間がそもそも存在しない(崖の位置がシーン間で逆転)」)が、
**まったく別の項に対して独立に再現した**ことを意味する。

原因は「候補順序どうしの目的関数の差」と「割引が作れる差」のスケール差である:

| W | 割引係数が作れる相対差 | base目的関数の相対スプレッド(中央値) |
|---|---|---|
| 0.25 | 9.9〜13.2% | **31.2%** |
| 0.5 | 22.8〜36.0% | 31.2% |
| 1.0 | 64.8〜100% | 31.2% |

W=0.25 では割引の効き(約10%)が候補間の差(約31%)の1/3しかなく、順位を覆せない。
覆せるところまで W を上げると、今度は割引が支配的になって崖に入る。

### 5.3 構造的な原因: 到達可能性と充填は直接対立する

再ランクが起きたとき、選ばれる順序は**例外なく配置個数が少ない**方だった:

| シーン | W=0 の勝者 | 再ランク後の勝者 |
|---|---|---|
| A02 | placed=**21**, blocked_ratio=0.697 | placed=**4**, blocked_ratio=0.458 |
| A03 | placed=**26**, blocked_ratio=1.000 | placed=**10**, blocked_ratio=0.871 |
| A04 | placed=**28**, blocked_ratio=0.813 | placed=**19**, blocked_ratio=0.406 |

荷物を1個置くたびに通路を塞ぐ可能性が生まれるので、**「通路を開けておく」と
「たくさん詰める」は原理的に競合する**。分母を `empty` ではなく `supported` にして
退化を避ける設計にした(§1.3)にもかかわらず、この偏りは残った。

`supported` 正規化は「置かない順序ほど有利」という**最悪の退化**(Phase18 の A07 が
fill 0.00 になった型)は防いだ —— 実際、本フェーズでは placement=100 を保ち、
fill が 0 に崩壊したシーンは1つも無い。しかし「やや置かない方が有利」という
**弱い偏り**までは消せなかった。

### 5.4 唯一動いた A03 の +9.10 も質が良くない

| | before | after (W=0.25) |
|---|---|---|
| fill_strict | 17.78 | 26.88 |
| fill_loose | 30.45 | 50.63 |
| **loose−strict ギャップ** | 12.67 | **23.75** |
| 配置個数 | 19/40 | **10/40** |

配置個数が半減し、loose−strict ギャップがほぼ倍に開いている。これは Phase26 の壁積みが
fill_strict を落としたときと**同じ signature**(体積は詰め込めているが境界すれすれに寄り、
厳マージンでの計上が不安定になっている)である。仮にこの +9.10 が実物だとしても、
**1シーンの単発効果**であることに変わりはない。

## 7. 採否の判断

**不採用。** `MYSOLVER_REACH_WEIGHT` の既定を **0.0(無効)** のまま維持する。

根拠:

1. 26シーン fill_strict **+0.350、t=+1.000**。基準 `t>2` に届かない。
2. 動いたのが **26シーン中1シーンのみ**で、単一シーン効果は t が 1.000 に恒等的に
   固定されるため、**原理的に基準を通過できない**(§5.1)。
3. **重み区間が存在しない**: 再ランク閾値が 0.23〜2.29 と10倍に散らばる一方、
   最小閾値のシーン(A03)は W=1.0 で既に崖から落ちている。広く効かせる W と
   どのシーンも壊さない W の共通区間が無い(§5.2)。Phase18 と同型の結論。
4. 唯一の改善シーンも配置個数半減・loose−strict ギャップ倍増という Phase26 と同じ
   signature で、質が良くない(§5.4)。
5. コストは +9.9%(実測)かかっており、効果が無い以上は純損失である。

ローカルで有意な改善が出ていないため、**public提出による最終判定は行わない**
(評価基準5、Phase23 の教訓)。

### コードの扱い

`reach.py` / `REACH_WEIGHT` / `REACH_UNIT_COST` は**既定無効のまま残す**。
`USE_SETTLED_SLACK`(Phase20)・`CORRIDOR_DB_MODE`(Phase24)・`WALL_MODE`(Phase26)と
同じ扱いで、「なぜ効かなかったか」を定数のコメントに記録することを優先する。
`reach.py` は Phase24 の監査ロジックを**エージェント側から呼べる形にした資産**でもあり、
今後「行き詰まり時点の到達可能性」を測りたい場面で再利用できる。

## 8. 次フェーズへの示唆

- **corridor_penalty の myopia を外す方向は、これで2通り試して両方閉じた。**
  Phase24(不感帯の帯域別化 = 候補側の精度向上)は +0.27 で不採用、本フェーズ
  (順序探索側で事後評価)は 1/26 シーンしか動かず不採用。Phase24 が挙げた具体案2
  「ビームサーチのスコアに同じ項を入れる」は、**同じ重み区間問題に必ずぶつかる**
  (§5.2 の閾値のばらつきは項の性質であって、入れる場所の問題ではない)ため、
  そのまま試すことは推奨しない。

- **「単一の大域重みで代理関数を較正する」路線は、これで3敗目である。**
  Phase18(stability 幾何代理)、Phase26(壁積みの厚み ≒ 構造パラメータ)、
  本フェーズ(到達可能性)。いずれも「シーンごとに崖・閾値の位置が違う」ことが原因で、
  **単一のスカラー重みでは較正できない**という同じ壁に当たっている。
  次に代理関数へ項を足す設計を検討する場合は、**大域重みではなくシーンごとに
  自己調整される形**(例: 候補間の目的関数スプレッドで正規化した相対割引)にしない限り、
  同じ結果になる可能性が高い。

- **候補順序の多様性そのものが不足している可能性**: §5.2 で分かったのは
  「build_order が比較している候補は6〜7件しかなく、その目的関数の相対スプレッドは
  約31%」ということである。項を足して**並べ替える**余地は、この6〜7件の中にしかない。
  再ランクで取れる上限そのものが小さいので、**候補集合を良くする**方向
  (リスタート配分 `CONSTRUCT_SLICE` の見直し等)のほうが期待値が高いかもしれない。
  ただし Phase25b で探索予算は飽和しているため、「増やす」のではなく
  「同じ予算での多様性を上げる」設計になる。

- **未解決のまま残る量**: 空きの38.8%(fill換算13.14pt)を占める搬入経路の封鎖。
  本フェーズはこれを**取りに行く方法**を1つ潰したが、量そのものは依然として最大の空き要因である。
