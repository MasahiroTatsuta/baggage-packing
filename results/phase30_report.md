## 1. 計測1: sup=0(13シーン)の内訳 —— (A)幾何 vs (B)支持

### 1.1 方法

Phase29 §5.1 の「支持付きで収まる位置がゼロ」判定(`reach._fit_positions` の `ok_sup`)は、
幾何fit(`ok`)と支持判定(footprint 下の occupied 比率 ≥ 0.55)を **合わせて** ゼロかどうかしか
見ていない。本計測は同じ判定式から支持フィルタだけを外し(`ok` の段階で数える
`raw_fit_count`、`agents/mysolver/reach.py` は無改変)、行き詰まり時点の X について

- `fit_nosupport`: 支持を無視した「箱がそのまま入る」位置数(全 orientation 合算)
- `fit_support`(=旧 `sup`): そのうち支持もある位置数

を voxel 0.05 と 0.025 の両方で数える。分類:

- **(A) 幾何で入らない**: `fit_nosupport == 0`(支持を無視しても位置が無い)
- **(B) 支持が無い**: `fit_nosupport > 0` かつ `fit_support == 0`(入る場所はあるが、
  その全てで下の凹凸のせいで支持率55%を満たせない)

### 1.3 A04 は「sup=0」ではなく境界例だった

Phase29 §4.1 は A04 を13シーンの内側に含めつつ「+A04 は棚のみ」と注記していたが、
実際には `fit_sup`(支持ありの位置)は voxel 0.05 で **1**、0.025 で **6** と**ゼロではない**。
その少数の支持あり位置は voxel 0.05 では全て棚に当たり(計測2の分類は iv)、
voxel 0.025 まで細かくすると一部が既配置荷物のみに塞がれる位置に変わる(分類は iii)。
「(A)/(B) の12シーン」には数えず、計測2側の(iii)/(iv)判定に委ねる(§2 表を参照)。

### 1.4 読み方

**(A) が シーン数・体積の両方で明確に支配的。** (A) のシーンでは、X のサイズの空間が
その時点までに他の荷物で使い切られている ―― 搬入経路の問題ではなく、
**「その時点までにどれだけの容積をどう配分したか」の問題**である。順序修正で通路を
開けても意味がない(Phase29 §5.1 の結論を追認)。一方 (B) の2シーンは、
空間の総量はあっても skyline が凸凹で支持率55%を満たす平らな床が無い、という
別種の問題(配置ポリシー側)である。

## 2. 計測2: 行き詰まり原因の5分類(i)〜(v) —— Phase22/24 の m³ 分解の置き換え

### 2.1 方法

optimize有効21シーンそれぞれについて、`tools/phase29_cand.py` が記録した採用順序
(build_order の実際の選択則を再現)を影シミュレータで1回再生し、行き詰まり時点の
プール(lookahead窓、既定1個・C01/C02/C03/P05のみ5個)の各荷物を次の基準で分類する:

```
fit_nosupport == 0                          -> (i)   幾何で入らない
fit_nosupport > 0 かつ fit_support == 0      -> (ii)  収まるが支持が無い
fit_support > 0 かつ:
    open(支持あり・棚も荷物も塞いでいない位置) > 0  -> (v)   置ける(別の理由)
    既配置荷物のみが塞ぐ位置がある            -> (iii) 既配置荷物が搬入経路を塞ぐ
    棚が塞ぐ位置しかない                      -> (iv)  棚が塞ぐ(順序では動かせない)
```
プールが複数件のときはシーンを「最も見込みがある」区分で代表させる
(優先順位 iii > iv > v > ii > i。iii を最優先するのは、Phase29 の衝突駆動リスタートが
実際にこの区分を対象にしていたため、既存の到達可能性と直接比較できるようにする)。
voxel は 0.025(見落としを避けるため最も細かい側)。「残体積」はその時点で未配置の
全荷物の体積合計(L×W×H)。

## 3. 計測3: 候補順序の cog×fill パレート分析

### 3.1 方法

`tools/phase29_cand.py` が記録した21シーン・130候補すべての `order` を
`tools/phase29_order_eval.py::run_with_order`(本物の env + `Evaluator` + `Scorer`、
`optimize` は呼ばない)に流し、実際の `fill_strict` / `cog_score` /
`placement_score` / `soft_item_score` を得た。新規探索は無し(記録済み順序の再生のみ)。
「現在の勝者」は `tools/phase29_blockers.py::winner_order` と同じ選択則
(shadow の risk_vol・違反率による辞書式比較)で決めた候補。

**パレート優越の定義**: 勝者以外の候補 c について、
`fill_strict(c) >= fill_strict(winner) - 1e-9` かつ `cog_score(c) > cog_score(winner)`
かつ `placement_score(c) == 100` かつ `soft_item_score(c) == 100`(制約を落とす候補は除外)。
あわせて **ε制約方策**(fill_strict ≥ 勝者のfill_strict を満たす候補の中で cog_score を
最大化)を全21シーンで評価した。

- 7シーン中 **4シーン**(A03, A05, A06, A08, D03, D04)で ε方策の Δfill も **正**
  (最大 A08 の +3.41pt)。つまり cog だけでなく fill 側でも、現在の勝者(shadow risk_vol
  基準で選ばれた候補)より優れた候補が候補プール内に既に存在していたケースがある。

### 3.3 D05: 勝者がプール内の別候補に "全指標で" 劣っていた例

D05 の勝者(heuristic順、c0)は12個しか配置できていないが、同じ候補プール内の
window探索候補(c4, phase1_window)は23個配置し、fill_strict(25.31→25.71)・
cog_score(50.74→**69.02**)ともに勝者を上回る(placement/soft は両方とも100)。
影シミュレータの risk_vol による選択がこのケースで real 評価と食い違っていたことを、
**実測 fill_strict・cog_score の両方で** 確認した(Phase20 が Spearman 0.71 と
報告した代理誤差の、個別シーンでの具体例)。

### 3.4 読み方

**cog は「fillとのトレード」ではなく、既存の候補プールの中に無料で拾える分がある
ケースが実在する(7/21シーン)。** ただしこれは**事後**(本物の評価器)で分かった
headway であり、build_order の実行時に使える形にはまだなっていない —— 影シミュレータ
(`simulate.simulate_order`)は現在 cog に関係する量を一切計算していないため、
「fillを落とさない候補の中で cog 最大」を**オンラインで**選ぶには、影シミュレータ側に
安価な cog 代理指標を追加し、その代理が本物の cog_score の順位をどれだけ保つかを
別途検証する必要がある(本フェーズでは未測定。Phase15 の「重み付き和で cog に
傾斜させると net −0.64」という結論はこの ε制約方式には適用されない――全く別の選択則
であることに注意)。

## 4. 判定: (A) 幾何で入らない(i)が支配的

### 4.1 根拠

- 計測2で、21シーン中 (i) が **シーン数48%・残体積54.8%** と両基準で最大区分。
- 計測1で、その (i) の中身が voxel 0.05/0.025 で揺るがない、**本物の**幾何的容量不足
  (支持を無視しても位置が無い)であることを確認した。搬入経路の問題ではない。
- 次点の (iii)(30.4%)は Phase29 が実装・実測済みで、到達2/26シーン・6シーン中4シーンで
  全手悪化という形で**不採用が確定している**。「(iii)の量が大きい」という情報は
  Phase29 の結論を覆さない。

### 4.2 (B)/(C)/(D) を採らない理由

- **(B) 支持が無い(ii)**: 2/21シーン(10%)のみで、(i)の1/5の規模。優先度は低い。
- **(C) (iii)が支配的**: シーン数・体積とも(i)に次ぐ2位であり「支配的」ではない。
  かつ Phase29 が実測して否定した経路そのもの。
- **(D) 割れて支配的要因が無い**: (i)が48%/54.8%と他の区分を上回っており、
  「割れている」と呼ぶには偏りが明確すぎる。

### 4.3 したがって **(A)** を宣言する。Phase31候補は **ALNS**。

## 5. Phase31 への示唆

### 5.1 本命: ALNS(破壊→再構築)

(i)(容積配分の失敗、10シーン)と(iii)(通路封鎖、6シーン、Phase29実装済み)は、
どちらも「特定の1手を動かす」のではなく「**局所的にまとまった範囲を壊して積み直す**」
オペレータでないと届かない可能性が高い。Phase29 §5.2 が (iii) の6シーン中4シーンで
「X を前に出すと層構造ごと壊れる」と報告しているのは、まさに1手移動の破壊半径が
小さすぎたことの兆候である。ALNS の worst/Shaw removal + greedy/regret insertion は、
除去する範囲を明示的に選べるため、この「小さい破壊で大きい層崩れが起きる」問題を
正面から扱える。

- (i) 側への適用: 行き詰まり時点で「X の居場所を奪っている」領域を同定し
  (本フェーズの `raw_fit_count` は「入るか否か」のみで占有者の identity を持たないため、
  これは Phase29 の `reach.item_blockers` を「掃引経路の障害物」から「Xが入れたはずの
  空間の占有者」へ拡張する必要がある――Phase29 §6.3 が既に示唆していた方向)、
  そこを含む一部区間を除去して再構築する。
- (iii) 側への適用: 既存の `reach.item_blockers`(再利用可能、Phase29が実装済み)を
  除去範囲の同定にそのまま使える。

### 5.2 次点: ε制約 cog(計測3の追試として)

計測3で「無料の cog」が7/21シーンに実在することを事後確認した。次フェーズで着手する
なら、まず影シミュレータに安価な cog 代理(例: 配置済み荷物の質量加重重心オフセット)を
追加し、その代理順位が本物の cog_score の順位をどれだけ保持するか(Spearman)を測ってから、
「fill_strict の代理値を落とさない候補の中で cog 代理を最大化」で選び直す効果を測る。
ALNS より実装コストは小さいが、**7/21シーンにしか効かない**(規模は(A)対応より小さい)。

### 5.3 保留: skyline平坦性・棚対応

(ii)(2/21)・(iv)(1/21、順序では原理的に不可)は規模が小さく、本フェーズでは優先しない。
ただし Extreme Point/EMS ベースの増分再構築を Phase31 で採るなら、その副産物として
skyline平坦性(研究報告 §9.1.3)も自然に改善しうる。単独の大域重みとしては追加しない
(Phase18/26/28 で3敗した経路)。

### 5.4 P05 の reach/planner 不一致(§2.4)

原因調査は本フェーズの範囲外。次に (iii) や (i) 向けの機構([[reach.item_blockers]] の
拡張)を実装する際、この不一致が同じ機構の別シーンでも起きていないか
(=同定した「占有者」を除去しても実際には置けない、という誤検出)を測る形で
副次的に検証するのが効率的。
