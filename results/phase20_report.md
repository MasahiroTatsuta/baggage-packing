## 1. 背景と測定設計

### 1.1 なぜ今これを測るのか

探索側の改善が3フェーズ連続で fill を動かしていない。

| フェーズ | 変更 | 26シーン fill_strict の変化 |
|---|---|---|
| Phase16 | optimize予算 30s→120s(4倍) | +1.15 |
| Phase17 | 決定性リファクタ(std 5.25→0.0000) | −0.14 |
| Phase19 | 候補生成の高速化(plan()時間 −29%) | −0.63 |

探索は速く・決定的で・予算単調になった。それでも結果が伸びないなら、
**最適化している目的関数そのものが実評価とずれている**というのが最も自然な説明である。
そして Phase17 で決定性が確保されたため、この「代理誤差」は**初めて乱数に埋もれずに
厳密に測れる**状態になっていた。

### 1.2 測定の設計(`tools/phase20_surrogate.py`)

`ordering.build_order` は候補順序ごとに `simulate.simulate_order` を呼び、
その戻り値から目的関数

```
objective = risk調整済み体積 − PLACEMENT_PENALTY_WEIGHT × 総容積 × placement違反率
```

を作って argmax を選ぶ。つまり build_order が実際に使っているのは**候補間の順位だけ**である。
したがって代理誤差の本質は Spearman 順位相関であり、絶対値のずれ(系統バイアス)は
全候補に共通なら順位を変えないので二次的——この区別が本フェーズの結論そのものになった。

3段構成:

1. **collect**: `simulate_order` を非侵襲にフックし、build_order が評価した全候補順序と
   予測値を記録する(戻り値も副作用も変えないので探索の軌跡は無改造時と完全に同一)。
2. **groundtruth**: 記録した各順序を `env.set_item_order` で実エピソードに固定順序として
   流し込み、真の fill_strict / fill_loose / 配置個数 / fill計上率を測る。
3. **analyze**: Spearman / Pearson、系統バイアス、**regret**(argmax(予測)を選んだことで
   失った実fill)、および誤差の (A)/(B) 分解。

**候補数の確保**: 既定予算120sでは build_order はフェーズ1の 4〜6 本しか回らず、N=5 で
Spearman を測ると推定量の分散が大きすぎる。そこで**フェーズ2と同じレシピ**(ランダム
window・ランダム戦略シード・score_noise・shuffle_ties)で追加候補を生成し、1シーンあたり
14〜16候補まで増やした。無関係なランダム置換を混ぜると「明らかに悪い順序を下位に置ける
だけ」で相関が過大評価されるため、候補は必ず**貪欲構築器が生成したもの**(=実際に競合
しうる、同程度の品質の順序)だけにした。native のみに限った相関・regret も併記する。

**打ち切りとの交絡の除去**: build_order 本来の検証枠(`MAX_VALIDATE_SLICE`=12s)は途中
打ち切られうる。打ち切られた予測は「置けるはずの残りを評価していない」ので系統的に過小に
なり、代理誤差と予算不足が交絡する。そこで全候補を**同一の潤沢な予算(60s相当)で評価し
直した**。実測では **125候補すべてで打ち切りは一度も発生しなかった**(trunc=0)ので、
この交絡は最初から存在しなかったことも確認できた。

### 1.3 実装中に潰した2つの計測バグ(いずれも偽の「代理誤差」を作る)

1. **既積み荷物の混入**: 影シミュレータが予測するのは「このエピソードで新たに置いた荷物」
   だけだが、`env.container_manager.packed_items` は既積みを含む。揃えずに比べると
   prepacked シーンで予測が一律に過小に見える。実際、最初の smoke test では
   「予測3個 / 実測13個」という壊滅的な誤差に見えたが、既積み10個を除くと
   **予測3個 / 実測3個(完全一致)** だった。`prepacked_index_list` を collect 側で保存し
   groundtruth 側で除外する形に修正した。
2. `Evaluator.calculate_fill_rate` は `list[Item]` を返す(index の列ではない)。

### 1.4 先に潰した2つの対立仮説(いずれも棄却)

| 仮説 | 検証 | 結果 |
|---|---|---|
| 影シミュレータの**1手あたり予算**(0.7s)が実 policy(5.5s)より8倍小さく、置けるはずの手を「置けない」と誤判定している | P02 の4候補で per_step を 0.7 / 2.0 / 5.5 に振って再実行 | **棄却**。3水準とも予測は完全に同一(n=3/17/16/13) |
| 影シミュレータは荷物を**目標点**(支持面から16mm浮いた位置)に記録し沈降させないため、積み上げるほど架空の高さが積算し行き詰まりを早める | `_place` の z を REST_CLEARANCE 下げて再実行 | **棄却**。予測はむしろ悪化(17→14 個など) |

さらに、heuristic order の1件について影シミュレータと実エピソードの**行動列を1手ずつ
突き合わせた**ところ、`s00〜s02` と `r00〜r02` が(z の16mm差を除き)完全に一致し、
両者とも同じ手で行き詰まっていた。**配置の軌跡そのものは高精度で再現できている**ことが
確認でき、誤差が (B) 計上予測に集中しているという後述の結論と整合する。

## 3. 【本フェーズ最大の知見】較正誤差と弁別誤差の分離

ターゲット2(§4)の結果を理解するうえで決定的だったのが、次の分解である。

代理誤差は2つの成分に分けられる。

* **較正誤差(calibration)**: シーンごとに、全候補へ共通にかかる一定の「下駄」。
* **弁別誤差(discrimination)**: 同一シーン内で、候補ごとに異なるばらつき。

`build_order` は同一シーン内の**順位**しか使わないので、
**較正誤差は定義上どんな決定も変えられない。順位を変えるのは弁別誤差だけである。**

計上割合の予測誤差について、シーン内の平均(=較正誤差)と標準偏差(=弁別誤差)を測った:

| | 較正誤差(シーン内平均) | 弁別誤差(シーン内std) |
|---|---|---|
| A: 目標点slack (Phase19まで) | **+0.141** | 0.075 |
| B: 沈降後slack (Phase20の修正) | **−0.049** | **0.075** |

**沈降後slackは較正誤差を65%削ったが、弁別誤差は 0.075 → 0.075 と小数第3位まで不変だった。**
これが「較正は劇的に良くなったのに順位相関が1ミリも改善しなかった」ことの完全な説明である。

**この結論は今回の実装に固有ではない。** `geo.fill_risk_factor` の定数(`SAFE_SLACK`)や
割引の形状をどう変えても、それは「どの姿勢・どのスケールで測るか」を変えるだけで、
主に較正誤差を動かす。**代理関数の再較正という方向自体が、原理的に意思決定を改善しない。**

## 4. ターゲット2:沈降後slackによる体積推定の精度向上(実装・検証・不採用)

### 4.1 何を直したか(新しいダイヤルを増やさない)

`risk_adjusted_volume` は `item_volume × geo.fill_risk_factor(info['slack'])` で
「その荷物が実際に fill に計上される期待値」を見積もる。しかし `info['slack']` は
**目標点**(支持面から `REST_CLEARANCE`=16mm 浮かせた点)の内包 slack である。
配置後の物理演算(`settle_wait_step=300`)で荷物は必ず支持面まで落ちるため、
本家 evaluator が8角点を判定するのは**沈降後の姿勢**であって目標点ではない。

床直置きの荷物の場合:

| | 床面の dot | `fill_risk_factor` |
|---|---|---|
| 目標点(現行) | −0.016 | **0.55**(55%計上されると予測) |
| 沈降後(修正後) | 0.000 | **0.00**(計上されないと予測) |

Phase11 の実測では床直置きは strict で必ず計上から漏れる。つまり現行は床置きを
**体積の55%分だけ過大評価**していた。これは重みの調整ではなく**評価する姿勢の誤り**であり、
修正しても調整パラメータは1つも増えない(本フェーズの設計原則を満たす)。

### 4.2 影響範囲を offline 目的関数だけに限定した(Phase11 の撤回時との違い)

`fe7c776` で撤回された実装は `_score()`(online の候補選択)にも同じ slack を使わせており、
online の挙動まで変えていた。本フェーズは **`_score()` を一切変更せず**、
`info['settled_slack']` を別キーとして追加して `simulate.simulate_order` だけがそれを使う形にした。
これにより変更は数学的に「`ordering.build_order` の目的関数」だけに限定される。

**検証(online不変の証明)**: `tools/phase17_dump.py` で optimize無効の5シーンの digest を比較。

| suite_B03_2c_80_prio | `4fb88042d6452548` | 一致 |

### 4.3 主KPI(順位相関)の再評価 — **改善しなかった**

真値(実エピソード)は候補順序だけで決まり目的関数の定義には依存しないため、

**較正は大幅に良くなったが、順位は改善しなかった**(理由は §3)。

## 6. 結論と次フェーズへの申し送り

### 6.1 本フェーズで確定したこと

1. **代理誤差は実在し、無視できない大きさである。** 順位相関 0.710(native)、
   実fillスプレッド 19.19pt に対し regret 1.14pt。
2. **その系統バイアスはほぼ全量が「計上予測」に由来する**(+4.30pt / +4.02pt)。
3. **しかし系統バイアスを直しても意思決定は改善しない。** 代理誤差は較正誤差と弁別誤差に
   分解でき、`build_order` が使う順位を変えるのは弁別誤差だけ。沈降後slackは較正誤差を
   65%削ったが弁別誤差は不変(0.075→0.075)だった。
4. したがって **「代理関数をより正確にする」方向では解けない。** これは指示にあった
   判定分岐「相関自体を改善できない場合は代理関数の改良では解けないと結論する」に該当する。

### 6.2 次フェーズの推奨:trust region + ρ-test

Phase18(単一大域重みでの stability 代理)に続き、本フェーズ(代理関数の較正改善)も
**「代理を正確にしてから信じる」という戦略の失敗**である。2フェーズ分の証拠が揃った以上、
次は**代理を信じずに真の評価で候補を gating する**設計へ移るべきである。

設計上の要点(本フェーズの知見を踏まえて):

* **狙うべきは弁別誤差であって較正誤差ではない。** 全候補に共通の下駄を直す施策は
  今後も一切効かない。「この候補**だけ**が予測より悪い」を検出する仕組みが要る。
* **regret が少数シーンに極端に集中している**(A05 が 8.45、他7シーンは 0.00〜0.69)ことは
  ρ-test にとって有利な性質である。全候補を等しく疑う必要はなく、
  **「代理を信じすぎている少数の候補」だけを弾けばよい**。
* 真値に近い gating 信号として何を使うかが設計の中心になる。本フェーズの計測基盤
  (`tools/phase20_surrogate.py`)は、任意の候補集合について
  「予測 vs 真値」を物理エピソードごと測れるので、ρ の定義を実データで較正するのに
  そのまま使える。
* **`suite_A05_2c_80_prio` が最良の単一デバッグ対象である。** native regret 8.45 と突出し、
  Phase17 以降は決定的なので再現も容易。

### 6.3 未解決のまま持ち越す項目

1. `gen_2containers_priority` の stability 制約違反(96.87 < 97)。Phase17 から未解決。
   本フェーズの計測では、このシーンの native Spearman は 0.700 と悪くない一方
   regret 0.69 が残っており、代理誤差だけが原因ではない可能性がある。
2. Phase19 からの申し送り「高速化で得た余力を fill 改善へ変換する探索構造の見直し」。
   本フェーズの §2.3(実fillスプレッド 19.19pt)は、その余地が実在することを裏づけている。
