# Phase54 報告: sudden deathの直接原因を特定 — 単一の決定論的バグ(30/30件が同一原因)

## 結論(先出し)

**sudden deathの原因は、規模でも本番固有の乖離でもなく、`agents/mysolver/agent.py`の
policyフォールバック1箇所にある単一の決定論的バグである。** 測定した30シーン
(26シーン+scalestress3+sample_config2)のうち、**sudden deathが発生した30件全てが
同一のシグネチャ**(`cause=is_included`、`item_idx_in_pool=0`、境界はみ出し量=
**厳密に5.000mm(標準偏差6.4e-9m)**)で終了した。これは統計的な傾向ではなく、
**数式レベルで証明できる恒等式**である(後述)。この段階ではplanner/scorer.pyは
変更していない(指示どおり報告のみ)。

「あと1手」を回避する実測価値は平均+0.14pt/シーン(public composite換算)にとどまるが、
これは**バグを1回だけ回避して即座に同じ壊れたフォールバックに再び当たった場合**の
下限値であり、根本原因(たった数行のz座標計算式)を修正すればsudden death自体が
**構造的に消滅する可能性が高い**——これは今回の調査全体(Phase41〜54)で唯一、
**原因が100%決定論的に特定でき、修正が自明な**レバーである。

## ステップ1: 死因の分類

### (1-1)(1-2) 死因の集計(26シーン+scalestress3+sample_config2、計31シーン中30件でsudden death発生)

`tools/diagnose_sudden_death.py`(新規、読み取り専用)でpolicyループを自前実行し、
終了直前のaction(item_idx・place_pos・orientation)と、`validator.py::check_inclusion`の
判定式(6/7面の平面判定`dots`)をそのまま複製して記録した。

| 項目 | 結果 |
|---|---|
| sudden death発生 | **30/31シーン**(唯一の例外: `suite_A06_1c_40_small`、全40個完走) |
| 死因(`cause`) | **`is_included`が30/30(100%)**——`is_valid`・`is_placed_safe`は一度も観測されず |
| 死を招いたアイテムのpool内位置(`item_idx_in_pool`) | **0が30/30(100%)** |
| 境界はみ出し量(`overshoot.max_excess`) | **平均0.0050000006m、標準偏差6.4e-9m**
(最小0.004999986m〜最大0.005000014m——浮動小数点誤差の範囲でしかない) |
| 死因アイテムの属性 | is_soft=4/30(13%)、is_prioritized=3/30(10%)——プール内基準比率
(15〜20%/8〜30%)からの乖離なし。**アイテムの属性自体は死因と無関係** |
| n_placed_at_death(何手目で終了したか) | 最小12〜最大45、平均22.6(シーンごとに大きく異なる) |

**「はみ出し量の分布」は事実上分布ではなく単一の定数(5.000mm)だった。** 指示(1-2)の
判定基準に照らせば明確に「数mmのわずかなはみ出しが大半」の側であり、しかも
**わずかどころか、全件が寸分違わず同じ値**——これは`planner`の配置判断が
シーンごとに微妙に境界を誤るという話ではなく、**特定の1コード経路が呼ばれるたびに
必ず同じ量だけはみ出す、という構造的な現象**であることを意味する。

### 根拠: なぜ全件が寸分違わず5.000mmになるのか(数式で証明できる)

`agents/mysolver/agent.py::policy()`は、`planner.plan()`が合法手を1つも見つけられず
`None`を返した場合(コード中のコメントによれば「密グリッドでの最終リトライまで
内部で行った上で本当にどこにも置けない場合」)、以下の**フォールバック行動**を返す:

```python
z = thickness + item.get('height', 0.2) / 2.0
action = {'item_idx': 0, 'container_idx': container.get('index', 0),
          'place_pos': np.array([0.0, 0.0, z], dtype=np.float32), 'orientation': 0}
```

一方 `validator.py::check_inclusion` の床面判定は
`dots[floor] = n_vec_floor·(target_pos-point_floor) + |n_vec_floor|·half_lwh`で、
床面の法線`n_vec_floor=(0,0,-1)`・床面上の点のz座標`=thickness`とすると:

```
dots[floor] = -1·((thickness + h/2) - thickness) + 1·(h/2) = -h/2 + h/2 = 0
```

**アイテムの高さ`h`によらず、このフォールバックの床面判定は厳密に0になる
(恒等式)。** そして本プロジェクトの検証済みシーン設定(`configs/gen/suite_*.json`
26シーン全件・`configs/sample_config.json`両タスク・`scalestress_*`3シーン、
確認した全シーンで共通)は`validator.inclusion_margin = -0.005`(**負のマージン**、
「境界に触れるだけでは足りず、最低5mmのクリアランスを要求する」設定)——
`dots<=margin`つまり`0<=-0.005`は常に偽となり、**超過量は`0-(-0.005)=+0.005m`で
確定する。アイテムの寸法・シーン構成に一切依存しない、フォールバック式と
マージン設定の組み合わせだけで生じる純粋な計算上の帰結である。**

「マージン設計で救える可能性がある」(指示1-2)に完全に該当する——**フォールバックの
z座標に数mmの余裕を追加するだけで、この特定の失敗経路は原理的に解消する。**

### (1-3) 終了直前のパターン

終了直前の数手を確認したところ、**直前まではplace_pos_localが多様な値
(通常の探索結果)であり、死んだ瞬間だけ`place_pos_local=[0.0, 0.0, z]`という
identical patternに切り替わる**、という鋭い不連続が全件で見られた
(例: `suite_C02_2c_55_shelfprio` — 33〜36手目は
`[-0.659,-0.172,1.337]`/`[0.530,-0.580,0.294]`等の正常値、37手目(死亡)で
唯一`[0.0, 0.0, 0.287]`)。**姿勢・コンテナ位置・アイテム形状に偏りは無く、
唯一の共通点は「フォールバック発火の瞬間の座標パターン」そのもの。**
段階的な劣化ではなく、`planner.plan()`が`None`を返した瞬間の一発死である。

## ステップ2: 「あと1手」の価値を定量する

### (2-1)(2-2) 実測: 死因アイテムをitem_stream.item_listから除去して再実行

`tools/measure_skip_death_item.py`(新規、読み取り専用・configファイルは書き換えない)で、
sudden deathが発生した25シーン(A06を除く)について、死因アイテム1個だけを
メモリ上で除去し、`agent.optimize()`→policyループ→`Scorer`の5成分を再測定した。

| 集計(n=25シーン) | 平均 | 最小 | 最大 | 負値の件数 |
|---|---:|---:|---:|---:|
| 継続手数の差(Δn_placed) | +2.52 | −6 | +12 | 6/25 |
| Δfill_score | +0.96 | −17.58 | +12.13 | 7/25 |
| Δcog_score | −0.41 | −8.26 | +11.64 | 12/25 |
| Δstability_score | −0.05 | −1.69 | +0.85 | 12/25 |
| Δplacement_score | −0.24 | −5.88 | 0.00 | 1/25(D03のみ) |
| Δsoft_item_score | 0.00 | 0.00 | 0.00 | 0/25 |

**重要な注意点**: 「該当アイテムを除いた順序で再生する」を、本ツールは
**除去後のプールに対して`agent.optimize()`を再実行する**形で実装した(「同じ順序から
1件だけ抜く」ではなく、除去後のプールに対する**新しい最適順序**を求め直している)。
そのため結果には**再最適化そのもののノイズ**が乗る——実際、6/25シーンで
継続手数がむしろ**減少**し(最悪`suite_D03`で−6)、`suite_A07_1c_40_bulky`では
fillが−17.58ptと大きく悪化した。これは「1個消しても別の1個が新たに壁を作った」
というより、除去後の再最適化が偶然元より不利な順序を選んだ結果と考えられる。
一方`suite_D03_A_2c_60_prioheavy_cont`では**除去後にplacement_scoreが94.12まで低下**
(今回の全調査で初めて100を下回った実測例)——除去に伴う再最適化が別の積み重なりを
誘発した可能性があり、**「1個消せば必ず良くなる」わけではない**ことを裏付ける。

### (2-3) public composite換算

`(2·fill + 1.5·cog + 1.5·stability + 1·placement + 1·soft) / 7` で
シーンごとのcomposite_strictを算出し、`phase40_baseline_off_mac.json`との差分を取った:

| 集計(n=25) | 値 |
|---|---:|
| Δcomposite 平均 | **+0.1449pt/シーン** |
| Δcomposite 最小/最大 | −2.35 〜 +2.06 |
| 負値のシーン数 | 9/25(36%) |

**「あと1手」1回分の実測価値は平均+0.14ptと小さく、ばらつきも大きい
(3分の1超のシーンでむしろ悪化)。** ただしこれは**根本原因を直したときの価値の
下限値**にすぎないことを次節で説明する。

## この2つから: sudden death回避に投資する価値があるかの見立て

**投資する価値は極めて高いと判断する。** 理由は2つの発見を組み合わせたところにある:

1. **ステップ1で明らかになった原因は、統計的傾向ではなく100%決定論的な単一バグ**
   ——観測した30件のsudden death全てが寸分違わず同じ数式的帰結(はみ出し量
   5.000mm、標準偏差6.4e-9m)であり、`agent.py`のフォールバックのz座標計算に
   数mmのクリアランスを追加するだけで**原理的に解消するはずの**現象である。
2. **ステップ2の測定値(+0.14pt/シーン)は「1回だけ回避して即座に同じ壊れた
   フォールバックに再び当たった」場合の値であり、根本修正の価値を大幅に
   過小評価している。** 実際、このバグが**現在観測されている sudden death の
   唯一の原因(100%)**である以上、フォールバック自体を直せば、1シーンにつき
   1回だけでなく、**エピソード全体を通じて何度でもこの経路の発火を回避できる**
   可能性が高い——これは既存の進捗まとめが言う「5成分すべてがsudden deathまでに
   何個置けたかの下流である」という構造そのものに直接効く。

**他の保留レバーとの比較**:

| レバー | 実測/試算された上限 | 原因の特定度 | 修正の見通し |
|---|---:|---|---|
| **sudden death fix(本フェーズ)** | 未確定(下限+0.14/シーン、根本修正なら大幅に上振れ見込み) | **100%決定論的(全件同一原因)** | **自明(z座標に数mmのクリアランス追加)** |
| ρ-test原因究明 | +0.48(完全に機能した場合) | 未特定(本番で機能しない理由が不明) | 診断ビルドが必要、保留中 |
| placement/soft_item | +13.61(合計、完全に機能した場合) | ローカルで一度も再現せず(Phase44-47) | 見通し立たず |
| stability | +0.39(実質それ未満) | 物理エンジンの沈静化残差(Phase52) | 見通し立たず |
| シーン規模 | — | 仮説棄却(Phase53) | 該当なし |

**sudden death修正は、今回の調査全体で唯一「原因が100%特定でき、かつ修正が
自明」なレバーである。** 次フェーズでは、この1点(`agent.py`のフォールバックの
z座標計算)に絞った修正の実装・検証を最優先で行うことを推奨する。
