## タスク1: フォールバック経路

### 1.1 実装した4つの防御

**(a) import を致命傷にしない** —— 最も危険だった箇所

`replica.py` は `src.ground_handling`(本物の env 実装)を引く。素朴に
`from . import replica` と書くと、提出先の環境構成が想定と違った場合に
**`ordering.py` 自体が import できず、エージェントが丸ごと起動しない**(=全シーン全損)。
Phase35 の実装はこの形だった。`try/except` で握って `None` に落とすよう修正し、
複製評価器を使わないだけで Phase34 相当の挙動へ自動的に落ちるようにした。

**(b) preflight —— 取り置きを決める前に使えるかを確定させる**

run2 の設計は「取り置き45秒を**壁時計から**先に引いてから構築する」ため、
失敗がいつ判明するかで到達できる状態が変わる。import 失敗・pybullet 初期化失敗で
取り置きだけ残ると「複製評価をしないのに構築の締切だけ45秒早い」という**一番損な状態**になる。
そこで構築開始前に `preflight()`(実際に DIRECT クライアントを1つ作って壊すだけ、数ミリ秒)を
通し、駄目なら取り置きを 0 に戻して**ρ-test 無効時と完全に同じ経路**へ落とす。

**(c) 部分結果を捨てない**

Phase35 の実装は `except Exception: best_real = None` としており、
**K件のうち4件目が失敗すると1〜3件目で得た正しい勝者まで捨てていた**。
実評価済みの結果は本物の測定値なので保持するよう修正した。

**(d) ラッチ(1-3)**

pybullet の初期化に失敗するような環境ではK件すべてで同じ失敗が起きる。
リトライは壁時計を焼くだけで、**余裕が約15秒しかない現状では timeout の引き金**になる。
そこで**同一シーンで1度でも失敗したら以降そのシーンでは複製評価をしない**ラッチを入れた。

握る例外は `Exception`(`BaseException` は握らない → KeyboardInterrupt/SystemExit は素通し)。

### 1.2 (1-2a) 早期失敗はビット単位一致 —— **6/6**

`MYSOLVER_REPLICA_FORCE_FAIL={import,init}` を注入し、ρ-test 無効時の `build_order` 出力と比較:

| シーン | import | init |
|---|---|---|
| A01_1c_40_plain | 一致 (差分 0/40) | 一致 (差分 0/40) |
| A02_1c_80_plain | 一致 (差分 0/80) | 一致 (差分 0/80) |
| A03_1c_40_shelf | 一致 (差分 0/40) | 一致 (差分 0/40) |

preflight が取り置きを正しく解除していることの直接確認である。

### 1.3 (1-2b) 実行時失敗は run1 の劣化を再現しない —— **劣化 0.00**

構築後に判明する失敗ではビット単位一致は原理的に不可能なので、
**run1 の劣化パターン(A07 −10.74 / D01 −10.77 / C02 −6.92)を再現しないこと**を確認した。

| シーン | 注入 | 停止理由 | ラッチ | 実評価 | 順序が off と一致 | run1 の劣化 |
|---|---|---|---|---:|---|---:|
| A07_1c_40_bulky | runtime | `runtime_error` | True | 0 | **一致** | −10.74 |
| A07_1c_40_bulky | deadline | `wall_deadline` | True | 0 | **一致** | −10.74 |
| D01_A_1c_40_softheavy | runtime | `runtime_error` | True | 0 | **一致** | −10.77 |
| D01_A_1c_40_softheavy | deadline | `wall_deadline` | True | 0 | **一致** | −10.77 |
| C02_2c_55_shelfprio | runtime | `runtime_error` | True | 0 | **一致** | −6.92 |
| C02_2c_55_shelfprio | deadline | `wall_deadline` | True | 0 | **一致** | −6.92 |

**3シーンとも順序が off 構成と完全一致した(=劣化 0.00)。**
理由は run2 の設計そのもので、これらのシーンは**壁時計ではなくユニット予算を使い切って
先に構築を終える**ため、壁時計から引いた45秒の取り置きが**そもそも binding していない**。
run1 が大きく劣化したのは取り置きをユニット予算からも引いていたからで、
「壁時計からしか引かない」という原理が実際に効いていることが実測で確かめられた。

### 1.4 (1-3) ラッチ —— **6/6 発動**

上表のとおり全ケースで `latched=True`、`実評価=0`(最初の失敗で即座に打ち切り)。
成功→失敗→成功→失敗→成功 の5連続実行でも、失敗回はラッチが立ち、
**成功回には影響しない**(実評価4件で正常動作)ことを確認した。

## タスク3: 提出既定 2.0e7 での26シーン確認

**対照も 2.0e7 で取り直した**(1.55e7 の対照と比べてはならない、という指示どおり)。

### 3.1 結果

| 指標 | off (2.0e7) | on (2.0e7) | 差分 | σ | SE | **t** | 悪化シーン |

| fill_loose | 36.213 | 38.125 | +1.912 | 6.312 | 1.238 | 1.545 | 1件(D05 −7.36) |

**fill_strict は t=2.659 で採用基準を維持し、悪化シーンは0件。**

| 予算 | mean | σ | t | 到達シーン数 k |
|---|---:|---:|---:|---:|
| 1.55e7 | +1.850 | 3.060 | 3.082 | 10 |
| **2.0e7(提出既定)** | +1.671 | 3.205 | **2.659** | **7** |

### 3.2 群別の集計(恒久ルール6)

| 群 | n | mean | σ | 変化 | 悪化 |
|---|---:|---:|---:|---:|---:|
| 複製評価器の適用対象(既積みなし・optimize有効) | 16 | **+2.716** | 3.754 | 7件 | **0件** |
| 既積みあり(適用外) | 5 | ±0.000 | 0.000 | 0件 | 0件 |
| optimize=False(構造的に不変) | 5 | ±0.000 | 0.000 | 0件 | 0件 |

適用外の10シーンが**きっちり ±0.000** であることは、`is_applicable` のゲートと
既定無効経路が意図どおり働いていることの裏取りでもある。

### 3.3 t が下がった原因は「取り置きと予算の相互作用」で確定

指示どおり、これは統計的なばらつきではなく**実在する相互作用の証拠**として扱う。
実際、原因はシーン単位で特定できた。**2.0e7 で ρ-test が効かなくなった4シーンは、
すべて壁時計律速になったシーンである**:

| シーン | 1.55e7 の効果 | 2.0e7 の効果 | 2.0e7 の optimize (off → on) | 判定 |
|---|---:|---:|---|---|
| A06_1c_40_small | +1.45 | **±0.00** | 154.7s → **165.0s** | 複製の締切(165s)に到達 |
| C02_2c_55_shelfprio | +4.88 | **±0.00** | 120.5s → **165.2s** | 複製の締切(165s)に到達 |
| A08_2c_140_extreme | +3.41 | **±0.00** | 103.8s → 120.0s | 構築の締切(165−45=120s)に到達 |
| D03_A_2c_60_prioheavy_cont | +2.05 | **±0.00** | 110.6s → 136.5s | 実評価の件数が足りず勝者が変わらず |
| C03_2c_80_prio | ±0.00 | **+1.87** | 113.9s → 148.3s | 逆に 2.0e7 で新たに効いた |
| D05_A_1c_40_tall | +0.39 | **+2.12** | 93.0s → 97.9s | 同上 |

機序: ユニット予算が増えると**構築が壁時計まで走るシーンが増える**。
取り置きは壁時計からしか引いていないので、構築が長引くほど
**複製評価に実際に使える時間が削られ、評価できる候補数が減る**。
候補数が減れば「代理の1位より良い候補」を引き当てる確率も下がり、k が 10 → 7 に減った。

**新たに壁時計律速になったシーンID**(1.55e7 では 118s 未満だったが 2.0e7 で到達):
`A02_1c_80_plain` / `A04_2c_80_noprio` / `A05_2c_80_prio` / `A08_2c_140_extreme` /
`D03_A_2c_60_prioheavy_cont`

なお **fill_strict の悪化シーンは0件**なので、この相互作用は「効果が薄まる」形で出ており、
「壊す」形では出ていない。ここが run1 の劣化(構築の質そのものが落ちた)と決定的に違う。

### 3.4 壁時計の余裕(3-2 の発動条件の判定)

| 構成 | optimize mean | optimize **max** |
|---|---:|---:|
| off (2.0e7) | 82.98s | 154.69s |
| **on (2.0e7)** | 91.92s | **165.17s** |

指示された発動条件は「**optimize max が 170秒を超える**、または安全弁の発火が1件でもある」。
実測 **165.17s < 170s** なので、数値条件は満たしていない。
165秒に達しているのは A06(165.0s)と C02(165.2s)の2件で、これは
**複製評価ループが設計どおり締切で打ち切った**もの(`stopped='wall_deadline'`)であり、
異常ではない。`optimization_timeout=180s` に対する余裕は **約14.8秒**。

締切は `HARD_WALL_LIMIT` による**壁時計**の保証なのでマシン速度には依存しない
(遅いマシンでも165秒で切り上がる)。超過しうるのは締切判定の後に走る1配置ぶんで、
`planner.plan`(最大6秒)+ pybullet の定着ぶんに有界である。

**本フェーズでは対処を入れていない。** 数値条件(170秒)を満たしておらず、
対処を入れれば「対処後の fill 低下を必ず測定する」ために26シーンをもう1回
(約45分)回す必要があるためである。ただし余裕14.8秒は薄いので、
**提出前に対処するかどうかはユーザー判断としてエスカレーションする**(§タスク4)。
対処する場合の第一候補は指示どおり `HARD_WALL_LIMIT` 165 → 158秒である。

### 3.5 判定

判定基準「t>2 かつ悪化シーンが少数(2件以下、いずれも −2.0 未満)」に対し、
**t=2.659 / 悪化シーン 0件**で通過。タスク4(提出)へ進める状態にある。

### 予測と判定基準(提出後に追記する)

ベースライン 53.64、予測 **+1.11 ± 0.36**(SE=0.629 fill ≒ public ±0.38)。
ただし 2.0e7 の実測は +1.671 fill なので、public 換算の予測は **+1.00 前後**に下がる
(fill → public の換算 0.6 倍、Phase35 の +1.850 に対する +1.11 と同じ換算)。

- **+0.6 以上** → 転移。この構成を主枠に格上げし、53.64 を保険枠へ
- **+0.1 〜 +0.6** → 部分的に転移。採用は維持。
  **原因の第一候補は「隠しシーンにおける既積みシーンの比率」**
  (ローカルの適用対象は 16/21。隠し側で既積みが多ければ効果はその比率どおり縮む)
- **+0.1 未満** → 転移せず。Phase33 と同じパターン。Phase37 に進む前に判断を仰ぐ

⚠ **この提出をレジーム判定に使ってはならない。** strict +1.671 / loose +1.912 の差は
public 換算で一般化誤差 ±0.38 より小さく、どちらのレジームでも同じ結果が出るため判別不能。
Phase12 と同じ誤り(1回の Δpublic から判別できると思い込む)を繰り返さないこと。
