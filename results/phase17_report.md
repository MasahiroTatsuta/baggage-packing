## 1. 背景と方針

Phase16 §2.3 で、反復間ノイズ(P02 で fill_strict ±5.14)とシーン単位の budget 非単調性
(スプレッド最大13.4pt)の共通根本原因が
`planner._search_best` / `_evaluate_candidates` の多重な `time.perf_counter()` チェックに
あることを特定した。リスタート層だけの決定化では解決しないことも実証済み。

本フェーズでは、打ち切り条件の**表現**を「壁時計」から「消費した評価コスト(ユニット)」へ
全階層で置き換える。挙動そのものを変えるのが目的ではないが、打ち切り位置は必然的に
変わるため、出力の完全一致は「optimize無効かつ時間内に自然完了するシーン」でのみ要求する。

壁時計に残す役割は2つだけ:

1. **較正**: 呼び出し元が秒で表現した予算を、決定的な定数 `UNITS_PER_SEC` でユニット数へ換算する。
2. **非常用の最終安全弁**: 本番タイムアウト(policy 8s / optimization 180s)を絶対に踏まない
   ための保険。通常は発火しない。発火した場合のみ決定性が失われるが、その場合でも
   制約遵守を優先する(方針3)。

## 2. 実装

### 2.1 コストモデルの実測較正(`tools/phase17_probe.py`)

`_evaluate_candidates` の全呼び出しについて (候補XY数 n_xy, supports数, obstacles数, 実時間) を
収集し、`_candidate_xy` と `plan()` の実時間も併せて計測した(6シーン、`plan()` 総時間155.1s、
`_evaluate_candidates` 29994回、`_candidate_xy` 26420回)。

| 内訳 | 総時間 | 1回あたり | 呼び出し回数 | plan時間比 |
|---|---|---|---|---|
| `_evaluate_candidates` | 62.6s | 2.09ms | 29994 | 40.4% |
| `_candidate_xy` | 90.2s | 3.41ms | 26420 | 58.1% |

**重要な実測結果: 候補集合の構築(`_candidate_xy`)のほうが評価(`_evaluate_candidates`)より重い。**
グリッド生成 + Extreme Point 列挙 + `set`/`sorted` が Python レベルで走るためで、しかも
呼び出し回数もほぼ同数である(候補キャッシュは `(pool_idx, orn_idx)` 単位で、y層のlevel 0 で
確定することが多いため再利用がほとんど効かない)。評価コストだけをユニット化すると探索作業の
半分以上を計量し損ねるため、候補構築も同じユニット系で計上する。

採用したコストモデル:

```
units(評価)     = n_xy * (n_supports + n_obstacles + COST_CONST)      # COST_CONST = 8.0
units(候補構築) = CANDIDATE_BUILD_COST * (グリッド点数 + 8 * n_obstacles)  # = 18.2
```

`CANDIDATE_BUILD_COST` は「両者が同じ units/sec になる」ように決めた
(評価 1.63e7 units/s ÷ 候補構築 8.94e5 生units/s = 18.2)。

較正定数は集計 1.60e7 units/s(シーン別 1.31e7〜2.01e7)に対し、名目秒あたりの実所要時間が
名目を超えにくいよう **`UNITS_PER_SEC = 1.55e7`** を採用した。

### 2.2 `planner.SearchBudget`

打ち切りを「消費ユニット」で判定する予算オブジェクト。親子の入れ子をサポートし、
`spend` は親へ伝播、`exhausted` は親も見る(1手の予算 ⊂ 1リスタートの予算 ⊂ optimize全体の予算)。
`exhausted()` は「これ以上新しい評価を**始めない**」判定であり、始めた評価は必ず最後まで行う。
超過量は1回の `_evaluate_candidates` 分(高々数ms相当)で有界。

### 2.3 各階層の置き換え

| 階層 | 旧: 壁時計 | 新: ユニット |
|---|---|---|
| `_evaluate_candidates` | 入口で `perf_counter() > deadline` | `budget.exhausted()` → `budget.spend(units)` |
| `_search_best` | container/level/pool/orientation の4箇所で `perf_counter()` | 同4箇所を `budget.exhausted()` |
| `plan` | `deadline = start + time_budget`、再探索の可否も壁時計 | `SearchBudget.from_seconds(time_budget)`、再探索可否は `not budget.exhausted()` |
| `simulate.simulate_order` | 毎ステップ `deadline - now` から予算算出 | 親予算の `child_seconds(per_step)` |
| `simulate.greedy_construct_order` | 同上 | 同上 |
| `ordering.build_order` | リスタート配分・打ち切りを「残り時間」で決定 | 「残りユニット」で決定 |

### 2.4 build_order が単調になる理由

残り予算がユニットで決まると、**リスタート回数 N も各リスタートへの配分も決定的**になる。
さらにリスタート i の乱数列はリスタート 0..i-1 の消費だけで決まり、それらも決定的なので、
**リスタート i の結果は N に依存しない**。したがって `build_order` は
「決定的な系列の先頭 N 個の argmax」という構造になり、予算(=N)を増やすと目的関数
(risk調整済み体積 − placementペナルティ)が**単調に**改善する。
Phase16 §1.5 で観測した「予算を変えると乱数列がまるごとシフトして、シーンごとに改善するか
悪化するかが事実上ランダムになる」構造がここで解消される。

### 2.5 非常用安全弁(方針3)

| 経路 | 名目予算 | 安全弁 | 根拠 |
|---|---|---|---|
| `agent.policy` | 5.5s 相当のユニット | `POLICY_HARD_WALL = 6.0s` | policy_timeout 8s / 制約 policy<7s。決定性より制約遵守を優先 |
| `agent.optimize` | `DEFAULT_TIME_BUDGET = 120s` 相当 | `min(165s, 名目 × 1.4)` | optimization_timeout 180s / 制約 <170s |

安全弁の壁時計チェックは `exhausted()` 64回に1回に間引いている(発火しない限り結果に関与しない)。
本環境より**遅い**マシンでは同じユニット数の消化に時間がかかるが、安全弁が発火するまでは
最後まで決定的に探索しきる(=マシン速度に依らず同じ出力)。本環境より**速い**マシンでは
同じ探索を短時間で終える(安全側)。

### 3.3 検証(b): budget 再掃引(30/60/120/165)— スプレッド **−58%**、非単調 **−70%**

#### 3.3.1 まず出た負の結果: 決定化だけでは単調性は回復しなかった

ターゲット1(決定化)のみのコードで3点(30/60/120)を掃引したところ、**スプレッドはむしろ拡大**した。

| | strict spread 平均 | strict 最大 | 隣接予算で悪化した回数 |
|---|---|---|---|
| Phase16(×3) | 5.33 | 9.84 | 16/42 |
| ターゲット1のみ | **6.76** | **18.36** | 16/42 |

原因は §2.4 の単調性の議論が「同一予算内」でしか成立していなかったことにある。
`build_order` は1リスタートへ配る予算を「残り予算 ÷ 残り候補数」で決めており、さらに

リスタート i の結果そのものが変わる**。予算を増やしても「同じ系列をより多く辿る」のではなく
「まるごと別の系列を辿る」ため、改善するか悪化するかは事実上ランダムのままだった。

#### 3.3.2 ターゲット2: 配分を総予算から独立させる

1リスタートの配分(`CONSTRUCT_SLICE = 20.0`)・`final_margin`・`max_validate_slice` を
すべて総予算に依存しない固定値にし、さらに「満額の枠が入らないなら新しいリスタートを
始めない」ことで尻切れリスタートも排除した。

`tools/phase17_restart_trace.py` でリスタート系列の**接頭辞性**を直接検査した(P02):

```

b60 (2リスタート) vs b120(5):  一致 2/2 -> PREFIX-OK
```

#### 3.3.4 残った非単調性(7/63)とその原因

C03(15.18)は**単調非減少**(20.46→35.64→35.64→35.64)なので、スプレッドが大きいこと
自体は問題ではない(そのシーンでは予算が本当に効く、という意味)。一方、実際に悪化した
7ケース(A07/C02/C01/P01/A06/A08/D04)には2つの原因が残っている:

1. **目的関数の代理誤差**: `build_order` が単調に改善させるのは影シミュレータ上の
   「risk調整済み体積 − placementペナルティ」であって、実機の fill ではない。
   代理指標が良くなっても実 fill が下がることは原理的に起こりうる。
2. **最後のリスタートの validate が切り詰められうる**: `FINAL_MARGIN`(6.0s)が
   `MAX_VALIDATE_SLICE`(12.0s)より小さいため、最後のリスタートの検証だけは
   残予算で truncate されうる。ここだけ総予算依存が残っている。
   **`FINAL_MARGIN >= MAX_VALIDATE_SLICE` にすれば解消できる見込み**だが、本報告の
   掃引はこの設定で計測済みのため、本フェーズでは変更せず次フェーズの候補として記録する

| 120 | 18.24 | 62.84 | 96.87 | 116.64 | あり |
| 165 | 18.24 | 62.84 | 96.87 | 125.36 | あり |

60秒以上ではすべて同じ順序に収束する(=単調性は効いている)。問題は、**探索が
「影シミュレータの目的関数(risk調整済み体積 − placementペナルティ)は改善するが、
実 fill も stability も悪化する」順序を選んでいる**ことである
(fill 20.54→18.24、fill計上率 65.9%→56.1%)。予算の再調整では解決しない。

なお、このシーンの stability は Phase14: 98.18/98.19、Phase15: 98.17、Phase16: 98.27 と
一貫して98前後だったので、「旧コードでは運良く通っていただけ」ではない。
**Phase17 の決定的な探索が、このシーンで実際に悪い順序に収束している。**
言い換えると、決定化は代理誤差を作り出したのではなく、**これまで運任せで間欠的にしか
現れなかった代理誤差を、常に露出する形に変えた**。

#### 3.5.2 試した対策: `FINAL_MARGIN >= MAX_VALIDATE_SLICE`(効果なし・据え置き)

§3.3.4 で挙げた「最後のリスタートの validate が切り詰められる」問題を潰すため
`FINAL_MARGIN` を 6.0→12.0 にして旧6シーンを再計測したが、**6シーンすべてで
fill/cog/stability/placement が完全に一致**し(差は壁時計のみ)、この違反には無関係だった。
さらに 12.0 では `CONSTRUCT_SLICE`(20.0)と合わせて1リスタートの起動に32秒必要になり、
**budget=30 でリスタートが1回も回らなくなる**(実測 opt 3.73s)ため、掃引の30秒点の意味が
変わってしまう。本フェーズの全計測は 6.0 で実施しているので **6.0 のまま据え置き**、
`CONSTRUCT_SLICE` の引き下げとセットで次フェーズで再検討する。

## 4. 計測プロトコルの再評価(指示5)

**結論: A/B比較のための「3回平均」は不要になった。repeats=1 で十分で、repeats=2 は
「決定性が壊れていないことの見張り」として残す価値がある。**

根拠:

* P02 ×5(最終コード、budget 30 と 120 の両方): 全6指標で **std = 0.0000**。
* 26シーン×2(既定予算): **26シーン全部で std = 0.0000**、スイート集計でも std = 0.0000。
* しかもこれは「マシンが安定していたから」ではない。P02 の5回の実所要時間は
  budget30 で 29.5〜41.5秒、budget120 で 101.9〜141.5秒と**約4割**ばらついている。

したがって、これまで「3回平均」が必要だった理由(同一入力でも結果が変わる)は消滅した。

**推奨プロトコル**

| 用途 | 推奨 repeats | 理由 |
|---|---|---|
| コード変更のA/B比較 | **1** | 決定的。3回平均は同じ数字を3回足すだけで情報量ゼロ |
| 最終確認・回帰チェック | **2** | std>0 が出たら「非常用安全弁が発火した(=このマシンが較正より遅い)」という**実行環境の警告**として読める。ノイズではなく異常検知になる |
| 3回以上 | 不要 | — |

副次的な効果として**計測コストが約1/3になる**。実際、本フェーズの4点掃引は
repeats=1 で 21シーン×4予算を約2時間で回せた(Phase16 は同じ掃引に repeats=3 で
約6.6時間かけていた)。次フェーズ以降はこの余力をより広い掃引・より多くの候補比較に
充てられる。

**重要な注意**: この決定性は「非常用安全弁(hard_deadline)が発火しない限り」成立する。
本環境(2コア)より遅いマシンでは発火しうるので、std>0 を観測したら真っ先に
`UNITS_PER_SEC` の較正を疑うこと。本フェーズの全計測ではスイート26シーン・
掃引84シーン実行を通じて std=0 が保たれており、発火は観測されていない。

### 5.3 次フェーズの最優先ターゲット(具体的に)

1. **目的関数の代理誤差の縮小(最優先)**。`simulate.simulate_order` の
   risk調整済み体積は、`gen_2containers_priority` で実 fill と逆向きに動いた
   (目的関数↑ / 実fill 20.54→18.24 / fill計上率 65.9%→56.1% / stability 98.23→96.87)。
   決定性が確保された今、**この代理誤差は単一シーンで再現可能な形で固定されている**ので、
   デバッグ対象として極めて扱いやすい(Phase16以前は同じ調査が乱数に埋もれて不可能だった)。
   目的関数に stability の代理(積み上げ高さ・支持の際どさ)を入れる案が第一候補。
2. `CONSTRUCT_SLICE` の引き下げ + `FINAL_MARGIN >= MAX_VALIDATE_SLICE` のセット導入
   (§3.5.2)。現在 budget120 でフェーズ2(ランダムリスタート)がほぼ回っていない
   (5リスタート×20秒でフェーズ1が予算を使い切る)ので、スライスを細かくすると
   多様性と予算利用率の両方が上がる可能性がある。
3. `_candidate_xy` の高速化。probe実測で **plan() 時間の58%** を占めており、しかも
   候補キャッシュがほとんど再利用されていない(26420回の構築に対し評価は29994回)。
   ここを削れば同じ壁時計でユニット予算を大幅に増やせる = 実質的な探索力の向上になる。
   本フェーズのユニット化によって「探索量」が明示的な数値になったので、
   高速化の効果をそのまま予算増として評価できるようになった。
