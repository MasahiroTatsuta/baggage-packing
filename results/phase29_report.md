## 0. エグゼクティブ・サマリ

- **【結論】不採用。** 衝突駆動リスタートが build_order の出力を変えるのは
  **26シーン中2シーン**(C03, P05)だけで、うち採点指標が動いたのは **1シーン**
  (C03: fill_strict **32.208 → 34.904 (+2.696)**、fill_loose 48.019 → 52.665 (+4.645))。
  26シーン平均は **fill_strict +0.104 / σ=0.529 / SE=0.104 / t=+1.000**。
  単一シーン効果は t≡1.000 に固定される(Phase28 §5.1)ので、採否基準 `t>2` を
  **原理的に**通過できない。指示の足切りルールに従い **26シーン測定は実行していない**。

- **【本フェーズ最大の成果: Phase24 の (a) の解釈が誤っていた】**
  (a)=搬入経路が封鎖された空き 29.993 m³(空きの38.8%・fill換算13.14pt)は
  **「残荷物の *どれか* が入る空間」の合計**である。ところが評価は sudden death なので、
  エピソードを止めるのは常に **次の1個(X)** であり、意味があるのは「X が置けるか」だけ。
  実測: **21シーン中15シーンで、X はそもそもどこにも入らない**
  (支持付きで収まる位置が **ゼロ**。voxel を 0.10 → 0.05 → 0.025 と細かくしても
  ゼロのまま、`tools/phase29_diag.py` §5.1)。つまり (a) の大半は
  「X 以外の荷物のための空間」であり、**X の順序を直しても取りに行けない**。
  Phase24 が見積もった 13.14pt は、順序修正の射程内には無い。

- **【機構そのものは動く。効かないのは母数】** 衝突が同定できた6シーンのうち2シーンでは、
  修正した順序が代理・実測ともに改善した(C03 +2.696 / P05 の `delay_blockers` は

  問題は「そういう衝突が21シーン中6件しか存在しない」ことである。

- **【副産物: 目的関数が最良の修正を選べていない】** P05 では、目的関数が採用する

  棄却された `delay_blockers` が **+4.799** だった。影シミュレータは P05 で
  placed 19個と予測するが実機は28個で、この乖離が修正手の順位を狂わせている(§5.3)。

- **【ステップ0(0-1)】候補順序の母集団は21シーン全体で 5〜10件・中央値6・平均6.19。**

  実質の母集団は「ヒューリスティック順 1件 + フェーズ1の window 列挙 4〜5件」である(§1)。

- **【ステップ0(0-2)】行き詰まり時点の量から最終fillの順位は復元できない。**

## 2. ステップ0(0-2): 行き詰まり時点の量から最終fillの順位は復元できない

各シーンで、記録済みの全候補順序について
Spearman(最終fill, 行き詰まり時点の量) を取り、21シーンで平均して t 検定した
(最終fillは影シミュレータの `placed_volume`。A06 は全候補が同fillで順位が定義できず n/a)。

| 量 | 平均ρ | σ | SE | t | \|ρ\|≥0.5 のシーン |
|---|---:|---:|---:|---:|---:|
| `blocked_ratio` | **+0.375** | 0.364 | 0.081 | **+4.61** | 9/20 |
| `blocked_volume` | −0.278 | 0.425 | 0.095 | −2.92 | 7/20 |
| `supported_volume` | −0.668 | 0.245 | 0.055 | −12.22 | 16/20 |
| `empty_volume`(参考) | −0.940 | 0.072 | 0.016 | −58.04 | 20/20 |
| `n_placed`(参考) | +0.425 | 0.414 | 0.093 | +4.59 | 10/20 |
| 参考: `risk_vol`(現行の目的関数) | **+0.846** | 0.138 | — | — | — |

読み方は3段構えで、結論は「**閉じた**」である。

1. **`blocked_ratio` の符号は Phase28 の罰則と逆。** ρ=+0.375 (t=+4.61) は有意だが**正**、
   つまり「行き詰まり時点で通路が塞がっている順序ほど、最終fillが高い」。
   Phase28 はこれを**罰していた**。Phase28 §5.3 が A02〜A04 の3シーンで観測した
   「再ランクすると必ず配置個数が減る」は、21シーンでも統計的に再現した。

2. **`supported_volume` / `empty_volume` の強い相関は情報ではない。** どちらも
   「詰めた量の裏返し」(詰めるほど残りの空きは減る)で、`empty_volume` の ρ=−0.940 は
   ほぼ恒等式である。目的関数は既に「詰めた量」を `risk_vol` として**直接**持っており、
   その順位復元力は **ρ=+0.846** と、行き詰まり時点のどの量よりも強い。

3. **決定打: `risk_vol` を条件付けると `blocked_ratio` の相関は消える。**
   部分順位相関 ρ(fill, blocked_ratio \| risk_vol) は
   **平均 +0.090 / σ=0.518 / SE=0.126 / t=+0.72**(n=17)。シーン別には −0.754〜+0.866 と
   符号すら安定しない。**目的関数が既に持っている情報を超える順位情報は無い。**

→ **再ランク方向(行き詰まり時点の量で候補順序を選び直す)は完全に閉じた。**
Phase28 の不採用は「重みが悪かった」のではなく「**その量に順位情報が無かった**」ためである。

## 3. ステップ1: 衝突駆動リスタートの実装方針

**重みは一切導入していない。** 目的関数(`risk調整済み体積 − placementペナルティ`)は
Phase28 以前と完全に同じで、変えたのは「次に評価する順序をどう作るか」だけである。
したがって Phase18/24/26/28 が繰り返し踏んだ「シーン横断で使える重み区間が存在しない」問題は
構造的に発生しない。

### 3.1 ブロッカーの同定(`reach.item_blockers`)

新規に書き起こしてはいない。判定式は `tools/phase24_corridor_audit.py` →
`agents/mysolver/reach.py` の掃引判定(`p1 | p2`)をそのまま使い、
**障害物に identity を持たせた**だけである(Phase24 は経路上の障害物の *個数* までは
数えていたが、どの荷物かは記録していなかった)。

行き詰まり時点(`simulate.simulate_order` が `plan() is None` で抜けた瞬間。
新設の `stall_info` 出力引数でその瞬間の containers と pool を受け取る)に、
置けなかった荷物 X について:

1. X が幾何的に収まり支持もある位置を全 orientation で列挙する
2. そのうち搬入経路が塞がれている位置に絞る
3. **棚(静的障害物)が当たっている位置は除外する** —— 棚は順序では動かせないので、
   そこを開けることは原理的にできない
4. 残った位置のうち**ブロッカー数が最小**の位置を選び(C順の最初の最小 = 決定的)、
   その位置を塞いでいる既配置荷物の index 集合を返す

voxel は **0.05**(`MYSOLVER_REPAIR_VOXEL`)。Phase28 の集計用既定 0.10 は
「残荷物の *どれか* が入る空間」を測るには足りるが、**特定の1個**が入る位置を数えるには粗い
(voxel は少しでも重なれば occupied 側に倒れるので細い隙間が消える)。実測 §5.1 のとおり
D01 は 0.10 で「衝突なし」だが 0.05 では衝突が見つかる。1回あたり数十msなので細かい側を採った。

### 3.2 順序の作り直し(3手・決定的な順番で試す)

| 手 | 内容 | 意図 |
|---|---|---|
| `_advance_before` | X を **order 上で最も早いブロッカーの直前**へ移動 | 本命の多手移動。1手スワップではなく、X を全ブロッカーより前へ一気に出す |
| `_delay_blockers` | ブロッカー群を **X の直後**へまとめて移動(相対順序は保つ) | 同じ「X が全ブロッカーより前」を、X 以前の積み方を保ったまま達成する破壊の小さい経路 |
| `_advance_to_front` | X を先頭へ | lookahead_k>1 では**ブロッカーがストリーム順で X より後ろに居ることがある**(置いた順と流れてきた順が違う)。この場合 上2つは None を返すので、唯一作れる手になる。実測 C03 がこれに該当し +2.696pt |

改善(目的関数の厳密改善)しなければその修正は捨て、次の衝突へ移る。改善したら
新しい行き詰まり地点から測り直す。上限 `REPAIR_MAX=12`(通常は予算が先に尽きる)。

### 3.3 従来リスタートとの配分 —— **比率パラメータを作らない設計**

指示は「一定割合は従来どおりのリスタートを残す設計を検討」だったが、
**比率という調整パラメータ自体を作らなかった**。理由は、比率を置くとそれが
実質的な較正対象になり、Phase18/24/26/28 と同じ「シーン横断で使える値が無い」問題を
別の形で持ち込むためである。代わりに:

> フェーズ1/フェーズ2のループは「満額の枠(construct 20s + margin)が入らないなら
> 新しいリスタートを始めない」ので、**必ず端数の予算が余って捨てられている**。
> 修正の試行は validate 1回だけで済む(構築をやり直さない)ので、この端数に収まる。

実測した端数(名目秒): A05 12.6 / C02 1.7 / C03 8.5 / D01 39.7 / P05 9.4。
**総ユニット予算・リスタート回数・その決定的な系列はいずれも不変**で、
Phase17 が確立した「小さい予算の系列は大きい予算の系列の接頭辞」も保たれる。

なお、端数を使い切る判定には **MAX_VALIDATE_SLICE(12s)ではなく validate 1回の実費**
(そのシーンでの実測最大)を使う。実費はシーンで 0.37〜8.84 名目秒と20倍以上ちがい、
上限値で判定すると実費1.5sのシーンでも「端数が足りない」と誤判定して修正が一度も回らない。
`FINAL_MARGIN` の取り置きも修正フェーズには適用しない —— これは
「最後のリスタートの validate が切り詰められると評価値が総予算に依存する」ことを防ぐための
仕掛けであり、修正フェーズでは**切り詰め = 体積の過小評価 = 棄却**にしかならず安全側に倒れる。
実測でこの2点を直さないと到達シーンが **2 → 0** になった(§4)。

## 5. なぜ効かなかったか

### 5.1 【主因】Phase24 の (a) は「次の1個」のための空間ではない

これが本フェーズで最も重要な発見である。

Phase24 の (a) = 29.993 m³ は、**残っている全荷物 × 全 orientation を全位置で列挙し、
「どれかが入って支持もあるが搬入経路が死んでいる」空間**の合計だった。
一方、評価は sudden death なので、エピソードを止めるのは常に **次の1個(X)** であり、
X の後ろに並んだ荷物には出番が来ない。**(a) の大半は「X 以外の荷物のための空間」**である。

実測(`tools/phase29_diag.py`、行き詰まり時点の X について位置を分類):

| voxel | A01 (X=item13) | A03 (X=item13) | A07 (X=item31) | D04 (X=item1) | P02 (X=item1) | D01 (X=item11) |
|---|---|---|---|---|---|---|
| 0.100 | sup=0 | sup=0 | sup=0 | sup=0 | sup=0 | sup=0 |
| 0.050 | sup=0 | sup=0 | sup=0 | sup=0 | sup=0 | sup=2(全て荷物が封鎖) |
| 0.025 | sup=0 | sup=0 | sup=0 | sup=0 | sup=0 | sup=12(全て荷物が封鎖) |

`sup=0` は「支持付きで X が収まる位置が容器内に1つも無い」という意味であり、
**voxel を 1/4 まで細かくしてもゼロのまま**なので離散化の見落としではない。
つまりこれらのシーンで X が置けなかった理由は**搬入経路ではなく、単に場所が無いから**で、
X を前に出す・ブロッカーを後ろに回すといった順序修正では何も変わらない。
21シーン中 **13シーン**がこれに該当する(+ D05 は棚が塞いでいて順序では動かせない)。

**Phase24 が「順序修正で開けられる上限」と見積もった 13.14pt は、
sudden death 下では到達可能な量ではなかった。**
Phase24 の「経路上の障害物1個 23.6% / 2個 21.5% / 3個以上 55.0%」という内訳も、
同じ理由で「順序修正の難易度の分布」としては読めない。

### 5.2 衝突がある6シーンでも、開けるコストのほうが大きいことが多い

衝突が同定できた6シーンで、修正した順序の代理fillを全て測った
(`tools/phase29_repair_probe.py`)。ブロッカーを1個ずつしか越えない弱い手
(`advance_before_<blocker>` = 実質的な単発スワップ)も含めている。

| scene | X | ブロッカー | 各修正の Δ代理fill |
|---|---:|---|---|
| A05 | 36 | [9, 44, 73] | −1.86 / −4.01 / −4.46 / −4.77 / −6.48 / −6.48(**全て悪化**) |
| C01 | 15 | [4] | −7.24 / −7.91 / −7.91 / −9.62(**全て悪化**) |
| C02 | 8 | [33] | −0.50 / −0.50 / −1.63 / −5.12(**全て悪化**) |
| C03 | 38 | [0] | **+5.79**(`advance_to_front` のみ作れる) |
| D01 | 11 | [13, 22, 30] | −3.93 / −10.98 / −11.39 / −11.39 / −12.51(**全て悪化**) |
| P05 | 45 | [40] | **+3.71** / +0.96 / +0.74 |

X を前に出すと、**それまでの層構造ごと積み方が変わる**。開いた通路より、壊した層のほうが
大きいことが多い。4/6 シーンではどの手も悪化した(目的関数も正しく全て棄却している)。

### 5.3 【副産物】影シミュレータが最良の修正を選べていない(P05)

P05 では目的関数が `advance_before` を採用するが、実機では **±0.000**
(順序は変わるのに online の配置結果が完全に同一)。一方、棄却された `delay_blockers` が
実機で **+4.799pt** だった。原因は影シミュレータの悲観で、P05 の base 順序について
影シミュレータは placed 19個と予測するが実機は 28個 置けている
(pre-packed + 棚 + 優先コンテナの複合シーン)。
**修正手そのものは良いものを作れているのに、選ぶ段階で取りこぼしている。**
これは Phase20 が測った代理誤差(Spearman 0.71)が、1手の差という細かい粒度では
より効くという形で現れたものである。

### 5.4 母集団の小ささは「衝突駆動」では直せない

ステップ0(0-1)で分かったとおり、フェーズ2のランダムリスタートは 4/21 シーンでしか
回っておらず、実質の母集団は固定5通りの window 掃引である。本フェーズは
「同じ件数の候補をより良いものに置き換える」ことでこれに対処する狙いだったが、
**置き換えの種になる衝突が6件しか存在しない**以上、母集団の問題には手が届かなかった。

## 6. 採否の判断と、残したもの

### 6.1 判定: **不採用**(既定 `MYSOLVER_REPAIR=0` のまま)

- 到達 2/26 シーン、採点指標が動いたのは 1 シーン、t=+1.000(2×SE を超えない)。
- 指示の足切りルール(1〜2シーンなら打ち切り)に従い 26シーン測定は実行していない。
- **無変更の確認**: `MYSOLVER_REPAIR=0` で決定的5シーン(B01-B04, P04)+
  optimize有効の先頭3シーン(A01-A03、シーンID昇順という機械的な規則で選択)を測定し、
  **8/8 がベースラインとビット単位一致**(fill_strict/fill_loose/cog/stability/placement/soft
  すべて差分 0.000、`results/phase29_noleak.json`)。

### 6.2 実装は残す(既定無効)

`reach.item_blockers` / `stall_info` / 3つの順序修正手は、次の理由で残す:

- **ブロッカー同定は再利用可能な部品**である。Phase24 は「経路上に障害物が何個あるか」までしか
  持っておらず、「どの荷物か」を返す実装は本フェーズが初めて作った。
- **機構は正しく動いている**(C03 で実測 +2.696pt、P05 の `delay_blockers` で +4.799pt)。
  効かない理由は機構ではなく母数(§5.1)なので、母数が変わる設計(下記)では再び使える。

### 6.3 この結果が次に示唆すること(推奨/非推奨)

- **非推奨: 到達可能性を目的関数に足す路線**(Phase24・Phase28)。§2 で
  「行き詰まり時点の量には、目的関数が既に持つ情報を超える順位情報が無い」ことが
  部分相関まで含めて確定した。重みの探し方の問題ではない。
- **非推奨: (a) の 13.14pt を目標に据えること。** §5.1 のとおり、sudden death 下で
  順序修正が触れる量ではない。空き体積の分解をターゲットにするなら、
  **「次の1個が置けるか」だけを分母にした指標**を作り直すところから始める必要がある。
- **検討の余地: X が「そもそも入らない」13シーンの側。** これは搬入経路の問題ではなく
  「その時点までに X の居場所を使い切った」という**容積配分**の問題である。
  X を殺した領域を占有している荷物を同定する(=本フェーズのブロッカー同定を
  「掃引経路の障害物」から「X が入れたはずの空間の占有者」へ置き換える)なら、
  同じ機構がそのまま13シーンに届く。ただし §5.2 のとおり
  「前に出すと層が壊れる」問題は共通なので、効くかどうかは別途測る必要がある。
- **検討の余地: 影シミュレータの精度(§5.3)。** P05 で 19個 vs 実機28個という乖離は、
  修正手の選択を実際に誤らせている。Phase20 の代理誤差は「順位は保たれるので
  意思決定は変わらない」と結論していたが、**1手差の粒度では順位が変わる**ことが
  本フェーズで実例つきで確認できた。
