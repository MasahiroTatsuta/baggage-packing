(a) `hint_soft`/`resolved_priority=2` による整数tier分離が既に実装済みで

この矛盾をユーザーに確認したところ、**「Phase78報告書(実測済み)を正として

## (1-1) centroid緩和で救われたfail_support件数の再測定

### 方法論上の落とし穴(先に報告)

`MYSOLVER_MIN_UNION_SUPPORT_RATIO`等はplanner.py **import時**に環境変数から
一度だけ読まれるモジュール定数であるため、プロセス全体を緩2の環境変数付きで
起動すると、`_reach_death`によるエピソード再現そのものが緩2挙動になり、
死亡局面(pool_list/container_listのindex)がPhase64/65の345件の記録と
一致しなくなる。実際に単純な再実行では大量の`container_or_item_not_found`
が発生することを確認した(該当シーンで20件中20件が不一致)。

そこで `tools/phase79_centroid_recheck.py`(新規)を作成し、
1) 環境変数は一切設定せず(既定0.55/0.6/0.15)Phase64/65と同一手順で
   `_reach_death` を呼んで死亡局面を再現し、
2) 各findingについて `_evaluate_candidates` を **既定閾値のまま** と
   **呼び出し直前だけmonkeypatchした緩2閾値(0.35/0.4/0.25)** の両方で実行し
   (エピソード自体は既定閾値のまま動かしているため死亡局面は変化しない)、
3) 呼び出し後は必ず既定値へ戻す、

という形で「支持判定の受理条件だけ」を変えた場合の効果を分離した。
新しい判定式は書いていない(既存の`_evaluate_candidates`をそのまま2回呼ぶだけ)。

全18シーン345件で実行(`results/phase79_centroid_recheck.json`)。
`n_default_fail_support=345`(Phase64/65の345件と完全一致)により、死亡局面の
再現が正しいことを確認した。

### 結果

| | 件数 |
|---|---:|
| 既定閾値でfail_support(Phase64/65の345件そのもの) | 345 |
| **緩2閾値で救われた(support_ok=Trueになった)件数** | **0** |
| 緩2閾値でも依然fail_support | 340 |
| うち threshold_only(forbidden_hit無し) | 148 |
| うち both(forbidden_hit併発) | 192 |
| うち forbidden_only | 0 |
| fail_supportではなく別段階(fail_transport_y)に切り替わった件数 | 5 |

**centroid緩和(実際にはunion/span/centroidを同時に緩2へ)は、この345件のうち
1件も救っていない(0/345、0%)。**

内訳の変化は既定(153/192/0)→緩2(148/192/0)で、threshold_onlyが5件減っただけ
(数字自体は「救われた」わけではなく、下記の理由で別の失敗段階へ移った)。
forbidden_hit併発の192件(55.7%)はPhase66で確定した式構造上の理由により
不変(union/span/centroidをどれだけ緩めても救えない)。

threshold_onlyから減った5件(P02_A_1c_pre10、item_index=32の5候補)は、
支持判定自体は緩2でTrueになったが、**元々`_evaluate_candidates`は支持判定で
早期returnしていたため一度も評価していなかった搬入経路判定(legal1のy方向掃引)
が、実は別途fail_transport_yで不合格だった**ことが露呈した。つまりこの5件は
「支持を緩めれば置ける」のではなく、支持と搬入経路の**二重の理由**でそもそも
置けない候補だった(centroidでは絶対に救えない)。

### 判定: centroidでは「取り切れていない」のではなく、この345件は元から対象外

**この345件(Phase64が総当たりで見つけた、死亡局面での「合法解の座標」)は、
centroid緩和が実際に効いている経路ではない。** 一方、Phase71/74で確認した
本番の実測(緩2で public 57.18、配置率64.34%、centroid単独で+3.54pt)は疑いなく
本物の効果である。両者を両立させる唯一の説明は:

**centroidの効果は「この27件の死亡局面で最後の1個を救う」ことではなく、
エピソードの序盤〜中盤で無数に発生する軽微な支持判定(union比率0.15〜0.25の
境界域)を随所で通すことで、置ける順序・組み合わせが全体として変わり、
そもそもこの27件の死亡局面のいくつかに到達しなくなる(または、より遅い・
より有利な死亡局面に置き換わる)ことで効いている。**

これは実際に検証できる: 本フェーズの最初の試み(環境変数付きの単純な再実行)で
緩2環境下ではエピソード再現先の死亡局面のitem/container indexが元の345件と
ことごとく一致しなかった(=死亡局面そのものが変わっていた)。これは上記の
解釈と整合する副産物的な確認である。

**含意**: 「Phase64の345件のうち何件救えるか」という枠組み自体が、centroidの
実際の効き方(局所的な最後の1個の救済ではなく、全体の軌道変化)を捉えられない
測定である。今後この種の支持閾値パラメータを追試する場合、ローカルの
post-mortem解析ではなく、Phase73〜77が実際に行ったとおり本番投入(または
最低でもフルエピソードのnum_placed_items実測)で見るしかない。

## (1-3) 未試行の経路の一覧

### 支持判定以外にplan()がNoneを返す原因

コード上は存在する(`fail_inclusion`/`fail_ceiling`/`fail_transport_y`/
`fail_transport_x`/`no_xy`)が、Phase64/65が確認した27件の死亡局面(345件の
候補)では**実測で0件**。この母集団に関する限り、支持判定以外の経路は
「試していない」のではなく「観測されていない」。

### Phase64の「genuinely詰み」9件

Phase64は全item×全向き×全container×5mmグリッド×全z源(床+全既配置荷物上面)
で、支持品質要求を一切課さない最も緩い条件(内包×搬入経路のみ)で総当たり
した上で0件だった。7/9は可視プール1件のみでその1件が本当にどこにも入らない、
残り2件(B04/C02)は5〜10件の可視プールに対し690〜1674comboを評価して0件。
**本フェーズで追加検証すべき新しい角度は無い**(既に最も緩い判定基準で
最も細かいグリッドを尽くしている)。再検証しても同じ結果が出ることが
ほぼ確実なため、実施しなかった。

### オフライン順序(build_order)側の余地

Phase24(到達可能性を目的関数に加算)/Phase28(同、重み付き)/Phase29
(1手移動による誘導)/Phase34(ALNS)の4連敗を再確認した。**指示文は
「当時は足切りを知らずにfillで評価していた」ことを再考の理由に挙げているが、
コードとREADMEを確認した限り、この4件の不採用理由はいずれもfillのcutoff
盲目性とは別の、独立した理由である**:

- Phase28/Phase29: 出力順序が変化したシーン数がk=1〜2件にとどまり、
  t値が`5√k/√(26−k)`で構造的にt≤1.443に頭打ち(k=1→1.000、k=2→1.443)。
  これは**出力そのものが変わるシーン数**の問題であり、num_placed_items等
  cutoff対応の指標に差し替えても、動くシーン数kは変わらないため同じ天井に
  当たる。
- Phase34(ALNS): 受理判定(山登り)が使う代理関数の改善幅と、
  **`replica.py`による本物のpybullet評価器で測った実fillの改善幅**との
  順位相関がρ=−0.321(負)。ローカルのcutoff盲目composite scoreではなく
  本物の評価器で測った結果なので、Phase70が発見した「ローカルscorerは
  足切りを実装していない」問題とは無関係に、代理関数そのものの精度不足が
  原因だった。

**したがって、この4フェーズは指示文が示唆するほど「新しい光で見直す価値」は
高くない。** 唯一cutoff盲目性の影響を受けていた可能性があるのはPhase31
(選択則の取りこぼし+2.638、1シーンの反例で不採用)だが、これも「1シーンの
反例」という個別の理由であり、指標をcutoff対応にしても反例自体は消えない。

**むしろ再検討の価値があるのはPhase35/44のρ-test(REPLICA_SELECT)**。
Phase35はALNSの代理関数問題を「代理を使わず本物のpybullet評価器で選ぶ」
ことで解決し、ローカルA/Bでt=3.082(採用基準を通過、悪化0件)を記録した。
しかしPhase44で確認された通り、**本番投入では`fill_score`が13桁不動=
一度も機能しなかった**。原因は`REPLICA_RESERVE_S`(45秒)の取り置きすら
発生していない(=`build_order`冒頭のゲートで早期に諦めている)ことまでは
Phase37/38のテレメトリで絞り込まれていたが、n=4(`evaluate()`内の実行時例外)
という段階特定で止まっている。**この先の切り分け手法(実行時間への内部状態
の符号化=診断ビルド)は、Phase61で公式セミナーにより明示的に規約違反と
確認され、恒久的に断念が確定している**(`docs/submission_policy.md`
Phase61追記)。したがって、この経路は「未着手」ではなく「ローカルでは
これ以上進められない、正規の調査手段が尽きた」状態であり、再開には
新しい(規約に触れない)診断手段が必要——現時点でそのような手段は
特定されていない。

### 推奨する次の一手

**`MYSOLVER_BEAM_SOFT_LAST`(Phase78)の本番投入。** 理由:

1. 支持閾値(centroid/union/span)・幾何定数(INCLUSION_MARGIN等)の軸は、
   Phase73〜77で頂上・崖の両側を確認済みで、**これ以上動かしても実測上の
   伸びしろがほぼ無いことが確定している**((1-1)の追加実測もこれを補強した)。
2. build_order側の4つの過去の不採用(Phase24/28/29/34)は、cutoff盲目性とは
   独立の理由で正しく不採用になっており、指示文が示唆する「知らずに評価
   していたから見直す価値がある」という前提は**この4件に関しては成立しない**。
3. ρ-test(REPLICA_SELECT)は本番で機能しない原因を追う手段が規約上尽きている。
4. 残るのは唯一、**機序を実測済みで(window境界またぎ→ソフト先取り)、
   修正を実装済みで、ローカルA/Bで弱いが一貫した正の効果(num_placed_items
   +0.89pp)を示し、かつ本番結果をまだ一度も見ていない`BEAM_SOFT_LAST`だけ**
   である。

これ以外の「配置数を増やす経路」は、本フェーズの棚卸しにより
**実質的に打ち止め**と判断する。楽観的な数字は出さない——`BEAM_SOFT_LAST`
自体もローカルでは弱いシグナル(per-sceneはカオス的、5改善/3〜5悪化)であり、
本番で伸びる保証はない。
