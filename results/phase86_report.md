## Tier1: Look-ahead Beam

### ステップ1-1: 設計

**現行`simulate.beam_construct_order`の構造**(実装前に確認):
各ステップで、ビーム内の各部分解に対し`planner.plan_topk`が返す上位`top_k`候補
(1手だけ置いた直後の(item, orientation, position))を、「その1手を置いた直後の
risk調整済みobjective」でランク付けし、上位`beam_width`個を残す。**現状は1手先
までしか見ない近視眼的な枝刈り。** 本番既定は`BEAM_WIDTH=1`で、その場合
`top_k = max(1, beam_width) = 1`となり、比較対象すら1個しかない(事実上の貪欲法)。

**設計(既存資産の再利用を徹底)**:

1. `MYSOLVER_LOOKAHEAD_DEPTH`(既定`'0'`)が正のとき、各ステップの枝刈りに使う
   スコアを「1手先の即時objective」から「その1手を置いた後、さらに
   `LOOKAHEAD_DEPTH`手をグリーディ(top_k=1、実質`planner.plan()`)に転がした
   終端でのobjective」に置き換える。**コミットする実際の状態(次ステップに引き
   継がれるcontainers/remaining/risk_vol)は常に最初の1手のみ**——追加の
   ロールアウトは評価専用の使い捨てで、次の実ステップであらためて展開し直す
   (固定した未来を強制しない、標準的なlook-ahead pruningの設計)。
2. **新しい評価関数は作らない。** ロールアウトは既存の`_objective`(risk調整済み
   体積 − 優先手荷物誤配置ペナルティ)と`geo.fill_risk_factor`をそのまま使う。
   本ソルバは元々「幾何評価でオフライン順序を選び、pybulletは本番評価器側でのみ
   最終判定する」という二段構えを既に持っているため、Deep Researchが指摘する
   「rolloutは幾何評価のみ、最終候補だけ本物の安定性判定」は追加実装なしで
   自動的に踏襲される。
3. `LOOKAHEAD_DEPTH>0`のときのみ、比較する枝の数を`LOOKAHEAD_BREADTH`
   (既定3、env`MYSOLVER_LOOKAHEAD_BREADTH`)以上に引き上げる。本番既定の
   `BEAM_WIDTH=1`では`top_k=1`のままlook-aheadしても比較対象が無いため、
   look-ahead有効時だけ最低限の比較候補数を確保する(`BEAM_WIDTH`自体は
   変更しない——ビーム幅を増やすと部分解を持ち越す本数が増え、コストの性質が
   look-aheadの深さとは別次元で変わるため)。
4. 増分更新(EP/EMS差分更新、Phase81のcutcorner含む)はロールアウトでも
   `planner.plan()`を通常どおり呼ぶだけで自動的に使い回される(候補生成自体は
   Phase81ですでに共有関数化されており、新規実装は不要)。

### ステップ1-2: 実装

`agents/mysolver/simulate.py`:

- `LOOKAHEAD_DEPTH = int(os.environ.get('MYSOLVER_LOOKAHEAD_DEPTH', '0'))`
- `LOOKAHEAD_BREADTH = int(os.environ.get('MYSOLVER_LOOKAHEAD_BREADTH', '3'))`
- 新規関数`_lookahead_rollout_score(...)`: 候補1手を仮コミットした状態から
  `extra_depth`手をグリーディに転がし、終端でのobjective値を返す(評価専用、
  `budget.exhausted()`または合法手枯渇で早期終了するanytime設計)。
- `beam_construct_order`内: `effective_top_k = max(top_k, LOOKAHEAD_BREADTH) if
  LOOKAHEAD_DEPTH > 0 else top_k`でplan_topkの候補数を調整。各候補について、
  `LOOKAHEAD_DEPTH>0`のときだけ複製→仮コミット→ロールアウトでランク用スコアを
  算出し、`cands.sort()`のキーに使う。**ビームに実際にコミットする
  risk_vol/n_prio/n_mis(='score')は常に浅い(1手だけの)値のまま**——
  ロールアウトの結果は枝刈りの判断材料としてのみ使い、実際の状態には反映しない。

既定(`LOOKAHEAD_DEPTH=0`)では`effective_top_k == top_k`かつ`rank_score == score`
となり、既存コードパスと完全に同一の計算になる。

### 判定: 撤退(ノイズレベルを大きく超える明確な悪化)

**depth=1で−23%、depth=2で−32%という、深さを増やすほど悪化する明確で単調な
負の効果を確認した。** 6シーート中4シーンが両depthで一貫して悪化し(A01/A03/D01/
P02)、悪化しなかった2シーン(B01/C01)も改善はゼロ(完全に同一)——**改善方向の
シーンは1件も無かった。** 指示書の撤退基準「伸びがノイズレベルなら撤退」を
遥かに超える、明確な負の結果であるため、**Tier1は撤退と判定する。**

**分析(推測、未検証)**: look-aheadロールアウトは`_objective`(risk調整済み体積)を
グリーディに数手先まで伸ばして枝を選ぶが、この短いグリーディロールアウトは
「直近数手で体積を稼ぎやすい」枝を過大評価しやすく、その選択が後続の配置可能性
(搬入経路・残り空間の形状)を悪化させている可能性が高い。これはDeep Research
(B)自身がリスクとして明記していた「評価関数の精度がrollout品質を規定する点は
ALNSと同じ弱点」が、まさに実測で顕在化した形であり、Phase34のALNS不採用
(代理gainと実fillの順位相関ρ=−0.321)と同型の失敗モードだと考えられる。

**指示書の指示どおり、Tier2(MCTS)は見送る。** MCTSも本質的に同じロールアウト
評価(greedy playout by現行スコア関数)に依存する設計であり、Tier1で確認された
「短いグリーディロールアウトが逆効果」という問題が解消されない限り、MCTS化しても
同じ失敗モードを踏襲するリスクが高いと判断した。**Tier3(BRKGA)に集中する。**

## Tier3: BRKGA(Biased Random-Key Genetic Algorithm)

ユーザーからTier3着手の許可を得て実施した。

### 設計

`agents/mysolver/ordering.py`の`build_order`内、従来の**フェーズ2(ランダムリスタート)を
`MYSOLVER_BRKGA=1`のときだけ丸ごと置き換える**形で実装した(if/elseで完全に分岐するため、
既定無効時はフェーズ2が従来どおり動く)。

- **エンコーディング**: 荷物ごとのrandom-key(実数ベクトル、`argsort`で並び順に変換)。
- **decoder**: 新しい評価関数は作らず、既存の`simulate.beam_construct_order`をそのまま使う
  (Deep Researchが指摘する「decoderに現行構築ヒューリスティックを使う」設計そのもの)。
- **母集団**: 既定30体。エリート20%は無条件複製(fitness再評価もしない)、ミュータント20%は
  毎世代ランダム再生成、残りはエリート親×任意親のbiased交叉(既定0.7でエリート遺伝子を
  優先継承)。初期個体の一部はフェーズ1と同じ戦略順(volume_desc等)から埋め込む。
- **noisy-fitness対策**(Deep Research(B)がALNS不採用の原因への処方として挙げる
  re-evaluation + threshold selection): 母集団評価はフェーズ2と同じ`score_noise=0.35`で
  多様性を確保する一方、暫定最良を更新した個体は**ノイズ無しで再decode・再検証**し、それでも
  上回った場合のみ採択する。
- fitnessは代理評価ではなく`validate()`(既存のrisk調整済み体積、real decoder出力)そのもの。

### 実装中に発見・修正した設計ミス(重要)

当初、個体1体のdecode予算を「1世代の総予算 ≈ phase2_units(フェーズ2の1リスタート分、
pop=30なら計40s相当)」で固定していた。**A01で直接検証したところ、フェーズ1(window 5本)が
既定budget=120sのうち74.7sを消費し、残り45.3sではこの1世代分(46s相当)にすら届かず、
世代数0のまま一度もdecodeが走っていなかった**(`BRKGA_STATS={'generations': 0, 'n_eval': 0, ...}`)。

副産物として、**フェーズ2(既存のランダムリスタート)自体もこの規模の予算では0〜1リスタート
しか回っていない可能性が高いことが判明した**——Phase83の「rcl_k15/k50で本番スコアが13桁一致」
という未解決の謎(§—欄外)と整合する一つの具体的な手がかりである(未検証、今回はBRKGA側の
修正のみ行い、フェーズ2側の同種の再設計はスコープ外とした)。

修正: 個体の予算を固定値ではなく、**「フェーズ1終了時点の実際の残り予算」を実測してから、
目標世代数(既定15)に収まるよう逆算**する方式に変更した(`BRKGA_TARGET_GENS`)。
併せて、1世代を開始する条件も「1世代丸ごとの予算」から「個体1体分+最終マージン」に緩め、
残り予算をシーンごとの変動によらず使い切れるようにした(decoder/validateの既存anytime設計
——予算が尽きればそれまでの構築を完全順列にして返す——にそのまま乗る形なので、
安全側の劣化のみで暴走しない)。

### 検証: 既定無効時の不変性

```
[B01] ... [A03] ... 8/8 OK(基準値と一致)
```

**8/8確認。** 設計ミスの修正後も再確認済み。

### 検証: cc_rcl土台+6シーン、BRKGA有効/無効

Tier1と同じ6シーン代表サブセット(A01/A03/B01/C01/D01/P02)、cc_rcl土台(loose2閾値+
cutcorner+rcl)で、**2つの予算水準**で対比した(1回目はCPU競合で無効化——後述)。

**budget=60s(Tier1と同一条件)**: フェーズ1だけで予算をほぼ使い切り、修正後の設計でも
BRKGAは世代数0〜2・評価個体数54(A01)程度しか回らず、6シーンとも配置数はBRKGA無効時と
完全に同一だった。

**budget未指定(本番既定120s、実効上限165s)**: フェーズ1後によりまとまった残り予算が
できるため、BRKGAは複数世代を回せている(opt[s]がBRKGA有効時に一貫して長い:
例A01 84.9s→130.0s)。しかし結果:

| シーン | 配置数(BRKGA無効) | 配置数(BRKGA有効) | fill/cog/stability |
|---|---:|---:|---|
| A01 | 19/40 | 19/40 | 完全一致 |
| A03 | 22/40 | 22/40 | 完全一致 |
| B01 | 24/40 | 24/40 | (このシーンはconfig上`optimize:false`——offline構築非対象、BRKGAと無関係) |
| C01 | 17/40 | 17/40 | 完全一致 |
| D01 | 23/40 | 23/40 | 完全一致 |
| P02 | 31/50 | 31/50 | 完全一致 |
| **合計** | **136/250** | **136/250** | — |

**6シーン中6シーンとも、配置数・fill/cog/stabilityスコアまで完全に一致した(改善0件)。**
BRKGAは実際に複数世代を回している(処理時間の増加で確認済み)ため、「フェーズ1がほぼ全予算を
使い切って全く動いていない」という当初のバグとは異なる——今度は**本当に動いた上で、
フェーズ1の最良解を一度も上回れなかった**。

**なお、budget=60sとbudget未指定でBRKGA無効側の配置数自体が異なる(A01: 26/40→19/40)のは
BRKGAとは無関係の既知の現象**(build_orderの単一グローバルRNGが壁時計依存の消費個数で
分岐するため、Phase16で報告済みの予算非単調性)。BRKGA有効/無効の対比だけを見れば
両水準とも差分ゼロである。

### 判定: 撤退(局所改善ゼロ、明確な負ではないが正の効果も皆無)

Tier1(明確な悪化)とは異なる性質の結果——**BRKGAは積極的に悪化させてはいないが、
検証した6シーン×2予算水準(計12ケース)のいずれでも、フェーズ1の決定的構築を一度も
上回れなかった**。個体1体あたりのdecode予算がフェーズ1の1リスタート(20s相当)に比べて
遥かに薄い(実測 0.05〜数秒相当)ことが主因と考えられる(推測、未検証)——Deep Research
自身も「decoder1回=フル構築なので offline 3分では評価回数が限られる」とリスクとして
明記していた点が、まさにこの予算配分で顕在化した形。

母集団により多くの予算を割くにはフェーズ1(window 5本、既存の手厚い決定的構築)側の
配分を削る必要があるが、フェーズ1は既存の主要な得点源であり、Phase9以来の慎重な調整を
経ている資産のため、今回はそこに手を入れなかった。**この意味で「BRKGAという発想自体」を
否定する結果ではなく、「現在の予算配分の中でBRKGAに割ける取り分が薄すぎた」という
条件付きの否定的結果である。**

以上により、**Tier3は撤退と判定する**。zip化は行わない(局所シグナルが完全にゼロのため、
本番judgment枠を消費する根拠がない)。

### zip化: 実施しない

主枠(cc_rcl、public 57.545)・2枠目(rest020、55.96)は変更なし。
`MYSOLVER_BRKGA`は既定無効のまま安全にリポジトリへ残す(8/8ビット単位不変確認済み)。
