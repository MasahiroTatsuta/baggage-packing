## 訂正(Phase13時点・重要)

**本報告の結論「本番は厳(-0.005)で確定」は撤回する。** 根拠として使った「実提出アンカー」(phase7≈24.40 / phase8≈25.21 / phase9≈27.14)は、**本番フィードバックの fill_score ではなく、`tools/hist_ladder.py` が過去に厳マージンで再計測したローカル値そのもの**だった。厳マージンで測った値を厳マージンで測り直して一致するのは論理的に当然であり、これはレジーム判定の根拠になり得ない**循環論法**である。

SIGNATE の提出フィードバックは合成スコアのみを返し、fill_score 単体の内訳(まして inclusion_margin の値)は開示されない。したがって**本番の fill 計上レジーム(厳 -0.005 / 緩 +0.01 のどちらか)は現時点では判別不能**として扱う。§2〜§4 の「決定的証拠」「結論」は誤りであり、Phase13 以降は**レジーム不問(both-regime-safe)戦略**——`fill_strict` と `fill_loose` を常時併記し、両方が伸びる改善のみを正とする——に切り替える。詳細は `results/phase13_report.md` を参照。

以下、原文はそのまま残す(誤りの経緯を記録として保存する目的)。

## 0. エグゼクティブ・サマリ

- **ターゲット0(本番の `inclusion_margin` レジーム同定)は解決した。結論: 本番は厳(strict, `-0.005`)。** README「内包判定は検証時よりも緩く設定されている」という記述、および `Evaluator.__init__` の既定値 `inclusion_margin=0.01`(緩)にもかかわらず、実測は**厳側と一致**する。
- **決定的根拠:** phase9 エージェントを、提出履歴のfillアンカーが存在する固定6シーン(phase10 で使用した集合)で再計測したところ、
  - **厳(-0.005)**: ローカル fill = **27.12** ⇔ 実提出のアンカー **27.14**(**差 0.02**、実質完全一致)
  - **緩(+0.01)**: ローカル fill = **36.73** ⇔ 同アンカー **27.14**(**差 +9.59**、大幅な過大評価)

  loose ≥ strict は定義上必ず成り立つため、本番が緩レジームなら実提出値は緩計算値に近づくはずだが、実際は厳計算値に(ノイズ内で)一致し、緩計算値とは遠くかけ離れている。他の2アンカー(phase7実測差 +1.48、phase8実測差 0.00)も同じ厳側で説明でき、**緩を支持する系統的な片側ギャップ(+9〜10pt級)はどのアンカーにも見られない**。
- **含意:** phase10/11 のすべてのローカル fill 測定(`tools/scorer.py` 経由、configの `validator.inclusion_margin=-0.005` をそのまま使用)は**最初から正しいレジームで測っていた**。加えて phase11 §3 で発見した「**床直置きの荷物は fill に計上されない**」という構造的事実は、ローカル特有のバグ・簡略化ではなく **本番でも成立する真の制約**であることが確定した。今後も「他の荷物の上に積む(=支持される)体積」を増やす方向の改善が引き続き正しい優先順位である。
- **26シーンスイートでの副次確認(感度分析):** before(p9)→after(現行)で **fill_strict: 18.23 → 22.16(+3.93)**、**fill_loose: 34.27 → 36.47(+2.20)**。単発計測(各1回)のため phase11 本報告の3回平均値(16.99→22.00)とは完全一致しないが、after の値(22.16)は phase11 の after(22.00)と **0.16 差**でほぼ整合し、計測方法の妥当性を裏づける。strict/loose のギャップ(≒床置き非計上分)は **16.04 → 14.31 に縮小**し、phase11 が報告した fill 集計率の改善(0.490→0.589)と整合する。

## 1. 背景と経緯

Phase11 の申し送り(`results/phase11_report.md` §3.3, §6-2)で、以下が **最優先・情報価値大** として指摘されていた。

> 本番 margin の同定: 提出フィードバックの fill_score と、ローカルで inclusion_margin を -0.005 / +0.01 に振って測った fill を突き合わせる。同一エージェントでも local(-0.005) と local(+0.01) の fill 差は極めて大きい(fill_counted_ratio が約 0.59 ⇔ ほぼ 1.0)ため、どちらのレジームかは1回の提出で判別できる。

これを受けて前セッションで `tools/measure_regime.py` を新規作成し、26シーンスイート(p9エージェント)で1回計測(`results/phase12_regime_p9.json`)を行ったところでセッションが切断された。本セッションではこれを引き継ぎ、(1) 同ツールで真の決定打となる**6シーン(提出アンカーが既知の集合)での突き合わせ**を追加実行し、(2) 26シーンスイートの after(現行エージェント)を測定して前回計測との整合性を確認し、報告をまとめた。

### 1.1 `tools/measure_regime.py` の設計

- **非破壊・1エピソード=1回のシミュレーションで両レジームを同時取得**する。`src/ground_handling/evaluator.py Evaluator.calculate_fill_rate` は幾何判定のみで `stepSimulation` を呼ばないため、同一の最終コンテナ状態に対し `inclusion_margin` を変えて2回呼ぶだけで済み、2倍の実行時間にはならない。
- config の `inclusion_margin` 自体は変更しない(変えるとエピソード中の validator 合否判定=物理的に何が置けるかが変わり比較が汚染される)。
- 他4指標(cog/placement/soft/stability)は `tools/scorer.Scorer` で通常どおり1回算出(stability は破壊的なので必ず最後)。
- `src/` と `agents/` は一切変更しない。

### 2.1 判定ロジック

`fill_loose ≥ fill_strict` は定義上(緩マージンは厳マージンが認める内包判定の超集合を認める)常に成り立つ。したがって、

- 本番が **緩レジーム**なら、実提出値は緩計算値に近く、厳計算値からは大きく下振れして観測されるはず。
- 本番が **厳レジーム**なら、実提出値は厳計算値に近く、緩計算値からは大きく下振れして観測されるはず。

実測は明確に後者だった。**phase9 は緩計算値(36.73)から 9.59pt も下振れ、厳計算値(27.12)とは 0.02pt しか違わない。**

### 2.2 ノイズ床との比較

同一エージェント・同一6シーンを2回(phase10 の `hist_ladder.py` 初回計測と本フェーズの `measure_regime.py` 再計測)独立に測った結果、厳側の値は **27.80 → 27.12(差 0.68)** だった。これは探索が壁時計デッドラインに依存すること・stability の揺れ試験に起因する測定固有のノイズであり、**このパイプライン自体の再現ノイズは 1pt 未満**とみなせる。

phase7 の差(+1.48)はこのノイズ床の2倍程度でやや大きいが、片側(緩を支持する方向)には振れていない。緩レジーム仮説が正しければ必要となる **+9〜10pt 級の系統的なギャップ**は、3アンカーのいずれにも表れていない。以上により、**本番の fill 計上レジームは厳(-0.005)** と判定する。

## 4. 結論と含意

1. **本番のレジームは厳(-0.005)で確定。** README の「内包判定は検証時よりも緩い」という記述と、配布 `Evaluator` クラスの既定値(`inclusion_margin=0.01`)は、**実際の本番評価とは異なる**(あるいは README の記述対象が異なる可能性がある)。今後のローカル計測・目的関数設計は厳マージンを前提としてよい。
2. **phase11 で発見した「床直置きは fill に計上されない」という制約は、ローカルの偶然の一致ではなく本番でも真である。** したがって、phase11 で採用した「置ける個数・体積そのものを増やす(union 支持面)」という方向性は理論的にも正しく、逆に phase11 で一度検討して撤回した「沈降後 slack で床置きの期待価値を0とみなす」設計(`fe7c776` で撤回)は、**実は撤回する必要が無かった可能性がある**——ただし phase11 の撤回理由は「README との矛盾」であり、本フェーズはその矛盾を「実測は README と異なる」という形で解消したにすぎない。この設計を再度検討する場合は、撤回時の判断(過適合回避)を踏まえて別途評価すべきであり、本フェーズはこの再検討自体は実施していない(§5 参照)。
3. **cog とのトレードオフ評価(phase10 の重み推定)は前提が正しかったことが裏づけられた。** 重み推定は厳マージンの fill を独立変数として使っており、これは本番の実測と一致する変数だったことになる。したがって phase10 の「fill が public を支配し、cog の独立寄与はほぼ無視できる」という結論の信頼性が下がることはない。

## 5. Phase13 への申し送り

本フェーズはターゲット0の解決のみに専念し、`agents/mysolver/` 自体には一切手を入れていない。phase11 §6 の残項目はすべて未着手のまま持ち越す。

1. **【最優先・未解決】`B01_1c_40_plain` の stability 制約抵触(94.20 < 97)。** phase11 §5.2 で union しきい値の締め付けは割に合わない(B01 fill −10.51, P06 fill −6.11)ことを確認済み。次の方向性は (a) 積み上げ段数・高さの上限、(b) `_score` の `stability_penalty` を「高く積むこと自体」に効かせる拡張、(c) パターンB(optimize無し・lookahead=10)固有要因の切り分け。
2. **搬入経路の詰まり(`fail_transport_y`)の解消。** 依然として停止時の支配的な失敗要因。
3. **cog の再検討。** §4-3 のとおり重み推定の前提の信頼性は上がったため、fill の伸びが頭打ちになった段階で cog とのトレードオフを再評価する価値がある。
4. **旧6シーンの `gen_shelf_patternA` 低下(29.54→25.23、配置21→14個)。** phase11 で示唆された「棚シーンで union 支持面が何かを取りこぼしている可能性」は未調査。
5. **(新規・低優先)** 本フェーズで判明した「README の記述と本番実測の乖離」自体は競技運営側の記述誤りである可能性があるため、次回提出時に実際の `fill_score` を確認し、厳マージン予測(本フェーズの計測値)と再度突き合わせて結論を補強するとよい。
