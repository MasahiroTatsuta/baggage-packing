## 1. 実装したもの

### 1.1 破壊オペレータ(3種、決定的ラウンドロビン)

| オペレータ | 狙う区分 | 何を外すか | 実装 |
|---|---|---|---|
| `occupier removal` | **(i) 幾何で入らない(10/21シーン)** | X が収まりえた位置を**占有している**荷物 | `reach.item_occupiers`(新規) |
| `blocker removal` | (iii) 搬入経路の封鎖(6/21シーン) | X の掃引経路を塞いでいる荷物 | `reach.item_blockers`(Phase29 の既存部品) |
| `worst removal` | 区分横断 | risk割引が最も大きかった配置(=無駄な空間を作った) | `simulate_order` の `contrib_out`(新規) |

**`occupier removal` の実装(`item_blockers` からの拡張点)**

Phase30 §5.1 が指摘した欠落は「現在の `raw_fit_count` は入るか否かしか持たず、
**占有者の identity が無い**」ことだった。`item_blockers` が持っていた部品
(`build_masks` / 箱和による収まり判定 / `SUPPORT_RATIO` の支持判定)は
そのまま流用し、変えたのは **何との衝突を数えるか** だけである:

- `item_blockers`: 掃引箱 (`_sweep_boxes`) と既配置荷物の衝突 (`_hits`) を数える
  → 「経路を塞いでいる荷物」
- `item_occupiers`: **荷物の最終位置そのもの**と既配置荷物 AABB の重なりを数える
  → 「居場所を奪っている荷物」

新規に書き起こした幾何判定は「候補箱と既配置荷物 AABB の区間重なり」だけで、
しかも voxel 化せず連続座標の区間で判定する(3軸に分離可能なので
`mi[:,None,None] & mj[None,:,None] & mk[None,None,:]` の外積1回で済み、
格子解像度による取りこぼしも無い)。手順:

1. X の各 orientation について、**棚・容器外に一切かからない**位置を列挙する
   (棚・壁は順序では動かせないので、そこに掛かる位置は原理的に不可能)
2. そのうち現状態で**支持がある**位置に絞る(空中の無意味な位置を候補にしないため)
3. 各位置で AABB が重なる既配置荷物を数え、**重なり数が最小(かつ1以上)** の位置を選ぶ
4. その位置を占有している荷物の index 集合を返す

実測コストは1回あたり **0.01秒未満**(voxel=0.10)。

### 1.2 修復オペレータ(2種)

外した集合 R = {X} ∪ S を `remaining_order` の先頭へ戻す。並べる規則が2種:

- `greedy insertion`: 体積の降順(積付けの古典的な貪欲。大物ほど置き場所を選ぶ)
- `regret insertion`: **除去後の状態**で収まる位置が少ない順(most-constrained-first)。
  位置数は `reach.fit_position_counts` が実測する

破壊1回につき修復2種を決定的な順(greedy → regret)で試す。

### 1.3 適応化は入れていない

オペレータ選択は **決定的なラウンドロビン**(`alns.OPS` の並び順)。
選択確率を成績で適応させる本家 ALNS の機構は、その重みが実質的な調整パラメータになり、
Phase18/26/28/31/32 が繰り返し踏んだ「シーン横断で使える値が存在しない」問題を
持ち込むため入れていない。受理則も温度パラメータを持たない**厳密改善のみ**の山登り。

### 1.4 予算・決定性

- 反復はフェーズ1/2 が使い残した**端数**だけを使う。総ユニット予算・リスタート回数・
  その決定的な系列は一切変えていない(Phase29 と同じ設計)。
- 固定反復回数ではなく端数に収まるだけ回す anytime 設計。
- 幾何判定のコスト(`item_occupiers`/`item_blockers`/`fit_position_counts`)は
  決定的な量(格子数×形状数)で `simulate.REACH_UNIT_COST` を介してユニット予算へ計上する
  (壁時計だけ伸びて非常用安全弁を踏むのを防ぐ)。
- 乱数は使っていない(破壊も修復も決定的関数)。
- 新規定数はすべて環境変数フック付き・**既定は無効**(`MYSOLVER_ALNS=0`)。

## 2. 接頭辞再開の正しさ(実装の前提条件)

### 2.1 何が問題になりうるか

評価は「スナップショットからの再開」で行うが、`build_order` が返すのは**順序そのもの**で、
本番環境はそれを最初から流し直す。したがって「再開して得た評価」と「返した順序を
最初から流した結果」が一致していなければ、**再開では良く見えたが実際は違う順序**を
採用してしまう。lookahead_k>1 のシーンでは、プールに引き込まれる順番が変わると
その前の判断まで変わるため、素朴に末尾を並べ替えるとこの一致が壊れる。

### 2.2 設計による解決

`alns.py` は **`remaining_order`(まだプールに引き込まれていないストリームの残り)しか
並べ替えない**。プールに既に入っている荷物には触らない。こうすると新しい順序の先頭
`n_consumed` 個は元の順序と完全に同一なので、最初から流し直したときも必ず同じ
スナップショット状態に到達する。`choose_snapshot_k` は「R の全員がまだ
`remaining_order` 側に居る**最大の k**」を選ぶ(=再開位置を最も後ろに取り、
1反復を最も安くする)。

### 2.3 実測(`tools/phase34_probe.py`)

11シーン(うち (i) が8、lookahead_k=5 が2)で
`RESUME`(スナップショットから末尾だけ)と `FULL`(その順序を最初から全部)を比較:

```
等価性(RESUME == FULL): 11/11 件が一致
  placed_ids / placed_volume / risk_vol / violation_ratio / stability_risk すべて差分0
occupier removal が候補を作れたシーン: 11/11
```

`lookahead_k=5` の C02/C03 でも一致しており、2.2 の設計が意図どおり働いている。

### 2.4 既定(ALNS無効)の無変更確認

`simulate_order` の内部(順序ストリームの読み出し)にも手を入れているため、
「新しい引数を渡さなければ無変更」だけでは足りない。Phase34 適用前のコミットを
git worktree に展開し、**同一シーン・同一予算で `build_order` が返す順序そのもの**を
比較した(`tools/phase34_noleak.py`):

```
A01_1c_40_plain   一致=True 差分要素=0/40
A03_1c_40_shelf   一致=True 差分要素=0/40
C02_2c_55_shelfprio 一致=True 差分要素=0/55
D05_A_1c_40_tall  一致=True 差分要素=0/40
4/4 シーンで build_order の出力が完全一致
```

あわせて Phase33 の接頭辞再開検証(`tools/phase33_prefix_resume.py`)を再実行し、
**9/9 件のビット単位一致**と A01 の `risk_vol=1.5079097051369992`(Phase33 の記録値と
完全一致)を確認済み。

## 3. ゲート1: 到達シーン数

ALNS は厳密改善のときだけ採用する山登りなので、**採用が1回でも起きた ⇔ ALNS 無効時と
出力が変わる**。したがって ALNS 有効の1パスだけで到達シーン数が数えられる。

```
optimize有効シーン          : 21 / 26 (B01-B04, P04 は optimize=False で構造的に不変)
ALNS が1回でも評価したシーン : 19
出力が変わったシーン         : 7
  A01_1c_40_plain / A04_2c_80_noprio / A05_2c_80_prio /
  D03_A_2c_60_prioheavy_cont / D05_A_1c_40_tall /
  P03_A_2c_pre8_prio / P05_C_2c_pre8_shelfprio
```

**判定: 4〜7 の帯 → t の上限を確認した上で26シーン測定へ進む。**

### 3.1 t 値の構造的上限

26シーン中 k 件だけが同じ量 d だけ動いたとき、t は d に依らず
`t = 5·√k/√(26−k)` で頭打ちになる:

| k | 1 | 2 | 3 | **4** | 5 | 6 | **7** | 8 |
|---|---|---|---|---|---|---|---|---|
| t の上限 | 1.000 | 1.443 | 1.806 | **2.132** | 2.440 | 2.739 | **3.035** | 3.333 |

k=1 は Phase28 の実測 t=1.000、k=2 は Phase29 の実測と一致しており、
この式が実データで裏付けられている。**k=7 の上限は 3.035** なので t>2 は原理的には
通過できるが、それは7件が**そろって同方向に同程度**効いた場合に限られる。

σ から逆算した必要水準(`t>2 ⇔ mean ≥ 2σ/√26`):

| σ | 2.0 | 3.0 | 4.0(Phase31相当) | 6.0(Phase26相当) |
|---|---|---|---|---|
| 必要な平均効果 | +0.78 | +1.18 | +1.57 | +2.35 |

## 4. 1反復の実測コスト —— Phase33 の見積りは転移しなかった

Phase33 §2.4 は「1反復は全構築1回の **1.6〜4.8%**、端数予算に数十〜200回超入る」と
見積もっていた。**この数字は実際の ALNS には転移しない。**

Phase33 は「末尾15%相当」でスナップショットを取って測っていた。しかし
**占有者は積み山の下のほうに居る**ので、X の居場所を空けるには
ストリームのかなり手前から再開せざるを得ない(`choose_snapshot_k` が返す k が小さくなる)。
`tools/phase34_probe.py` の実測では resume / full-validate 比が **15.9〜96.8%**
(平均約59%)で、A02 と P06 は **k=0**(=ロールアウト丸ごとやり直し)だった。

結果、1シーンあたりの評価回数は **中央値3回・最大29回・21シーン合計82回** にとどまった
(Phase33 の見積り 40〜250回/シーンとは2桁違う)。

停止理由の内訳(21シーン):

| 停止理由 | シーン数 | 意味 |
|---|---:|---|
| `no_candidate` | 10 | **破壊オペレータが対象を出し尽くした**(予算はまだ余っている) |
| `budget_exhausted` | 5 | 総ユニット予算を使い切った |
| `fraction_exhausted` | 5 | 端数が1反復ぶんに満たなくなった |
| `no_stall` | 1 | 全件流し切った(A06。壊すべき衝突が無い) |

**律速は予算ではなく候補の多様性だった**(10/21シーンが `no_candidate`)。
原因は構造的である: lookahead_k=1 のシーンでは行き詰まり時のプールに荷物が
**1個しか入っていない**ため、破壊対象 X の選択肢がそもそも1つしかない。
破壊3種 × 修復2種 = 最大6候補を試し尽くすと、それ以上作る手が無い。
29回まで回った D05 だけが例外(プールの X が入れ替わりながら複数回同定できたシーン)。

C02 は Phase29 の予測どおり「端数 1.7秒 < validate 実費 8.84秒」で
**1回も評価できなかった**(母数が小さいシーンでは反復が入らない)。

### 5.1 動いたシーンとその大きさ

**動いたのはゲート1が予告した7シーンちょうど**(残り19シーンは差分 +0.000、

|---|---:|---:|---:|---|
| A04_2c_80_noprio | +0.4546 | **−3.63** | 2/4 | **逆転** |
| P03_A_2c_pre8_prio | +0.2393 | **−4.62** | 1/1 | **逆転** |
| P05_C_2c_pre8_shelfprio | +0.2296 | +3.92 | 1/1 | 一致 |

個々の変化はいずれもノイズ床(同一シーン再実行の±0.90)を超えており、
「効果が小さくて見えない」のではなく **効果は大きいが符号がそろわない** 状態である。

fill_loose でも同じ3シーン(A04 −2.97 / P03 −6.50 / D03 −7.16)が悪化しており、
レジームによらず同じ構造が出ている。

### 5.2 なぜ効かなかったか(本フェーズ最大の成果)

**ALNS は7シーンすべてで代理目的関数を改善させている。**受理則が厳密改善のみの
山登りなので、これは構成上の必然である(代理が下がる手は採用されない)。
にもかかわらず **実fillが改善したのは 4/7 にとどまり、3シーンでは逆に悪化した。**

さらに、代理gainと実fill差分の**順位相関は Spearman ρ = −0.321(負)** だった:

- 代理gainが**最大**の A04(+0.4546)が、実fillでは**下から2番目**(−3.63)
- 代理gainが最小の A05(+0.0257)は実fillで +2.11 と素直に改善

つまり「代理が最も喜んだ手ほど、実際には裏切る」という関係が出ている。
n=7 と小標本なので相関の有意性は主張できないが、**符号がそろわないこと自体**は
26シーン全体の t を 0.372 まで押し下げた直接の原因であり、これは測定された事実である。

これは Phase32 が **候補の選択**で測った winner's curse(shadow の argmax が
系統的に過大評価されている、t=3.66)と**同じ構造が、ALNS の手の受理でも起きている**
ことを意味する。Phase32 は「どの完成順序を選ぶか」の段階での過大評価を測ったが、
Phase34 は「順序をどう作り変えるか」の段階でも同じ過大評価が効くことを示した。
Phase29 が P05 で単発観測していた現象(「目的関数が採用した手が実機±0.000、
棄却した手が+4.799」)が、7シーンの母数で再現したと言える。

**したがってボトルネックは探索機構ではない。**破壊オペレータは (i) に届いており
(§3、occupier removal が11/11シーンで対象を同定)、接頭辞再開も厳密に正しく
(§2、11/11ビット単位一致)、機構は設計どおり動いている。効かない理由は
**受理判定に使っている代理関数の精度**であり、これは Phase20 が
「代理をより正確にしても順位=意思決定は変わらない」と結論した領域そのものである。

### 5.3 副次的な制約: 候補の多様性

§4 のとおり 10/21 シーンが `no_candidate` で停止した。lookahead_k=1 のシーンでは
行き詰まり時のプールに荷物が1個しか入らないため、破壊対象 X が構造的に1つしかなく、
破壊3種 × 修復2種 = 最大6候補で打ち止めになる。仮に代理の精度問題が無かったとしても、
**このままでは到達シーン数を8以上へ増やすのは難しい**。

## 6. 判定と次フェーズへの申し送り

**不採用。** 既定は `MYSOLVER_ALNS=0` のまま。実装は残す(下記の理由)。

- **残す理由**: 機構の正しさは実測で確認済み(接頭辞再開11/11、occupier removal 11/11、
  既定無変更4/4)。効かない原因は機構ではなく代理精度に特定できているので、
  代理側が改善したときに再利用できる資産である。`reach.item_occupiers` は
  Phase30 が「identity が無い」と指摘した欠落を埋める部品として単独でも使える。
- **Phase35 で ALNS を延長するのは推奨しない。** 破壊オペレータを増やしても
  修復を増やしても、受理判定が同じ代理関数である限り 4/7 の符号一致率は動かない。
  ρ=−0.321 は「もっと探せば良くなる」形の問題ではない。
- **もし次に代理精度へ手を入れるなら**、Phase20 の教訓(較正誤差ではなく
  **候補間の弁別誤差**を減らさないと意思決定は変わらない)と、
  Phase32 の構造(4指標中3指標が独立でない)を前提にすること。
  本フェーズは「弁別誤差が実際に意思決定を誤らせている現場」を7シーンの
  対応表(§5.1)として残したので、次に代理を触るときの直接の教師データになる。
- **打ち切った探索路線の記録**: 順序探索側のレバーは
  Phase24(候補側)・Phase28(目的関数側)・Phase29(1手移動)・Phase34(ALNS)の
  4回でいずれも不採用となった。**探索の作り方を変える路線はここで閉じる。**
