## 0. 出発点(Phase34 の帰結)

Phase34 は決定的な事実を測った。ALNS は受理則が厳密改善のみの山登りなので
**採用された手は定義上すべて代理目的関数を改善している**。にもかかわらず実fillの改善は
7シーン中4シーンにとどまり、**代理gainと実fill差の順位相関は Spearman ρ = −0.321(負)**。
代理gainが最大の A04(+0.4546)が実fillでは下から2番目(−3.63)だった。

これは Phase20 の Spearman 0.71 より強い主張である。Phase20 は候補全体での相関を測ったが、
Phase34 は **最適化器が実際に動く方向(採用された改善手)** での相関を測り、そこでは負だった。
代理 = 実 + ノイズ なら、代理gainが大きい手を選ぶことは
**ノイズが正に大きい手を選ぶこと**である(optimizer's curse の純粋形)。

帰結: **現在の代理関数を山登りするあらゆる手法は失敗する。**
Phase24(候補側)・Phase28(目的関数側)・Phase29(1手移動)・Phase34(ALNS)の
4連敗はすべてこの一つの原因で説明される。
そして探索機構そのものは全部作り終わっている。**欠けているのは信頼できる受理判定だけ**である。

本フェーズは「代理を良くする」のではなく「**代理を信じないための仕組みを作る**」。

## 1. ステップ0: 複製評価器は作れるか

### 1.1 観測から復元できるもの/できないもの

エージェントが `get_init_states` で受け取るのは
`{optimize, lookahead_k, container_list}` だけである。

**復元できた**(`container_list` の各コンテナから):

| 必要な値 | 復元方法 |
|---|---|
| `length/width/height/thickness/cut_x/cut_y` | 観測にそのまま入っている |
| `is_prioritized` / `require_shelf` | 観測の `is_prioritized` / `shelf` |
| `offset_x` | `center[0]`(`local_to_global` は x にだけ offset を足すため) |
| `buffer` | `center[2] − height/2`(`center = (0,0,height/2+buffer)` の平行移動) |
| 既積み荷物の寸法・質量・姿勢・物理係数 | 観測の `packed_items`(`Item.get_info()` 相当) |

復元した幾何が観測値と一致するかを21シーンで検査した結果、
**`volume` / `center` / `n_vecs` / `points` すべて最大差分 0.000e+00(完全一致)**。

**復元できなかった**(`config['validator']` にあり、エージェントには渡らない):

| 値 | 本ローカルでの値 | 扱い |
|---|---|---|
| `inclusion_margin` | −0.005 | 決め打ち |
| `start_z` | 0.08 | 決め打ち |
| `safety_margin` | 0.015 | 決め打ち |
| `ceiling_margin` | 0.018 | 決め打ち |
| `displacement_threshold` | 0.3 | 決め打ち |
| `angle_displacement_threshold` | 45 | 決め打ち |
| `settle_wait_step` | 300 | 決め打ち |
| `item_stream.max_space` | 1 | 決め打ち |

これらはローカル26シーンの config 全件で同一値だった。値は `geometry.py` が既に前提に
しているものと同一であり、**本モジュール固有の新しいリスクではない**
(Phase12/13/27 から続く「本番の inclusion_margin レジームが未確定」という既知の課題そのもの)。

なお `src.ground_handling` をエージェントから import できることは新しい仮定ではない。
`simulate.py` が既に `from src.ground_handling.utils import ORNS` を本番提出コードで
使っており、16.94→53.64 の全提出がこの前提で通っている。

### 1.2 実装

判定式を書き写すと **それは「もう一つの代理関数」**になり同じ罠を踏むので、
`src.ground_handling` の**本物のクラスをそのまま使う**
(`MultiContainerManager` / `PlacementValidator` / `Evaluator` / `Item`)。
方策は `planner.plan` を `Agent.policy` と同一引数で呼ぶ。
エピソードの進め方(`check_inclusion` → `check_transport_path` → `place_item` →
プール補充)も `env.step` と同一順序にした。

### 1.3 忠実度(記録済み130候補との突き合わせ)

`results/phase30_cand_eval.json`(21シーン・130候補、本物の env で評価済み)と突き合わせた。
**新しい探索は一切行っていない**(記録済みの order を流すだけ)。

結果は明確に二峰性だった:

| 群 | シーン | 候補 | 完全一致 | fill_strict差 σ | シーン内順位 Spearman |
|---|---:|---:|---:|---:|---:|
| **既積みなし** | 16 | 99 | **99/99** | **0.000** | **1.000** |
| 既積みあり | 5 | 31 | 25/31 | 4.372 | 0.835(最悪 P06 = 0.455) |
| 合計 | 21 | 130 | 124/130 | 1.975 | **0.961** |

1候補あたりの実行時間は **mean 6.9秒 / max 22.8秒**(本物の env は mean 7.8秒。
複製側のほうが速いのは、本物が毎ステップ深度マップのレンダリングを行うため)。

### 1.4 既積みシーンでずれる原因(特定済み)

原因は実装の不備ではなく **情報の欠落** である。順に切り分けた:

1. **姿勢のズレ**: 複製は既積み荷物を「落ち着いた姿勢」から更に480ステップ定着させるため
   最大 0.74mm ずれていた。→ 観測値へ固定し直す修正を入れ、**初期状態は完全一致
   (ズレ 0.000000000m・速度 0)** になった。しかし P06 の結果は1ミリも変わらなかった。
2. **探索予算の違い**: 突き合わせ相手が既定 2.00e7 で記録されていたため 2.00e7 でも再測。
   → 結果は完全に同一。予算は原因ではない。
3. **乱数**: `planner.py` に `np.random` の使用は無く、policy 経路は乱数を使わない。→ 無関係。
4. **実際の分岐点**: P06 の該当候補では **先頭10手まで本物と完全に同一**の荷物を同じ順で置き、
   11手目以降で判定が食い違っていた。

決定的な計測: 複製側で1配置ぶんの定着(300ステップ)を回すと、
**既積み荷物が1回あたり約1.0mm 動く**。判定閾値は `safety_margin=0.015m` /
`inclusion_margin=0.005m` なので、数手ぶん累積すれば際どい合否をひっくり返すのに十分である。

つまり `container_list` は既積み荷物の**姿勢しか伝えず**、接触状態やソルバ内部状態
(どの接触が有効か、スリープしているか)は伝わらない。同じ姿勢から始めても
**その後の沈み込み方が本物と違う**。これは復元不能な情報である。

### 1.5 ステップ0の判定

**判定基準(順位 Spearman ≥ 0.95 かつ 1候補 20秒以内)を満たしたので、ステップ1へ進む。**
実測は ρ=0.961 / mean 6.9秒。

ただし平均値は二峰性を隠している。そこで **既積み荷物が1つでもあるシーンでは
複製評価器を使わない**(`replica.is_applicable`)。既積みの有無は `container_list` から
実行時に判定できるので、**精度が実証されている領域(ρ=1.000、完全一致99/99)だけで使う**
という設計にした。「使える所と使えない所を実測で切り分けて、使えない所では使わない」
のは Phase12 の撤回(根拠が循環参照だと気づいて結論を取り下げた)と同じ姿勢である。

## 2. ステップ1: ρ-test による選び直し

### 2.1 設計

構築ロジックには**一切触れていない**。変えたのは最後の勝者決定だけ:

1. 従来どおり候補順序を生成する(フェーズ1/2 のリスタート)
2. 生成された候補を代理スコア降順に並べ、重複を除いて**上位K件**(既定 K=4)を選ぶ
3. その K 件だけを複製評価器で実際に走らせ、**実 fill の argmax** を勝者にする

同点なら代理順位が上の候補を残す(決定的)。

### 2.2 予算配分(唯一の設計変数)

**総予算は増やしていない**(Phase25b で飽和済み・増やすと悪化)。複製評価に使う分だけ
構築の予算を減らす:

- `REPLICA_RESERVE_S = 45.0` 秒を先に取り置き、構築側の**ユニット予算と壁時計の両方**を
  その分だけ縮める(`build_budget_s = time_budget − reserve`)
- 実評価は固定 K 件。**「残り時間で入るだけ」にしない**のは決定性のため
  (マシン速度で件数が変われば Phase17 で確保した決定性が壊れる)。
  壁時計は別途 deadline を持たせ、超えたらその候補を捨てて代理の勝者を使う(安全側)

構築予算を減らす副作用が小さいことは Phase25b のスイープが根拠になる
(`UNITS_PER_SEC` 1.55e7 → 2.0e7 で public 53.61 → 53.64。25%削っても 0.03 しか動かない)。

**選び直しそのものは一貫して大きく効いており(+33.84)、悪化は例外なく構築削減側から
来ていた(−19.71)。** ここから設計の欠陥が特定できた:

> 取り置き(45秒)を **ユニット予算からも** 引いていたが、構築の大半のシーンは
> 壁時計ではなく **ユニット予算を使い切って先に終わる**(Phase31 実測で optimize の
> 壁時計は mean 51s / max 152s、上限165sに対して余裕がある)。つまり
> **取り置きを実際には使い切らないシーンでも構築の質だけが落ちていた。**
> A07 は optimize 全体が37秒で終わっているのに、45秒ぶんの構築予算を失っていた。

修正は「**取り置きは壁時計からだけ引く**」。こうするとユニット予算で先に終わるシーンは
一切損をせず、壁際まで走るシーンだけが取り置きぶん早く切り上げられる。
run2 で A07 は 31.13 → **38.81(対照と完全一致=損失ゼロ)**、D01 も 28.45 → **31.53(同)**
に戻り、**悪化シーンが0件になった**。

これは「26シーンの結果を見て良い方を選んだ」のではなく「悪化の内訳を測って原因を特定し、
その原因を直した」ものである。とはいえ run1 の結果を見た**後**に修正していることは事実なので、
測定した構成が2つだけであること、掃引をしていないことをここに明記しておく。

### 3.3 fill_loose では有意でない(重要な留保)

| 指標 | 差分 | σ | SE | t | 悪化シーン |
|---|---:|---:|---:|---:|---:|
| fill_strict | +1.850 | 3.060 | 0.600 | **3.082** | 0件 |
| fill_loose | +1.344 | 6.650 | 1.304 | 1.030 | 5件(最大 A05 −4.63) |

複製評価器は `inclusion_margin=-0.005`(厳)を前提に「実 fill」を測って選んでいるので、
**厳レジームに最適化された選択**になっている。Phase27 が確定させたとおり採点と合法性判定は
常に同じ margin を共有するため実際に効くレジームは片方だけだが、**それがどちらかは未確定**である。
本番が緩レジームだった場合、この改善は有意水準に届かない可能性がある。
`MYSOLVER_REPLICA_INCL_MARGIN` で切り替えられるようにしてある。

## 3.6 判定

**採用**。既定を `MYSOLVER_REPLICA_SELECT=1` に切り替え、`mysolver_submit.zip` を再生成した。

Phase26 以降9フェーズ連続で public が動いていなかったが、その全期間で**ローカルの
採用基準 t>2 を満たした変更は一つも無かった**(Phase23 の b=3 も事後に t=1.62 と判明)。
本フェーズは Phase25a で採否基準を厳格化して以降**はじめて t>2 を通過した変更**である。

効いた理由は Phase34 の診断そのものにある。Phase24/28/29/34 の4連敗は
「代理関数を山登りしている」という一つの原因で説明でき、代理を良くする路線は Phase20 が、
選択則を作り替える路線は Phase31/32/33 が閉じていた。残っていたのは
**代理を使わずに決める**という選択肢だけで、それが本フェーズの複製評価器である。
実際、**代理の1位が実評価でも1位だったのは16シーン中6シーンだけ**だった。
