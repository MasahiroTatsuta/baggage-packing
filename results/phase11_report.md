## 実行方法

Phase10 と同様、長時間計測は `setsid nohup … > /tmp/*.log 2>&1 < /dev/null &` で端末から完全にデタッチして実行した(本環境には tmux/screen が無く `apt-get` も不可のため)。

**重要(本フェーズの計測設計):** 本環境は **CPU 2コア** であり、探索が壁時計デッドラインに依存する本エージェントでは並列実行が結果を歪める。そのため全計測を **逐次** で行い、かつ **before(`_hist/p9/`)と after(`agents/mysolver/`)を同一セッション・同一条件で新規に測り直した**。Phase10 の絶対値(fill 16.33 等)は当時のマシン状態に依存しており、実測で再現しない(例: P06 は phase10 で 8.99±0.00、本フェーズの before 再計測では 11.50)。したがって **本報告の before/after 比較は必ず本フェーズ内で対にした計測どうしで行う**。

## 1. ターゲット1：2コンテナ×優先コンテナ指定時の placement < 100

### 1.1 再現と原因特定

`tools/diagnose_placement.py`(新規)でエピソードを実走査し、`tools/scorer.calculate_placement_score` の2つの減点要因を切り分けた。

| 要因 | D03 | P03 |
|---|---|---|
| (a) 優先手荷物が非優先手荷物の**下敷き** | **0 件** | **0 件** |
| (b) 優先コンテナがあるのに**非優先コンテナへ配置** | **2 件** | **2 件** |

**減点は 100% が (b) の「誤コンテナ配置」**で、下敷きは1件も起きていなかった(Phase9 の `PRIORITY_CLEARANCE_XY/Z` によるハード制約は有効に働いている)。

誤配置が起きた瞬間の状態(実測):

| シーン | step | 荷物 | 優先コンテナ単独での合法手 | 失敗内訳 | その時の優先コンテナ(c0) | 非優先コンテナ(c1) |
|---|---|---|---|---|---|---|
| D03 | 13 | item21 (0.55×0.48×0.54, 優先) | **無し** | `fail_transport_y` 36件 | 8個 vol 43.8% **うち優先6(=非優先2個が占有)** | 5個 vol 23.0% |
| D03 | 19 | item23 (0.82×0.47×0.33, 優先) | **無し** | `fail_transport_y` 30 / `fail_inclusion` 6 | 10個 vol 50.5% うち優先8 | 9個 vol 36.5% |
| P03 | 9 | item45 (0.56×0.62×0.62, 優先) | **無し** | `fail_transport_y` 36件 | 10個 vol 29.4% **うち優先1(=既積み4+非優先5個が占有)** | 7個 vol 17.6% |
| P03 | 12 | item2 (0.76×0.43×0.53, 優先) | **無し** | `fail_transport_y` 30 / `fail_inclusion` 6 | 11個 vol 34.3% うち優先2 | 9個 vol 27.9% |

**原因(確定):**

1. `planner.plan` は「優先荷物は優先コンテナへ」(`enforce_priority_container=True`)は強制していたが、**その逆(非優先荷物を優先コンテナに入れない)は一切制約していなかった**。そのため非優先荷物が優先コンテナの容積と**搬入経路**を先に潰す。
2. 優先コンテナが搬入不能になった後に優先荷物が到着すると、`enforce_priority_container=True` の探索が全滅し、フォールバック(`enforce_priority_container=False`)で**非優先コンテナへ回されて減点**される。パターンA(lookahead=1)ではプールに荷物が1個しか無く、荷物を選び直す自由度が無いため、この一手が確定的に減点になる。
3. `ordering.build_order` の目的関数は `(risk調整済み体積, 配置数)` のみで、**placement 違反を一切評価していなかった**ため、順序探索が「優先荷物が手遅れに到着する順序」を選んでも罰されなかった。

とくに P03 では、最初の優先荷物が来る前に**非優先荷物5個が既に優先コンテナを占有**していた(既積み4個と合わせて10個)。これが「局所バグ」の実体である。

### 1.2 修正

**(1) 優先コンテナの「席取り」(`planner._search_best` の tier 化)**

`reserve_priority_container=True` のとき、候補を2段の tier に分けて **tier を score より優先** してランキングする。

- tier 0: 優先荷物→優先コンテナ / 非優先荷物→非優先コンテナ
- tier 1: 非優先荷物→優先コンテナ

tier 0 の合法手が1つでもあれば必ず tier 0 を選び、**tier 0 が皆無のときだけ tier 1 に落ちる**。したがって「置けたはずの荷物を置けなくする」ことは無く、配置数・fill を構造的に減らさない。有効化条件は「優先コンテナと非優先コンテナが両方存在する」場合のみ(1コンテナが優先指定のシーンでは無効)。

> **実装上の重要な知見:** 最初は「席取り専用の探索段を1つ追加する」実装にしたが、探索段どうしが同じ `time_budget`(policy 5.5s / offline は 1手 0.7〜3.0s)を食い合い、後段が時間切れで打ち切られて**合法手を取り逃す**。P03 で配置数が 21個 → **14個** に悪化し、fill も 12.94 → 5.63 に崩れた。**同一パス内のランキング**として実装し直すことで追加コスト0にした。

**(2) 順序探索の目的関数に placement を組み込む(`ordering` / `simulate`)**

`simulate.simulate_order` が「配置された優先手荷物のうち誤コンテナに入った割合」(既積みの優先手荷物も分母・分子に含む、`scorer` と同一定義)を返すよう拡張し、`build_order` の目的関数を

```
score = risk調整済み体積 − PLACEMENT_PENALTY_WEIGHT × 全コンテナ有効容積 × 違反率
```

とした。fill_score も placement_score も 100 分率なので、両者を等価とみなすなら重み 1.0 が厳密な換算になるが、Phase10 の重み推定で placement は識別できず fill が public を支配していたため、**fill を毀損してまで placement を取りにいかないよう保守的に 0.5** を採用した。

副次的に、目的関数が負値を取りうるようになったため `best_score` の初期値を `-1.0` から「未評価(None)」に変更した(旧実装のままだと全候補が負スコアのシーンで貪欲構築の結果が一切採用されなくなる潜在バグ)。

## 2. ターゲット2：prepacked(積付済み初期状態)の fill

### 2.1 診断

`tools/diagnose_prepacked.py`(新規)で P01/P03/P06 を実走査し、4つの候補仮説を切り分けた。

| 仮説 | 判定 | 根拠(実測) |
|---|---|---|
| **H1. 既積み荷物の上面を候補生成が使えていない** | **確定(主因)** | 下表のとおり、既積み層の上に着地できる候補XYは全体の 2.0%(P01)/6.6%(P03 c0)/7.3%(P06)しか無い。union 判定にすると 6.6%/22.7%/24.7% へ **2.2〜3.4倍** に増える。 |
| H2. 既積み荷物が非軸平行でAABB・搬入判定が過剰に保守的 | **棄却** | 既積み荷物の軸平行からのズレは **最大 0.35°(平均 0.04°)**、AABB体積の膨張率は **最大 1.016(平均 1.002)**。`env.build()` が物理で静定させるため、config で単位クォータニオンを与えた既積みはほぼ軸平行に落ち着く。**ただし本番の既積みが傾いている可能性自体は否定できない**ため、AABB を実姿勢から保守的に取る現行実装(`geometry.item_world_aabb`)はそのまま維持した。 |
| H3. offline最適化が既積み状態を考慮しない | **棄却** | `simulate.clone_containers` は `packed_items` を複製して引き継いでおり、`ordering.build_order` に渡る `container_list` も `get_init_states()` 由来で既積みを含む。考慮されている。 |
| H4. 層規律(Y_SLICE)が既積み荷物と整合しない | **軽微** | 既積みは奥半分(y≥0)を占有するため level0(奥層のみ開放)では合法手が出ず、毎手 level1(全開放)へ落ちるだけで、置ける手を失ってはいない。ただし H1 を直せば level0 が生産的になり相乗効果がある。 |

**H1 の定量(停止時点の状態に対し、未配置荷物×全 orientation の候補XYを総当たり):**

| シーン | 候補XY総数 | 既積み等の上に着地できる候補(現行=単一支持90%) | union 60% |
|---|---|---|---|
| P01 c0 | 173,281 | 3,424 (**1.98%**) | 11,398 (**6.58%**) |
| P03 c0 | 172,494 | 11,379 (6.60%) | 39,152 (**22.70%**) |
| P03 c1 | 172,332 | 20,628 (11.97%) | 47,609 (**27.63%**) |
| P06 c0 | 174,101 | 12,769 (7.33%) | 42,956 (**24.67%**) |

**原因(確定):** `planner._evaluate_candidates` の着地面判定が「**単一の**支持体に底面の 90% 以上が乗る」場合しか着地高さを上げていなかった。積付済み初期状態は典型的に「小さい箱が床に並んだ状態」(本スイートでは 0.26×0.26×0.26 のグリッド)であり、**どの1個の上にも 90% 乗れない**ため、既積み層の上面がまるごと使えない空間になっていた。到達高さ(最高到達点/コンテナ高さ)は 70〜90% に達しているのに体積利用率が 19〜25% しかない、という観測とも整合する。

### 2.2 修正

着地面判定を **skyline + union 判定** に置き換えた。

1. **pass1(着地高さ):** XY で少しでも重なる支持体はすべて「その上に乗るしかない障害」なので、重なる支持体の上面の最大値を着地上面とする(重なりゼロなら床)。
2. **pass2(支持の妥当性):** 着地上面と同じ高さ帯(`SUPPORT_LEVEL_TOL=0.02`)にある支持体だけを「接触している支持」として集計し、
   - 合計接触面積比 ≥ `MIN_SUPPORT_RATIO`(0.9) **または**
   - 合計接触面積比 ≥ `MIN_UNION_SUPPORT_RATIO`(0.55) **かつ** 接触領域の外接矩形が底面の各軸を `MIN_SUPPORT_SPAN_RATIO`(0.6)以上またぎ、接触面積の重心が底面中心から `MAX_SUPPORT_CENTROID_OFFSET`(半寸法比 0.15)以内

   のときのみ合法とする。後者の span/重心条件が「角にちょこんと乗る」不安定配置を排除する(接触面積比だけでは支持の偏りを判定できないため)。
3. 「同じ高さ帯に**優先/ソフト荷物**が含まれる」場合はハード禁止(下敷き防止)を維持。

**旧ルールに対する単調性:** 旧ルールで合法だった候補は新ルールでも合法(あるいは旧ルールでも実際には搬入経路/衝突判定で棄却されていた)であり、**合法候補の集合は真に拡大する**。旧ルールは「90%乗る支持体だけを見る」ため、より高い支持体との僅かな重なりを無視して床に着地させ、その後の衝突判定で棄却していた。新ルールはその候補を「高い支持体の上」に正しく持ち上げたうえで支持条件で判定する。

## 3. 副次的に判明した構造的事実：**本ローカル基盤では床直置きの荷物が fill_score に計上されない**

ターゲット2の計測中、`fill_counted_ratio`(配置済みのうち fill 集計に残った個数の割合)が 20〜30% しかないことに気づき追跡したところ、次の事実が確定した。

### 3.1 事実

`src/ground_handling/evaluator.py` の `calculate_fill_rate` は、静止後の8角点について各面の `dot` が `inclusion_margin` 以下であることを要求する。コンテナの面0は **内床面**(法線 `(0,0,-1)`、代表点 z=`thickness`)であり、この面の dot は

```
dot_floor = -(荷物の底面z - 内床面z)
```

となる。荷物が床に直置きされていれば底面z = 内床面z なので **dot_floor ≈ 0**。一方 `env.py` は Evaluator に **validator と同じ `inclusion_margin = -0.005`** を渡している(`configs/sample_config.json` を含む配布 config はすべて -0.005)。したがって `0 > -0.005` となり、**床に直接乗っている荷物はすべて「内包していない」と判定され fill から除外される**。

**直接検証:** 既積み6個(全て床置き)だけの初期状態で `Evaluator.calculate_fill_rate` を呼ぶと、

```
fill of prepacked-only state = 0   excluded items = [1000,1001,1002,1003,1004,1005] / 6
```

**fill_score = 0.00、6個すべて除外**。実行ログ上の `item N not inside (hit boundary plane), [1.2e-05, -0.85, ...]` は、いずれも第1成分(=床面)だけが ≈0 で他は大きく負、という同じパターンを示す。

`planner` は目標zを支持面から `REST_CLEARANCE=16mm` 浮かせて置くが、配置後の物理演算(`settle_wait_step=300`)で荷物は必ず支持面まで落ちるため、この 16mm は fill 集計時には残らない。

**含意:** 本ローカル基盤の `fill_score` は実質「**他の荷物の上に積まれた体積**」しか計上しない。床面の第1層は「積み上げの土台」としてのみ価値を持つ。

### 3.2 ただし本番基盤で同じとは限らない(重要な留保)

README「評価指標」には **『内包判定は検証時よりも緩く設定されている』** と明記されており、`Evaluator.__init__` の既定値も `inclusion_margin = 0.01`(正値=緩い)である。つまり **本番基盤の fill 判定は margin が正値で、床直置きも計上される可能性が高い**。配布ハーネスの `env.py` が validator の -0.005 をそのまま Evaluator に渡しているのは、ローカル確認用の簡略化(あるいは不整合)と考えられる。

そのためこの事実は、**「本ローカル指標を最大化する方向」に目的関数を書き換える根拠にはしなかった**。実際、本フェーズでは一度 risk 評価を「沈降後の姿勢」で行う実装(床置きの期待fill=0)を入れたが、**Phase10 が特定した「ローカル代理指標への過適合」を繰り返す**と判断して撤回した(commit `fe7c776`)。採用した union 支持面の変更は、床置き価値の仮定に依存せず「置ける個数・体積そのもの」を増やすものである。

### 3.3 Phase12 への申し送り(検証案)

1. **本番 margin の同定:** 提出フィードバックの `fill_score` と、ローカルで `inclusion_margin` を -0.005 / +0.01 / +0.02 に振って測った fill を突き合わせる。同一エージェントで local(-0.005) と local(+0.01) の fill 差は大きい(本フェーズの実測では `fill_counted_ratio` が 2〜3割 ⇔ ほぼ10割の差)ため、**どちらのレジームかは1回の提出で判別できる**。
2. 本番が **緩い(正値)** なら:現行の目的関数のままでよい。fill は「置いた体積」に比例するので、伸ばすべきは配置個数=搬入経路の詰まり(`fail_transport_y`)の解消。
3. 本番が **厳しい(-0.005)** なら:`z_term = -world_z * 12.0`(低い位置を強く選好)は fill に対して**逆効果**であり、積み上げを選好する方向へ重み再配分するだけで fill が大幅に伸びる余地がある(本フェーズの union 化だけで既に fill が大きく動いたのは、積み上げ可能性が増えたためである)。cog とのトレードオフになるが、Phase10 の重み推定では cog の寄与は +0.48pt/pt と小さい。
