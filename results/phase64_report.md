# Phase64 報告: plan()がNoneを返す局面に、本当に合法解が存在しないか

## 結論(先出し)

**27件中18件で、実際に合法解(内包判定 かつ legal1×legal2)が存在した。**
残り9件は存在しなかった。**「本当に詰んでいる」わけではないケースが過半数を超える。**
さらに、合法解が存在した18件を含む全27件で、`planner.plan()`に予算を桁違いに
増やして(実消費の最大でも1e15分の4300万=0.000004%)再実行しても**1件も
見つからなかった。予算不足が原因ではないことが確定した。**

---

## 実装(1-1)

`tools/phase64_exhaustive.py`(新規、読み取り専用)。

- 対象: Phase61-63で確認した27件のis_valid sudden death直前のobservation
  (Phase62では未保存だったため、本ツール内でエピソードを再現し死亡直前の
  observationをその場で取得する形にした——Phase61-63と全く同じ乱数シード・
  同一手順なので、得られるobservationはPhase61-63で観測したものと同一)。
- 探索範囲: プール内の**全アイテム**(item_idxを0に固定しない)・
  `planner._unique_orientations`が返す**全ユニーク向き**・**全コンテナ**・
  **5mm刻みのxyグリッド**(planner既定のBASE_GRID_DENSITY=2相当≈30mm間隔、
  RETRY_GRID_DENSITY=4相当≈15mm間隔より十分に細かい)・
  **床、および各既配置荷物の上面(+REST_CLEARANCE)** をzとして列挙
  (該当xyがその荷物のfootprintと重なる場合のみ)。
- 判定: **新しい判定式は書いていない。** `geo.check_inclusion_batch`
  (`INCLUSION_MARGIN`既定値、validator.check_inclusionと同式)と
  `agents.mysolver.agent._fallback_transport_legal`(Phase63で追加済み、
  `planner._collect_obstacles`・`planner._apply_obstacle_filters`をそのまま呼ぶ
  legal1×legal2判定)をそのまま呼んだ。plannerの支持品質要求
  (MIN_UNION_SUPPORT_RATIO等)は意図的に課していない
  (それ自体が原因かどうかを切り分けるため)。
- 副次チェック: `planner.plan()`に極端に大きい`SearchBudget`(limit=1e15、
  `hard_deadline`なし)を渡して再実行(判定式は一切変えず、予算だけ変更)。

## 1-2・1-3・1-4: 実測結果

### 合法解の有無(27件全て)

| | 件数 |
|---|---:|
| 合法解が存在した | **18 / 27** |
| 合法解が存在しなかった | **9 / 27** |

### 予算チェック(全27件)

| | 結果 |
|---|---|
| `planner.plan()`(予算1e15、実質無制限)で見つかった件数 | **0 / 27** |
| 実消費ユニット数 | 最小 1,579,906 / 最大 42,567,276 / 平均 10,005,484(limit比 最大でも0.0000043倍) |
| `budget_exhausted()` | 全件False(予算を使い切る前に探索が終わっている) |

**合法解が存在した18件を含め、予算を実消費の2,300万倍(1e15/42.5M)にしても
`planner.plan()`は1件も見つけられなかった。予算(SearchBudget)は原因ではないと
確定できる。**

### 合法解が見つかった18件の傾向(1-3)

- **z源は345件のサンプル全てが`item_top`(既配置荷物の上)。床(floor)は0件。**
  死亡局面では床付近の空きは既に尽きており、残る余地は「既配置荷物の上」にしか
  ないことを示す。
- **plannerの実際の候補グリッドとの距離**(同一item/orientation/containerに対し
  `planner._candidate_xy`が実際に生成する点集合との最短距離):

  | | BASE_GRID_DENSITY(≈30mm間隔) | RETRY_GRID_DENSITY(≈15mm間隔) |
  |---|---:|---:|
  | 最小 | 1.14mm | **0.18mm** |
  | 中央値 | 11.96mm | 6.21mm |
  | 平均 | 11.64mm | 5.92mm |
  | 最大 | 21.18mm | 10.94mm |

  **中央値がグリッド間隔の半分未満に収まっており、最小値0.18mmは実質的に
  plannerが生成する候補点そのものと同一の位置である。** つまり多くの発見位置は
  「グリッドが粗すぎて生成されなかった座標」ではなく、「plannerがほぼ同じ座標を
  候補として生成していた可能性が高い座標」である。
- 向き: 0番(160件)を筆頭に6方向全てで発見(特定の向きに偏ってはいない)。
- アイテム: 特定の1アイテムに偏らず、複数アイテム(item_index 2,4,7,10,11,17,
  19,36,46,55等)にまたがって発見された。

### 合法解が見つからなかった9件(1-4)

| シーン | 死亡時点のpool_list件数(可視窓) | 評価combo数 |
|---|---:|---:|
| A04_2c_80_noprio | 1 | 90 |
| A07_1c_40_bulky | 1 | 40 |
| A08_2c_140_extreme | 1 | 72 |
| D01_A_1c_40_softheavy | 1 | 100 |
| D03_A_2c_60_prioheavy_cont | 1 | 118 |
| D05_A_1c_40_tall | 1 | 56 |
| P06_A_1c_pre12_dense | 1 | 118 |
| **B04_2c_80_noprio** | **10** | **1674** |
| **C02_2c_55_shelfprio** | **5** | **690** |

**9件中7件は、死亡時点で可視プール(`pool_list`、ストリームの可視窓であり
残全アイテム数ではない)が1件しかなかった。** この1件についてのみ全向き・
全コンテナ・全xy・全z源を尽くしても合法解が無かった——荷物が大きすぎる、
または残っている空間の形状と合わないことが幾何的な理由として考えられる
(具体的にどちらかまでは本フェーズでは特定していない)。
**B04・C02の2件は可視プールに複数(5〜10)件あり、評価combo数も690〜1674と
多いにもかかわらず1件も合法解が無かった。** こちらは「たまたま最後の1個が
入らない」より踏み込んだ、より強い「詰み」の証拠である。

## 2. 判定

### (2-1) 合法解が存在した18件: plannerのどこを直せば見つけられるか

**総当たりの事実として言えるのはここまで:**

1. 予算(SearchBudget)は原因ではない(上記のとおり実測で確定)。
2. グリッド密度(BASE/RETRY)が主因である可能性は低い——見つかった座標の多くが
   plannerの実際の候補点のごく近く(中央値6〜12mm、最小0.18mm)にあり、
   「そもそも探索していない座標」というより「探索範囲のすぐ近く」である。

以上2点を消去法で除くと、残る説明は「plannerの候補生成・足切りロジックのどこかが、
内包判定・搬入経路判定を満たす候補を、別の理由で候補集合から除外している」
という**構造の存在**までであり、**どの具体的な関数・条件がそれに当たるかは
本フェーズでは特定していない**(仮説を立てて決めつけないという指示に従い、
未検証のまま候補名だけを列挙するに留める: `_evaluate_candidates`内の
支持品質要求(MIN_UNION_SUPPORT_RATIO/_STRICT)、Y方向の層規律
(`_apply_y_active_filter`のy_active_lo制限)、優先コンテナのtier分離ロジック、
のいずれか、または組み合わせ)。次フェーズでこれらを1つずつ直接検証することを
推奨する。規模は「原因を特定した後の修正」自体は関数1つ分の条件緩和程度で
小さいと見込まれるが、**特定作業(このうちどれが真因かを切り分ける調査)に
このフェーズと同程度の時間(1時間前後)がかかる**と見積もる。

### (2-2) 合法解が存在しなかった9件: レバーを閉じる

**このレバーを閉じる。** 7件は可視プールが1件だけの局面で、その1件がどの向き・
どの位置・どのコンテナにも収まらなかった。B04・C02の2件はより広い探索でも
0件であり、genuinely「詰んでいる」局面だと判断する。これらのケースについては、
`_fallback_place_pos`側の改善(Phase63)・`planner.plan()`側の改善のいずれでも
救えない。残る選択肢は選択肢:

- これらのケースを未然に防ぐ(その局面に至る前の配置順序・空間利用を改善し、
  「最後の1個が入らない」状況自体を減らす)という、より上流(offline optimize・
  online policyの配置戦略全体)の課題として扱う。
- 実利得の見積もり: 27件中9件(33%)が「本当に詰んでいる」——足切り(Phase61)や
  X方向搬入経路(Phase61)と同様、**このレバー単体を最後まで詰めても上限は
  27件中18件(67%)にとどまる**ことを、次フェーズの投資判断の前提として記録する。
