### ステップ1: 再現性の確認

| 2 | `[38, 0, 6, 26, 7, 33, 21, 25, 1, 19]` | 12.01s |
| 3 | `[38, 0, 6, 26, 7, 33, 21, 25, 1, 19]` | 11.72s |
| 4 | `[38, 0, 6, 26, 7, 33, 21, 25, 1, 19]` | 11.74s |
| 5 | `[38, 0, 6, 26, 7, 33, 21, 25, 1, 19]` | 11.74s |

**5回とも完全に同一の値・ほぼ同一の所要時間(11.7〜12.0s)。** 判定基準に照らし
「5回とも新しい値→決定的だが基準値が変わった」に該当。過去(Phase41〜48)の記録
(`first10=[13, 37, 28, 35, 22, 15, 25, 32, 29, 7]`、所要時間は当時11.4〜16.5s台で記録)
とは値が異なるが、いずれも**現行の壁時計上限(30×1.4=42s)より大幅に短く**、
両時代とも「探索がユニット予算を自然に使い切って終わった」結果に見える
(=壁時計での打ち切りではなさそう、という点はステップ2で直接検証)。

### ステップ2: 壁時計律速の検証

**(2-1) `MYSOLVER_HARD_WALL_FACTOR=100`でA03を実行**:

```
[A03] first10=[38, 0, 6, 26, 7, 33, 21, 25, 1, 19] (11.88s)
```

**過去の基準値に戻らなかった。** FACTOR=100(実質無制限化)でも新しい値のまま、
所要時間もほぼ変化なし(11.88s、既定FACTORの11.7〜12.0sと同水準)。

**(2-3) 他の壁時計定数も外して再試行**
(`MYSOLVER_HARD_WALL_FACTOR=100` + `MYSOLVER_POLICY_HARD_WALL=3000` +
`MYSOLVER_REPLICA_RUN_ORDER_HARD_WALL=3000`):

```
[A03] first10=[38, 0, 6, 26, 7, 33, 21, 25, 1, 19] (11.83s)
```

**これも変化なし。** `bp_check.sh`が直接呼ぶ`build_order()`は`POLICY_HARD_WALL`
(policy()呼び出しの壁時計、online実行時のみ関与)・`REPLICA_RUN_ORDER_HARD_WALL`
(replica.py経由、`REPLICA_SELECT=0`既定では未使用)のどちらの経路も通らないため、
コードを読む限りでも無関係と判断でき、実測もそれと整合した。

**CPU競合の確認**: `ps aux`でCPU使用率上位を確認したところ、他の重い計算プロセスは
無く、`load average 2.09/2.10/1.94`(8コア中)は特筆すべき高負荷ではなかった。加えて
5+2+2=9回の実行がすべて11.7〜17.3s台で安定しており(シーンごとにばらつきはあるが
同一シーンでの回ごとのばらつきは小さい)、**一時的なCPU競合による揺らぎという説明とも
整合しない**(競合なら値が振れるはずだが、A03は毎回寸分違わず同じ新しい値)。

**結論: 4つの壁時計定数(LIMIT/FACTOR/POLICY_HARD_WALL/REPLICA_RUN_ORDER_HARD_WALL)を
すべて外しても、CPU競合の兆候も無い状態でも、A03の値は変わらなかった。壁時計律速
仮説(Phase39由来、本フェーズの最有力仮説)は否定された。**

### 副次的に確認した候補要因: BLAS実装の相違(未確定)

`env_snapshot.txt`(Codespaces記録)は`numpy.show_config()`で
`"openblas configuration": "OpenBLAS 0.3.33.112.0..."`を報告しているが、この
`.venv`の`numpy.show_config()`は`"name": "accelerate"`(Apple Accelerateフレームワーク)
を報告する——`docs/migration_to_mac.md`が当初から警告していたリスクが実際に
起きていることを確認した。ただしこれは**Codespaces環境との相違**であり、
「同一Mac上でPhase41〜48とPhase49〜50の間に何が変わったか」を直接説明しない
(この`.venv`のBLASがセッションの途中で変わったとは考えにくい)。**候補要因として
記録するが、A03の値がいつ・なぜ切り替わったかの直接証拠は無い。**

### ステップ3: 基準値の再固定

**原因は特定できなかった**(壁時計律速は明確に否定、BLAS相違は確認したが直接の
引き金は未証明)。指示(3-3)に従い、**これを最重要の未解決事項として記録する。**

一方で、指示(3-1)の「bp_check.shが自動照合できる形」自体は、原因不明であっても
**今回時点の値を機械可読な基準として固定し、以後の変化を検知できるようにする**
目的で実施価値があると判断し、以下を行った:

- `scripts/bp_baseline_8scenes.json`(新規)に、決定的8シーンの`build_order()`出力
  (全要素、参考`optimize_time`込み)を記録。取得日2026-08-18、取得条件は
  `MYSOLVER_HARD_WALL_LIMIT=3000`・FACTOR/UNITS_PER_SECは既定・`time_budget=30.0`。
  **A03のみ`status: "unresolved"`とし、Phase41-48の`first10`(全40要素の記録は
  そもそも存在しないため捏造せずNoneのまま)を参考情報として残した。**
- `scripts/bp_check.sh`を更新し、このJSONと**自動照合**するようにした。
  `status="stable"`の7シーンは不一致なら`exit 1`(以後のA/Bへ進ませない安全弁)、
  `status="unresolved"`のA03は不一致でも警告のみに留める。
- `docs/migration_to_mac.md`を更新:
  - §3にFACTORが本検証条件では無関係だったことを訂正注記として追加。
  - §2にBLAS相違の実測確認結果を追記。
  - **§5.1(恒久ルール)に重大な訂正を追加**: 「同一マシン上は決定的」という
    Phase39由来の前提(D03の3回連続一致で実証)が、**A03のセッションをまたいだ
    ドリフトにより反証された**ことを明記し、「原因が判明するまでシーン単位の
    微小差分を変更の効果と断定しないこと」という運用上の注意を追加した。
  - §5.0を新設し、`scripts/bp_baseline_8scenes.json`の取得条件・自動照合の
    仕組みを明記(指示3-2相当)。

**`results/phase40_baseline_off_mac.json`(26シーン集計の対照)自体は取り直していない**
——指示(2-2)の「戻った場合」の分岐(FACTORを外した条件で取り直す)には該当せず、
原因不明のまま新しい26シーン計測を対照として確定させることは指示(3-3)の趣旨
(「原因不明のままA/Bを回してはならない」)に反すると判断したため。**今後26シーン
A/Bを回す前に、この一致しないA03問題の原因究明を優先すべきであり、この報告書を
次フェーズへの最優先の申し送り事項とする。**
