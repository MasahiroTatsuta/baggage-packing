  **Phase18 の教訓(部分集合の較正を信じない)が今回は「過小評価の見逃し」を防ぐ側に効いた**(§4.1)。

## 1. 背景:なぜ「候補の作り方」なのか

Phase20 と Phase22 の測定が同じ結論を指していた。

| 測定 | 値 | 含意 |
|---|---|---|
| Phase20: native regret | **1.14pt** | 見た候補の中では**ほぼ最良を選べている** |
| Phase20: 候補順序による実fillスプレッド | **19.19pt** | しかし順序の良し悪しの幅は非常に大きい |
| Phase22: 取りこぼし (c) のうち荷物選択の自由度由来 | **約7割** | online では原理的に取れず、順序側の問題 |

つまり **選び方(候補の取捨選択)は既に良く、作り方(候補の生成)が悪い**。
Phase20 で代理関数の較正は構造的に閉じ、ρ-test の天井も 1.14pt しかないと分かっているので、
残る打ち手は候補生成そのものの強化=貪欲構築のビーム化である。

## 2. 実装

### 2.1 `planner.plan_topk`:探索1回で上位k手を得る

素直に「上位k個の荷物選択を展開する」と `plan()` を k 回呼ぶことになり、1手あたりコストが
k 倍になる。これは **Phase22 §3.3 で実証済みの失敗**(1手あたりコストを増やすと予算内で
回れる組合せが減って逆効果)を繰り返すことになる。

`_search_best` は元々 (荷物 × 向き × 候補位置) を総当たりして argmax を取っているので、
**「荷物ごとの最良手」を控えるだけならコストはほぼゼロ**で済む。これにより
ビーム展開に必要な探索回数は **b×k 回ではなく b 回**になる。

`_search_best(top_k=)` は `top_k > 1` のときだけ荷物ごとの最良を辞書に控える。
`_evaluate_candidates` の呼び出し回数も rng の消費回数も変えないため、
**既定 `top_k=1` の経路は従来と1命令も変わらない**。

### 2.2 `simulate.beam_construct_order`:幅 b のビーム

各ステップで、ビーム内の各部分解について `plan_topk` で上位 k 手を展開し、
スコア上位 b 個を残す。設計上の要点は3つ。

1. **枝刈り基準と最終採否基準を一致させる。** スコアは
   `risk調整済み体積 − PLACEMENT_PENALTY_WEIGHT × 総容積 × placement違反率` で、
   `build_order` の目的関数と同一定義にした(重みは既存定数を流用し、
   **新しい調整パラメータは1つも増やしていない**)。
2. **多様性の維持。** 荷物集合と実際の姿勢を丸めたキーで重複排除する。
   詰めた順番が違うだけの同一状態でビームが埋まると実質 b=1 へ退化するため。
3. **遅延クローン。** 子のスコアも同一性キーも action だけから増分計算できるので、
   上位 b 個に絞ってから初めてコンテナを複製する(§3.2)。

打ち切りは `SearchBudget` のユニットで管理し、いつ打ち切られても
「それまでに構築できた順序 + 残りを末尾に付けた完全順列」を返す(anytime)。

### 2.3 予算配分:幅と試行回数のトレードオフ

幅 b のとき1構築あたりの探索量は b 倍になるので、**1リスタートの枠も b 倍**にした
(`construct_units = CONSTRUCT_SLICE × u × b`)。各ビーム状態が従来の貪欲1本と同じ計算量を
受け取り、その分**リスタート回数が 1/b に減る**。指示にあった
「b を増やすと予算内のリスタート数が減る」というトレードオフが、予算配分としてそのまま表現される。

### 2.4 b=1 の同一性(実装の正しさの担保)

| 検証 | 結果 |
|---|---|
| `greedy_construct_order` vs `beam_construct_order(b=1)` の順序一致 | **18/18 完全一致**(6シーン × window=20/全開放/ノイズ0.35) |
| 遅延クローンへの書き換え後の再検証 | **6/6 一致**(維持) |
| placement項追加後の再検証 | **6/6 一致**(維持) |
| b=1 の8シーン fill_strict が Phase22 ベースラインを再現するか | **8/8 完全再現** |

最後の項目は、`construct_units` を b 倍にする配線変更が **b=1 では何も動かしていない**ことの
裏づけになる。ノイズあり条件でも一致したので、rng の消費回数が変わっていないことも担保できた。

## 3. 実装中に潰した3つの落とし穴

### 3.1 `top_k=1` の戻り値型

`_search_best` は `top_k=1` のとき単一の dict(または None)を返す。`plan_topk` 側で
リスト化しないと **dict のキーを反復**してしまう。正規化を入れて解消。

### 3.2 子ごとのクローンが決定性を壊しかけた(最も危険だった)

初版は子を作るたびに `clone_containers` していた。これだと1ステップあたり
**b×top_k 回**の複製が発生する。**この複製費用はユニット予算に計上されない**ため、
b を上げると「ユニット的にはまだ余裕があるのに壁時計だけが膨らむ」状態になり、
非常用安全弁(`hard_deadline`)が発火して **Phase17 で確保した決定性が失われる**。

Phase22 §3.3 の失敗(コスト増が予算を食って逆効果)と同じ構図が、
今度は**決定性という別の経路**で現れるところだった。

子のスコアも同一性キーも action だけから増分計算できるため、
**上位 b 個に絞ってから初めて複製する**形に直し、複製を 1ステップ **b 回**に抑えた
(b=5 なら 25回 → 5回)。

### 3.3 ビームスコアの placement 項:入れたが構造的に不活性だった

初版のビームスコアは risk調整済み体積のみで、`build_order` の目的関数にある
placement ペナルティが抜けていた。掃引で **b=2 が D03 の placement を 92.86 に落とした**ため、
これが原因と考えて既存の `PLACEMENT_PENALTY_WEIGHT` を使って項を追加した。

**しかし再掃引の結果は1桁まで完全に同一だった。** 理由を追跡すると:
`plan_topk` は最初に `enforce_priority_container=True` で探索するため、
**構築中は「優先荷物を非優先コンテナへ置く候補」がそもそも生成されない**。
したがって構築中の違反率は常に 0 で、追加した項は枝の順位を一切変えない。

placement 違反は構築時ではなく、**その順序を online(pool=lookahead_k)で再生したとき**に
発生していた。つまり D03 の 92.86 は「ビームが体積目当てに優先コンテナを潰した」のではなく、
**b=2 が生成した順序が online 再生で単に劣っていた**ためである
(fill も 30.86 → 23.40 と悪化しており、トレードオフですらない)。

`enforce_priority_container=False` のフォールバック経路では効きうるため項自体は残すが、
**「効くはずだと考えて入れた修正が実測では不活性だった」**という事実をそのまま記録する。

## 4. 幅 b の決定

### 4.1 8シーンでの掃引(代表性を欠いていた)

| | b=1 | b=2 | b=3 | b=5 |
|---|---|---|---|---|
| fill_strict 平均 | 24.65 | **25.78** | 25.18 | 23.78 |
| fill_loose 平均 | 42.89 | 43.27 | 42.42 | 43.37 |
| placement 違反 | なし | **D03 92.86** | **なし** | **C02 85.71** |
| stability<97 | なし | なし | なし | なし |

平均では b=2 が最良に見えるが、**判定基準「placement/soft 全シーン満点」に抵触**する。
b=5 も C02 で 85.71。**制約を満たす b>1 は b=3 のみ**だった。

シーン別の振れは **+12.26 〜 −7.47** と極端で、D03 と C03 は b を増やすほど単調に悪化する。
Phase16/18/19 で繰り返し観測されている「探索パラメータは連続的なダイヤルではなく
**別の局所解へのスイッチ**として作用する」現象がここでも再現した。
したがって8シーン平均は信用せず、26シーンでの過適合チェックへ進んだ。

### 4.2 26シーンでの最終判定(b=3 採用)

| 指標 | b=1 | b=3 | 差 | 判定 |
|---|---|---|---|---|
| **fill_strict** | 23.74 | **25.68** | **+1.95** | **改善**(±0.90) |
| **fill_loose** | 36.65 | **39.13** | **+2.48** | **改善**(±0.90) |
| cog_score | 65.69 | 62.83 | −2.86 | 悪化(±0.67) |
| stability_score | 98.30 | 98.23 | −0.07 | ノイズ内 |
| placement_score | 100.00 | 100.00 | ±0.00 | 満点維持 |
| soft_item_score | 100.00 | 100.00 | ±0.00 | 満点維持 |

主な改善シーン: A03 +11.77 / P01 +11.08 / D04 +9.40 / A05 +8.86 / D02 +7.91 /
P02 +5.89 / P03 +5.79 / C02 +5.32 / C01 +4.72 / P05 +4.55 / A07 +4.38。
主な悪化シーン: **D01 −14.78** / D03 −7.55 / C03 −7.38 / A08 −5.86 / P06 −1.16。

**8シーンの掃引が +0.53 だったのに26シーンでは +1.95 になった。**
掃引の部分集合に敗者(D03/C03/A08)が偏って含まれており代表性が無かったためである。
Phase18 では「部分集合で良く見えた変更が26シーンで崩れる」形でこの教訓が効いたが、
今回は逆に**「部分集合で過小評価していた変更を取りこぼさない」形で効いた**。

**採点モデルでの純効果:**

```
Δpublic ≈ 0.6 × (+1.95) + 0.1 × (−2.86 + (−0.07) + 0 + 0)
        = +1.164 − 0.293
        = +0.87 pt
```

cog の −2.86 は禁止事項にある「cog と fill の意図的なトレード」ではなく、
**積み上げが増えたことの副作用**である(重心が上がるのは体積利用率が上がる以上避けられない)。
fill の寄与が cog の損失の4倍あり、net は明確にプラスなので採用する。

**制約の確認:** placement/soft は全26シーンで 100.00。stability は平均 98.23、
個別最小 **97.43**(97未満は0件、調査基準の96.5も大きく上回る)。
26シーン全てでエラー・タイムアウトは発生せず(status は正常終了25件+完全積載1件)、
シーン最大実行時間は 78.7 秒だった。

## 5. 中間KPI:(c) の再測定(部分達成、かつ描像の訂正)

Phase22 の `tools/phase22_void_audit.py` を b=3 で再実行した。

| 指標 | b=1 | b=3 | 差 |
|---|---|---|---|
| **置けた体積** | 54.327 m³ | **56.823 m³** | **+2.496** |
| 　= 体積利用率 | 37.8% | **39.5%** | **+1.7pt** |
| 配置個数 | 574 | **592** | **+18** |
| **(c) 取りこぼし** | 6.932 m³ | **6.421 m³** | **−0.511** |
| 　= fill換算 | 4.82pt | 4.46pt | −0.35pt |
| (c)適用後の空き | 79.499 m³ | 77.298 m³ | −2.201 |

**置けた体積は狙いどおり大きく増えた(+2.496 m³)。** これが fill_strict 改善の主因である。

**一方 (c) は 7% しか縮まなかった。** ここが当初の描像の訂正点である。
Phase23 の作戦は「(c) = 6.932 m³ という取りこぼしを順序側で回収する」というものだったが、
実際には **(c) は汲み出せば減る固定の貯蔵量ではなく、より多く積んだ新しい行き詰まり状態で
同じくらい再生成される**。(c) は「その状態からもう一段強い探索をすればまだ置ける量」という
**状態依存の量**であって、在庫ではない。

シーン別に見てもこの性質が確認できる。A05 は (c) 1.117 → 0.729 と縮みつつ置けた体積が
+1.21 増えた(狙いどおり)一方、A08 は (c) が 0.664 → **1.130 と増え**、置けた体積は
−0.55 減った(悪化シーン)。**(c) の増減と置けた体積の増減は連動していない。**

したがって中間KPIは「置けた体積の増加」は達成、「(c) の縮小」は限定的、と評価する。

**副次的な確認:** fill_strict +1.95 のうち、置けた体積の増加で説明できるのは
`0.63 × 2.496/143.855 × 100 = +1.09pt` である。残り +0.86pt は計上率の改善
(**0.629 → 0.650**)による。Phase21 で「計上率は独立に動かせるレバーではない」と結論したが、
これは「計上率だけを狙って動かすことはできない」という意味であり、
**積み方が変われば計上率も付随して動く**ことが今回確認できた(床層の相対比率が下がったため)。

## 6. 結論と次フェーズへの申し送り

### 6.1 確定したこと

1. **貪欲構築のビーム化(b=3)は有効。** 26シーンで fill_strict +1.95pt、
   採点モデル換算で public +0.87pt。全制約を維持。**採用**。
2. Phase20/22 が指していた「候補の作り方が悪い」という診断は正しかった。
   候補生成を広げるだけで、代理関数にも online 探索にも手を付けずに fill が動いた。
3. **(c) は在庫ではなく状態依存の量である。** 「取りこぼしを回収する」という描像は不正確で、
   正しくは「より良い順序を作れば置けた体積が増える」。

### 6.2 次にやるべきこと

1. **b とリスタート回数の配分の再検討。** 現在は「1リスタートの枠を b 倍」にして
   リスタート回数を 1/b に減らしている。b=3 が最良だったのは
   「幅3 × リスタート約1/3」の点だが、`CONSTRUCT_SLICE` 自体を下げて
   「幅3 × リスタート回数維持」に近づけられれば更に伸びる可能性がある。
   ただし Phase17 §3.5.2 で `CONSTRUCT_SLICE` と `FINAL_MARGIN` の関係に注意が要る。
2. **悪化5シーンの調査、とくに D01(−14.78)。** softheavy 分布で単独で大きく落ちており、
   ビーム化と相性の悪い条件がある可能性が高い。決定的なので再現・原因特定は容易。
3. **top_k と beam_width の分離。** 現在 `top_k = beam_width` で連動させているが、
   「幅は狭く候補は広く」(b=2, k=5 など)の組合せは未探索。
   ただし複数パラメータの同時変更は Phase19 §3.3 の「組み合わせの崖」に注意。

### 6.3 未解決の持ち越し

1. `gen_2containers_priority` の stability 制約違反(96.87 < 97、Phase17から未解決)。
   なお26シーンスイート側には該当シーンが無く、b=3 で 97未満は0件である。
2. 本番の内包判定レジーム(strict/loose)。Phase16 の n=1 の観測のみ。
