## 4. カテゴリ C: 順序探索

### C-1. フェーズ1優先(w3、✅ 採用)

`ordering.build_order()` のフェーズ1は、`window`(その時点の未配置荷物のうち体積上位N件だけを
1手の候補として見せる)を変えた**決定的リスタート**を順に試します。

`window` の意味:
- 小さい → 近視眼的。大きい荷物を律儀に上から処理する形に近づく
- `None` → 制限なし。幾何的に最も都合の良い1手を選べるが、小さい荷物で隙間を
  食い潰して後続の大物の置き場を狭める「トンネルビジョン」のリスク

| 設定 | 本数/秒 | public |
|---|---|---:|
| baseline | 5本 | — |

### C-2. `ordcount` — 目的関数の入れ替え(✅ 採用)

**本セッションで見つけた構造的なズレ**です。

```python
# 変更前 (ordering.py)
def _better(candidate, current):
    """(placement込みの調整体積, 配置数) の辞書式比較。体積を主指標、配置数は同点タイブレークのみ。"""
    return candidate > current
```

`validate()` は `(risk_adjusted_volume − penalty, count)` を返し、**体積が第1キー**でした。
根拠コメントは Phase10 期の「fill が public を支配していた」という当時の理解に基づきます。

しかし本番5提出(wallmode 除く)の相関は:

```
public vs num_placed_items = +0.980
public vs fill_score       = −0.984   ← 完全な逆相関
```

fill 最高の sup_mid(39.84)が public 最下位級(59.97)、fill 最低の L3(38.97)が最高(60.82)。
**得点のゲートは個数ベースの足切りであり、fill は足切りを生き延びる側＝レバレッジが
最も低い指標**です。Phase70 が変えたのは*測定KPI*であって、ソルバ自身の目的関数では
ありませんでした。

辞書式を **(配置数, 体積)** に入れ替え → public **+0.27**。
ローカルは +37個(+2.51pp、改善6/悪化0)。

Phase18 が記録した「加算ペナルティにすると『何も置かない方が得』へ退化する」問題は、
最大化方向が逆なので構造的に起きません。体積は第2キーとして残るため同数なら従来どおり。

## 5. カテゴリ D: 構築規則の再定式化

### D-1. WBC (Wall-Building Constructor) — 15ラウンドでストップロス

Deep Research の回答「accessibility を一級市民として扱う = wall-building 再定式化」を
受けて実装。`exp/wallbuild` ブランチ、`agents/mysolver/wallbuild.py`、
設計と全ラウンドの記録は `docs/wallbuild_design.md`。

| ラウンド | 内容 | 結果 |
|---|---|---|
| v1 | 実装 + planner に `region=` 制約 | 3シーン smoke、baseline に −23 |
| v2-v8 | 座標系 / 壁カーソル / region クリップ / 薄い壁 / usable 判定 | 6シーン net −12 |
| **v9** | **`_overlap` の index バグ修正** | **v1〜v8 の全不振の主因**。`s[1] < box[3]`(x0とz0を比較)が正しくは `s[1] < box[4]`。`_split_space` がほぼ発火せず maximal space が数手で枯渇していた |
| v10-v11 | region の y 下限緩和 / `_pick_ref` を床優先へ | plan は 13-16手に。だが episode は baseline 以下 |
| v12-v13 | 壁内充填を X-Z skyline 2D packing に | `validate_planned_xy` が ~87% 拒否 |
| v14 | 着地z/支持を自前化 | placed=0(引数形式の不整合) |
| v15 | 全スロット候補を集め inclusion/transport を通る最初を採る | **episode 壊滅**(A01 23→7)。ストップロス発動 |

**構造的結論**: 「WBC の offline プランを plan-executor が実物理で replay する」段で必ず
崩れます。自前着地z ↔ 実沈降、skyline 支持 ↔ 実支持の乖離が埋まらず、しかも縮退先の
全域貪欲が壁を壊して連鎖死。**密に詰めるほど replay で崩れやすい**という袋小路でした。

本当に効かせるには online policy 自体を wall-building にする(offline plan を捨てる)
必要があり、それは plan-executor の設計全体の作り直し = 数週間規模です。

### D-2. 層規律(Y方向)

```python
Y_SLICE_COUNT = 2
```

コンテナを Y方向に分割し、「奥側から level+1 個分の層」だけを合法候補の対象にします。
その層内で合法候補があればそれで確定し、手前の層は開放しません。
**最終 level は全開放**なので、真の行き詰まりの挙動(None を返す)は変わりません。

| `WALL_MODE`(荷物寸法から適応的に分割数を決める) | public **57.400(−3.42)** |

### D-3. floor-first(Z方向の規律) — ローカル no-op

3Dリプレイで「床占有率が全シーン最大54%、大半は32〜40%止まりなのに、進捗25%時点で
最大到達高さが 1.0〜1.4m(天井1.61m)に達している」ことを実測。

```
scene                 進捗   maxZ   床占有%
C02_2c_55_shelfprio   25%   1.39    17.3
A05_2c_80_prio        25%   1.13    22.5
A08_2c_140_extreme    25%   1.01    31.0
A06_1c_40_small       25%   0.47    26.9   ← 唯一の完走シーンだけ低い
```

`MYSOLVER_FLOOR_FIRST`: `_evaluate_candidates` で「床着地の候補が1つでも合法なら
床に限定、無ければ従来どおり」。既存のY層規律と同じ「最終段で全開放」の型なので
**実行可能集合は狭まらず、探索コストの増加もゼロ**(既に計算済みの `on_floor` で
`legal` をマスクするだけ)。last-resort では適用しません。

**結果: 786 → 785(−1)、26シーン中25シーンで挙動が変わらなかった。**

**⇒ ソルバは既に床候補があれば床を選んでいた。床占有の低さは「床を後回しにしている」
からではなく「残った床に到達できない」から。塔化は症状であって原因ではない。**

### E-3. `forbidden_hit` — 38軸で唯一 A/B されていなかったハード制約

```python
forbidden = (sup_prioritized and not item_is_prioritized) or (sup_soft and not item_is_soft)
support_ok = on_floor | (stacked_ok & ~forbidden_hit)
```

Phase9 の設計判断は「優先荷物・ソフト貨物の『下敷き』を**評価スコアに任せず**、
候補生成の段階で**ハード制約**として回避する(置く順序に関わらず下敷きは発生しない)」。

- **env フックが存在しない** = 探索の全期間で一度も A/B されていない
- Phase66 のコミットメッセージ: 「ステップ2向けに用意していた**env化フックは未使用のため
  差分から除去し**」 — フックを書いた上で、未検証のまま削除していた
- ブール式の構造上 `forbidden_hit=True` は `stacked_ok` に関わらず恒久的に `False` になる
  ため、**閾値をどう動かしてもこの分は1件も救えない**

**守っているスコアの経済性**: `placement_score` と `soft_item_score` はどちらも
`100 × (1 − 違反数/配置数)` で、しかも**足切りで0にされる側**です(`_CUTOFF_METRIC_KEYS`)。
1シーンあたりの合成寄与に換算すると **跨ぎ1回 = +2.75pt / soft違反1回 = −0.19pt(14:1)**。

つまりこの制約は、**全指標のゲートである配置個数を犠牲にして、ゲートを割れば0になる
2指標を守っていた**構造でした。

### E-5. なぜ下振れが構造的に無いか

### F-1. 左ポケットの封鎖(コンテナ長の22%)

全シーン・全コンテナで**左端が空**でした。最終状態の X 分布(左→右10分割):

```
A08 コンテナ0: [0, 0, 0, 1, 3, 0, 0, 4, 2, 0]   ← 左30%が完全に空
A08 コンテナ1: [0, 0, 0, 3, 1, 0, 0, 5, 0, 0]
A05 コンテナ1: [0, 2, 0, 7, 0, 0, 2, 8, 0, 0]
A01 コンテナ0: [0, 3, 0, 8, 1, 1, 6, 1, 5, 2]
```

原因は `geo.transport_x_bounds` が搬入スポーン x の下限に `cut_x` を**全高一律で**
加算していたことです。

```python
x_min = -length/2 + thickness + cut_x + half_x + START_MARGIN + ox
```

L=2.0 / cut_x=0.44 なら x_min ≈ −0.36、左内壁は −0.81。
**この差 0.45m が「スポーンできずスライドでしか入れない袋小路」。**

封鎖の実証(空コンテナに1個置いて到達可能点を数えた):

```
空のコンテナ                 左ポケット到達可能 9/9
ポケット入口(x=-0.20)に1個    左ポケット到達可能 0/9   ← 33点中21点が同時に死ぬ
中央やや右(x=+0.30)に1個      左ポケット到達可能 9/9
```

**1個置くだけで恒久封鎖されます。** そしてヒストグラムの bin 3〜4 がまさにその入口で、
ソルバは自分で蓋をしていました。

### F-2. 切り欠きの向き(記録の訂正)

実機のコンテナ面データ:

```
斜め面の法線  n = [−0.673, 0, −0.740]     代表点 p = [−0.96, 0, 0.418]
```

X も Z も負 = **切り欠きは左下の角**です。x = −0.70 での内包判定は z<0.42 が×、
z≥0.45 が OK。`utils.write_open_cut_corner_cup_obj` の断面ポリゴンは
`[[cut_x,0],[width,0],[width,height],[0,height],[0,cut_y]]` で原点側の角を削ります
(docstring の「左上角」は回転前の座標系での記述)。

### F-3. 修正の失敗

下限を `cutcorner_boundary_x` で切り欠き平面から高さごとに解析的に計算する版
(`MYSOLVER_TRANSPORT_X_BY_HEIGHT`)を実装。効果は意図どおり出ました:

```
従来の一律下限 x_min = −0.370(全高共通)
sweep_z=0.4 → −0.662 / sweep_z≥0.6 → −0.810(左内壁まで全開)
```

**だが 26シーン A/B は壊滅: 786 → 469(−317)、悪化17シーン、C02 は 43→1。**
fill 28.23 → 17.04。26シーン中25シーンが `is_valid` で即死。

**⇒ `+cut_x` の一律下限は過剰な保守ではなく、必要な制約でした。**
最も整合する説明: 切り欠きが**左下**にあるため斜面は右下→左上に立ち上がっており、
荷物は `START_Z` で持ち上げてから降下する以上、**左側で降下すると斜面を貫く**。
本モデルは掃引高さでの1点と最終位置しか見ておらず、降下経路を判定していません。

## 9. 測定手法の教訓

### 9-1. ローカル→本番の転移率は予測に使えない

| 手 | ローカル配置率増 | 本番配置率増 | 転移率 | public |
|---|---:|---:|---:|---:|
| last-resort | +1.29pp | +1.88pp | **1.46** | +2.33 |
| ordcount | +2.51pp | +0.51pp | **0.20** | +0.27 |
| oc_cf | +4.47pp | **−0.40pp** | **−0.09** | +0.05 |

**ローカル増分が大きいほど転移率が悪化 = 26シーンへの過適合。**
oc_cf でローカル最大だったシーンは C02 +11 / C03 +8 / A05 +7(いずれも2コンテナ優先・
棚系)で、本番シーン集合ではこの系統が手薄だと推測されます。

**符号は3回中2回転移しましたが、幅は7倍ぶれました。** 以後ローカル A/B は
「壊れていないことの確認」にのみ使い、採否は機序の妥当性と本番実測で決めています。

### 9-2. 採否基準の変遷

| 期 | 基準 | 根拠 |
|---|---|---|
| Phase10-69 | ローカル合成スコア | — |
| Phase70- | **`num_placed_items` を第一のローカルKPI** | ローカル合成スコアは足切りを実装しておらず本番の主効果(緩1の利得の98%)を検出できないと判明 |
| Phase89-90 | **+ 悪化シーン数の少なさ(頑健性)** | w3(悪化1シーン)は転移、w4(net+1だが2シーン大幅悪化)は本番で符号反転 |
| Phase96- | **提出判断には適用しない** | 提出は1日5回でき、枠を消費するのは選択期限。頑健性ゲートは最終枠の選択にのみ適用 |

### 9-3. 「実行可能集合の拡大」だけが効く

| カテゴリ | 本数 | 結果 |
|---|---:|---|
| **実行可能集合の拡大** | 1 | **+2.33** |
| 再ランク付け(定数・重み・種・候補順位・リスタート選択) | 15+ | 最良 +0.27、最悪 −5.19 |

90フェーズ磨かれたヒューリスティクスは局所最適に近く、上書きすると負けます。
一方で実行可能集合は、検証されたことのないハード制約で人為的に狭められていました。

**ただしこの法則にも例外があります**: `PRIORITY_CLEARANCE` の解除(実行可能集合の拡大)は
−0.12、`transport_x_bounds` の高さ依存化(同)は −317個で壊滅しました。
**「広げれば効く」ではなく「広げた先が本当に合法か」が決め手**です。

### 9-4. 禁止事項(運営規約)

運営が**評価関数のパラメータ解析を NG と明言**しています(`docs/submission_policy.md` §4、
Phase61 追記)。したがって:

- 各指標の重みを提出結果から逆算しない
- 足切り閾値そのもの(何個で発動するか)を逆算しない
- ρ-test 診断ビルド(スコア関数を探る目的の提出)は**断念確定**、以後再開しない

複数の仮説を並べた感度分析(§8)は、閾値を特定せずに意思決定するための手段として

## 10. 提出枠の方針(2026-09-09 変更)

それ以前の方針は「2枠目を主枠と独立した故障モードを持つ保険にする」(rest020、55.96)で、
これは**主枠を守ることに価値がある**ことを暗黙の前提にしていました。

目標が銅メダル(≒60)である以上、60に届かなければ 58.5 も 55.96 も等しく圏外であり、
この前提は目的と整合しません。

**目的関数を E[選択されたスコア] から P(max(枠1, 枠2) ≥ 目標) に変更**し、
2枠目は保険ではなく最も分散の大きい信用できる賭けに充てます。

あわせて **提出は希少資源ではない**ことを明確化しました。SIGNATE は1日5回投稿でき、
締切まで約165回の提出が可能です。**枠を消費するのは選択期限(2026-10-12)であって
提出ではありません。** Phase91 までの文書が「本番提出1枠を消費する」と書いていたのは、
最終枠を守るための基準を提出可否の判断にまで適用した過剰な保守でした。
