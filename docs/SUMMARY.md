## 1. 課題

ロボットが手荷物をコンテナ(ULD)へ積み付けるシミュレーションです。3Dビンパッキングに
**搬入経路の制約**と**物理シミュレーション**が乗ったもので、これが難しさの中心にあります。

### エージェントが実装する2つの関数

| 関数 | 呼ばれ方 | 制限 |
|---|---|---|
| `optimize(item_list) -> list[int]` | 開始時に1回。全荷物の**完全順列**を返す | 180秒 |
| `policy(observation) -> action` | 毎ステップ1個ずつ配置 | 8秒/手 |

`policy` は毎回別プロセスで生成されるため、**内部状態を持てません**。毎回 `observation`
から状態を再構築する設計が必須です。

### 3つの出題パターン(公式資料より)

- **パターンA**: EBS(Early Baggage Storage)で事前並べ替えあり。`optimize()` が全荷物の
  順序を一括計算する
- **パターンB**: 事前並べ替えなし、ただし常時20個程度がストックされ、その中から自由に選べる
- **パターンC**: 並べ替えなし。到着順に1個ずつ。**観測可能数は1個**

ローカル26シーンの `look_ahead` は 1 が17シーン、5 が4、10 が5。
**過半数が look_ahead=1** で、そこでは「どの荷物を置くか」の自由が無く、
`optimize()` が返す順序がすべてを決めます。

### 即エピソード終了(sudden death)

毎ステップ、以下を1つでも満たさないと**その場でエピソードが終わり、残り全荷物を失います**。

1. 形式(キー集合・範囲)
2. **内包判定** — 荷物が完全にコンテナ内にあるか
3. **搬入経路の干渉** — 荷物はコンテナ前面(y = −width/2)の上空に出現し、**+Y方向へ直進**
   してから**X方向へスライド**する。この**L字軌道**が既配置荷物・壁・棚に当たると失敗
4. **定着判定** — 目標へ置いて物理演算を約300ステップ進め、初期位置からのズレや傾き(>30°)
   が閾値を超えると失敗
5. タイムアウト(`optimize` 180秒 / `policy` 8秒)

### コンテナ形状

直方体に、**左下の角**が `cut_x × cut_y` で斜めに切り欠かれた五角形断面です。
実測した斜め面の法線は `n = [−0.673, 0, −0.740]`、代表点 `p = [−0.96, 0, 0.418]`。
棚(shelf)あり/なし、優先(is_prioritized)あり/なし、既積み(prepacked)あり/なしの
バリエーションがあります。

### 採点

`fill_score` / `cog_score` / `stability_score` / `placement_score` / `soft_item_score` /
`num_placed_items` の複合です。**重みは非公開**で、運営が評価関数のパラメータ解析を
NGと明言しているため、逆算は行っていません。

そして最も重要な要素が**足切り**です。公式仕様に「積み付けられた手荷物の**数**が一定数
以上にならないと、充填率(fill)以外は0点」とあり、**閾値は非公開**です。

## 3. ソルバの構造

`agents/mysolver/` 以下。

```
optimize() ─ ordering.build_order()
             ├ フェーズ1: 決定的リスタート(window = 15 / 25 / None の3本 × 各33.3秒)
             │   各リスタートは simulate.beam_construct_order で純幾何シミュを回し、
             │   結果を validate() = (調整済み体積, 配置数) で比較して最良を採る
             ├ フェーズ2: 乱数リスタート + RCL(上位30%シャッフル)
             │   ※26シーン中77%では一度も走らない(Phase87)
             └ build_plan(): look_ahead=1 かつ非棚・非既積みのシーンでは
                 全荷物の位置・向きまで確定したフルプランを作る

policy()  ─ agent.Agent.policy()
             ├ plan-executor: 計画位置が現在の実状態で合法ならそのまま実行
             ├ 不可なら planner.plan() の貪欲解へ縮退
             │   └ 合法手ゼロなら last-resort ラダー(後述)で救出を試みる
             └ それでも無ければ _fallback_place_pos() = 無検証の最終手段(ほぼ即死)
```

### 中核: `planner.plan()`

荷物1個ごとに候補位置(グリッド ∪ Extreme Point ∪ cutcorner サンプリング)を総当たりし、
`_evaluate_candidates()` が **内包・搬入経路(L字の2段掃引)・支持** を判定します。

```python
planner.py:1322   legal = base_legal & legal1 & legal2
```

`base_legal` に内包・天井・支持が、`legal1`/`legal2` に搬入経路のY掃引・Xスライドが
入っています。**搬入経路は候補の受理条件に最初から入っており**、後段で初めて検出される
わけではありません。

スコアは `fill + contact + support + back_term(奥選好、係数5.85) − corridor_penalty(通路、重み6.0)` 等。

### 決定性

壁時計ではなく `UNITS_PER_SEC` によるユニット予算で打ち切るため、**マシン速度に依存しません**。
同一条件の再実行はビット単位で完全に一致し、これは全フェーズで毎回検証しています
(`tools/phase63_determinism_check.py`、決定的8シーンの `action_digest` 突合)。

新機能はすべて環境変数でゲートし、**既定OFFで 8/8 ビット単位一致**を確認してから
初めて有効化します。

## 5. 転移可能な知見(これが最大の資産)

### (1) 足切りは階段関数である

last-resort の緩和レベルを 1 / 2 / 3 と上げて提出した結果:

| 版 | num_placed | public | placement | soft_item |
|---|---:|---:|---:|---:|
| 対照 | 0.6440 | 58.498 | — | — |
| Lv1 | 0.6498 | 58.498 | **63.3** | **66.0** |
| Lv2 | 0.6534 | 58.521 | **63.3** | **66.0** |
| Lv3 | 0.6628 | **60.824** | 67.4 | 68.85 |

配置数は単調増加なのに public は Lv3 で初めて跳ねました。決定的なのは
**Lv1 と Lv2 のサブスコアが小数まで一致**していること —— 両者は**同じシーン集合しか
足切りを通過していない**という意味です。

**⇒ 配置数の小さな改善は public に転移しません。跨ぐまで積んで初めて得点になります。**
これは Phase73 以降の多くの軸が「ローカルで net +数個」を追って全滅した理由の説明にもなります。

### (2) 足切りは本番シーンの約3割を0点にしている

本番のサブスコア実測値をローカル(足切り未適用)と比べると:

| 指標 | ローカル | 本番 | 比 |
|---|---:|---:|---:|
| stability | 98.04 | 77.16 | 78.7% |
| placement | 99.50 | 68.55 | 68.9% |
| soft_item | 100.00 | 70.20 | 71.3% |

足切りは cog/stability/placement/soft_item を0にし fill だけ残す仕様なので、
**この比がそのまま足切り通過率の推定になります**。

1シーンあたりの合成寄与に換算すると **跨ぎ1回 = +2.75pt / soft違反1回 = −0.19pt(14:1)**。
配置数を増やす施策とサブスコアを守る施策のトレードは、この比率で判断すべきです。

実際に last-resort はソフト荷物の下敷きを意図的に許可する実装ですが、本番の
`soft_item_score` は **+10.20 上がりました** —— 跨いだシーンが増えて「0点だった
soft_item が計上され始めた」効果が、シーン内の違反による減点を完全に圧倒したためです。

### (3) 実行可能集合を広げる変更だけが効く

| カテゴリ | 本数 | 結果 |
|---|---:|---|
| **実行可能集合の拡大** | 1 | **+2.33** |
| 再ランク付け(定数・重み・種・候補順位・リスタート選択) | 15+ | 最良 +0.27、最悪 −5.19 |

90フェーズ磨かれたヒューリスティクスは局所最適に近く、上書きすると負けます。
一方で**実行可能集合は、検証されたことのないハード制約で人為的に狭められていました**。

その代表が `forbidden_hit`(非優先荷物を優先荷物の上に、非ソフトをソフトの上に置くことを
禁じるハード制約)です。env フックが存在せず、**38軸の探索で一度も A/B されていませんでした**。

### (4) ローカル評価は予測能力を失った

| 手 | ローカル配置率増 | 本番配置率増 | 転移率 |
|---|---:|---:|---:|
| last-resort | +1.29pp | +1.88pp | 1.46 |
| ordcount | +2.51pp | +0.51pp | 0.20 |
| oc_cf | +4.47pp | **−0.40pp** | **−0.09** |

**ローカル増分が大きいほど転移率が悪化しています = 26シーンへの過適合。**
以後、ローカル A/B は「壊れていないことの確認」にのみ使い、採否は機序の妥当性と
本番実測で決めています。

### (5) 死因は100%が同じ1経路

`planner.plan()` が「どの荷物もどの向き・位置にも置けない」を返すと、
`agent.py` の `_fallback_place_pos()` に落ちます。この関数は**床レベルの9点
(1コンテナ・1荷物・向き0固定)しか見ません**。

そして総当たり測定の結果、**死亡局面で実在する合法解の z 源は100%が「既配置荷物の上」で、
床は0件**でした。つまりフォールバックは**解が存在しない唯一の高さを探し続けていました**。

死亡時の `orientation = 0` は、このフォールバックのハードコード値であり、
**ソルバが向きを選び損ねた結果ではありません**。これは死因を判別する簡便な指紋になります。

## 6. last-resort の設計(最大の成果なので詳述)

### 測定に基づく設計

現行ソルバで死亡25局面を総当たりした結果(`results/phase96_*.json`):

- **14/25 (56%)** に、内包・搬入経路とも合法な解が実在した
- その解 **250/250 (100%)** が `support_ok` 単独で落選。内包・搬入・候補生成・向き・tier は無罪
- 内訳は 閾値のみ 22.8% / **`forbidden_hit` 併発 77.2%** / `forbidden_hit` のみ 0%
- `plan()` に予算 1e15(実消費の2300万倍)を与えても **0/25** しか見つからない
  = 予算・グリッド密度は無罪
- 損失 745個のうち **496個(67%)** が「合法解が実在した」14シーンで失われていた

`forbidden_hit` のみが 0% なので、**それを外すだけでは1件も救えません**。閾値も同時に
緩める必要があり、そのため段階的なラダーにしています。

### 実装

```
plan() が全コンテナ・全荷物・全向き・密グリッドで合法手ゼロを返した直後だけ発火
  Lv1: forbidden_hit(下敷き禁止)のみ解除
  Lv2: ＋支持閾値を緩3相当(0.25 / 0.3 / 0.30)へ
  Lv3: ＋支持は「接触面積 > 0」のみ。定着可否は実物理に委ねる
最初に合法手が出た段階で採用する
```

**発火はオンライン `policy()` の実手番のみ**です。実装時に `planner.plan()` が
オフライン構築(`simulate.py` / `ordering.py`)からも呼ばれることが判明したため、
`plan(..., lastresort=False)` を追加して `agent.py` の1箇所だけが `True` を渡す形に
限定しました。**オフラインの純幾何シミュで緩めると代理関数が楽観化し、
過去に失敗した DRIFT_MODEL(−11)と同型になります。**

### なぜ下振れが無いか

発火点は、現状 `_fallback_place_pos()` が非合法位置を返して**100% sudden death している
1手**です。選択肢は「確定死」か「支持の甘い位置に置いて、定着に失敗すれば同じく死ぬ／
成功すればエピソード継続」であり、**確定死 vs 確率的生存**の交換なので構造的に損しません。

### ラダーの順序が効く(実測)

最も緩い Lv3 へ直行する版(`L3only`)を提出したところ **58.470(−2.35)**。配置数はほぼ
同一(−0.06pp)なのに足切りゲート4指標が揃って −2.7〜−3.7 落ちました。

**同じ数だけ積んでいるのに跨げたシーン数が減った** = ラダーが「その場で通る最も穏やかな
緩和」を選ぶことで救出配置の質が保たれ、それがその後のエピソード生存を左右しています。

なお、救出候補を支持比率優先で選ばせる版(`supfirst`)は **−2.27** で失敗しました。
通常スコアの `back_term`(奥選好)と `corridor_penalty`(通路)を上書きしてしまい、
救出配置が後続の搬入経路を塞いだためです。**救出時も通常スコアは必要**です。

## 7. 3D可視化から得られた知見

`tools/trace_episode.py` でエピソードを再生し、沈降後の実姿勢を含むトレースを
JSON に書き出せます。これを Three.js のビューア(Artifact)で観察しました。

**目視が、数百回の A/B では見つからなかった構造を掘り当てました。**

### 発見: 左ポケットの封鎖(22%)

全シーン・全コンテナで**左端が空**でした(A08 は左3割が完全未使用)。原因は
`geo.transport_x_bounds` が搬入スポーン x の下限に `cut_x` を**全高一律で**加算しており、
左 0.45m(コンテナ長の22%)が「スライドでしか入れない袋小路」になっていたことです。

```
空のコンテナ                 左ポケット到達可能 9/9
ポケット入口に1個置いた後      左ポケット到達可能 0/9   ← 33点中21点が同時に死ぬ
```

**1個置くだけで恒久封鎖されます。** そしてソルバは実際にその入口に置いていました。

ただし**修正は失敗しました**。下限を切り欠き平面から高さごとに解析的に計算する版は
26シーン A/B で 786 → 469(−317)、25/26シーンが `is_valid` で即死。
切り欠きが**左下**にあるため斜面は右下→左上に立ち上がっており、荷物は `START_Z` で
持ち上げてから降下する以上、**左側で降下すると斜面を貫く**。
`+cut_x` の一律下限は過剰な保守ではなく、必要な制約でした。

### 棄却した仮説: 「奥寄せ → 完走」

唯一完走する A06 は y重心が最大(+0.331)でしたが、**y重心 vs 充填率の相関は −0.851**で、
A06 の充填率は最低の16.2%。「奥詰め規律の強さ」ではなく「そもそも詰まっていない」
ことの裏返しでした。**因果は無く、層分割方面は追いません。**

### 塔化は症状であって原因ではない

床占有率は全シーン最大54%、大半は32〜40%止まりなのに、進捗25%時点で最大到達高さが
1.0〜1.4m(天井1.61m)に達していました。そこで floor-first(床候補が1つでも合法なら
床に限定)を実装したところ、**26シーン中25シーンで挙動が変わりませんでした**。

**⇒ ソルバは既に床候補があれば床を選んでいた。床占有の低さは「後回し」ではなく
「残った床に到達できない」ことが原因で、塔化はその症状です。**

## 10. 方針(2026-09-09 に変更)

提出枠の運用を **「メダルか無しか」** に変更しました。

それ以前の方針(2枠目を「主枠と独立した故障モードを持つ保険」にする)は、
**主枠を守ることに価値がある**ことを暗黙の前提にしていました。目標が銅メダル(≒60)である
以上、60に届かなければ 58.5 も 55.96 も等しく圏外であり、この前提は目的と整合しません。

**目的関数を E[選択されたスコア] から P(max(枠1, 枠2) ≥ 目標) に変更**し、
2枠目は保険ではなく最も分散の大きい信用できる賭けに充てます。

あわせて、**頑健性ゲート(「悪化シーン数が少ない強い信号でないと採用しない」)は
最終枠の選択にのみ適用し、提出するかどうかには適用しません**。提出は1日5回でき、
枠を消費するのは選択期限であって提出ではないためです。ローカル信号が本番へ転移しないことは
5回確認済みで、唯一信頼できる信号は public です。
