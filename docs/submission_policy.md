## 2. ステップ1: 最終評価の方式(確認結果)

### 確認できたこと

  という記載がある。これは**1日あたりの提出回数上限**であり、最終選択できるファイル数

  ハードコード禁止(隠しテストは全く別)」** という記載がある。これは
  **「配布されているローカルconfigとは別に、隠しテスト(採点用の入力)が存在する」ことを

  ——つまり本リポジトリは公式の応募要項・規約文書そのものを意図的に含んでいない。

### 見つからなかったこと

以下は**リポジトリ内のいずれの資料にも記述が見つからなかった**:

1. 最終評価がpublicと同じシーン集合で行われるか、別の非公開集合(private)で行われるか
2. 最終提出で選択できるファイル数(2という認識の裏付け)
3. privateスコアの存在、およびその公開タイミング

**推測で断定しない。** `README.md`が「コンテスト公募要領そのものの転載を避けている」と

NEDO Challengeの応募要項)は本リポジトリの外にあり、本調査(リポジトリ内資料の確認)の

直接確認する必要がある。**

### 判定

指示された判断基準の「不明」に該当する:

> 不明 → Phase55を主枠にする(バグを残す合理的な根拠がない)

**主枠: `submissions/mysolver_submit_phase55.zip`
(SHA256: `85bd11db422ed2fce01ca10c8f286ff608564abc2b4a720848a2bfaee8a8418e`)。**

根拠: 評価方式が確認できない以上、「public/private のどちらでも、既知のバグ

作り直す必要はない(コードは変更していないため、再現ビルドは既存コミット履歴から

## 4. ステップ2: ρ-testの規約確認(確認結果)

### 調査対象

§2と同一の資料(README.md / CLAUDE_CODE_指示書.md / docs/migration_to_mac.md /
docs/技術対策.docx)を、`規約`/`リバース`/`reverse`/`probing`/`プロービング`/`不正`/
`禁止`等のキーワードで検索した。

### 確認できたこと

`CLAUDE_CODE_指示書.md`(§8 禁止・境界)には以下の3項目のみが明記されている:

```
- 特定 config/コンテナ寸法/荷物順への**ハードコード禁止**(隠しテストは全く別)。汎用実装。
- 評価時**ネット接続不可**。有償API不可。外部データはオープンなもののみ。
- 期間中コード/モデルのチーム外共有禁止(公式Discordのみ可)。
```

これら3項目のいずれも、**「提出物の挙動・実行時間を診断チャネルとして使うこと」
(=採点に使われない`optimization`/`policy`の実行時間フィールドへ情報を符号化すること、
Phase37/40で既に実施している手法)を直接禁止する文言ではない。**

### 見つからなかったこと

以下は**リポジトリ内のいずれの資料にも記述が見つからなかった**:

1. 提出物の挙動・実行時間の利用に関する制限
2. 非公開テストセットのプロービング禁止に類する条項
3. 採点系のリバースエンジニアリング禁止に類する条項

### 判定

**「見つからなかった」ことは「制限が無いと確認できた」ことを意味しない。**
`README.md`が明言するとおり、公式の応募要項・利用規約そのものは本リポジトリに
含まれていない。**したがって「制限なし」と判定することはできず、「制限の有無を
リポジトリ内資料からは確認できなかった」という以上のことは言えない。**

指示された判断基準(「制限あり→打ち切り」「制限なし→次フェーズで実施を検討」)の
どちらにも該当しない、**第三の状態(未確認)** である。「無いと断言できない」ことと
「抵触する可能性が高い」ことは別であり、ここでは前者(未確認)であって後者
(高リスク)だと主張するものではない。

### 対応

**ρ-test原因究明の診断ビルド実施は、この点が確認されるまで見送る。** 理由:

- 本調査(リポジトリ内資料)だけでは確定できない一次資料(SIGNATEの利用規約・
  NEDO Challengeの応募要項)を、ユーザー自身が直接確認する必要がある。
- 確認すべき点は具体的に絞り込めている:「提出物の実行時挙動(壁時計等)を、
  採点結果とは別のフィードバックチャネルとして利用することの可否」の1点のみ。
- 既にPhase37/40で同種の手法(`optimization`/`policy`の壁時計へ内部状態を符号化する
  テレメトリ)を**実施・提出済み**であることも申し送りとして残す(下記参照)。

**申し送り**: 本プロジェクトはPhase37(n=4診断)・Phase40(2チャネル符号化設計)で
既に「採点に使われない実行時間フィールドへ内部状態を符号化する」手法を実装・
提出している。もしこの手法が規約上問題になるとすれば、**既に実施済みの提出が
該当する**ことになるため、規約確認は「今後どうするか」だけでなく「既に行ったことが
問題なかったか」の確認としても優先度が高い。

### Phase61追記: セミナーでの確認により§4の「未確認」状態が解消

公式チュートリアルセミナー(2026年、SIGNATE/三菱総合研究所)で、運営が口頭で
以下を明言した(セミナー動画 44:35 付近):

> 「フィードバック結果から、評価基盤で実装されている評価関数の中に設定されている
>   パラメーターとか、手荷物の具体的な内容とかを解析したりするのは基本的にNGなので
>   やめていただきたい」

これにより、上記「対応」節で**未確認**として保留していた論点
(「提出物の実行時挙動を、採点結果とは別のフィードバックチャネルとして利用することの
可否」)は、**確認済み・禁止**に確定する。実行時間への符号化は、まさに「フィードバック
結果(採点結果)から評価基盤側の情報を間接的に引き出す」行為であり、運営が名指しで
やめるよう求めた対象に含まれると判断する。

**確定した方針**:

- **ρ-test系の診断ビルド(実行時間への内部状態の符号化)は完全に断念する。**
  Phase40で設計した行番号符号化を含め、以後いかなる形でも再開しない。
- `MYSOLVER_TELEMETRY` 系のコード(`agents/mysolver/ordering.py`,
  `agents/mysolver/agent.py`)は**削除はしないが、既定無効(`=0`)のまま二度と
  有効化しない**。既に無効時は分岐にすら入らない実装になっており、現状維持で足りる。
- 上記「申し送り」にあるPhase37/40の**実施・提出済み**の事実は、今後の規約解釈上の
  リスクとして記録を残す(削除・改変しない)。新たに同種の手法を追加することはしない。
- **一次資料の範囲を拡張する**: これまで本ファイルでは「規約文書(利用規約・応募要項)の
  みが一次資料であり、リポジトリ内には存在しない」という前提で論じてきたが、
  **今後は公式が開催したチュートリアルセミナーでの運営の口頭説明も一次資料に含める。**
  文書化されていない口頭の運営見解であっても、明示的に述べられたルールは規約と
  同格に扱う。

この確定を受けて、評価基盤(スコアラー・シミュレータ)側の非公開パラメーター
(足切り閾値、揺らしテストの正確な振幅値など)を、本番の集計スコアから逆算・特定
しようとする分析も、同じ理由で行わない(詳細はPhase61の報告を参照)。
